config.list 기반 워크플로 설정 UI 목업 · 261116

좌하단 톱니(설정) 팝오버를 진입점으로, config.list가 돌려주는 37개 노브 카탈로그(쓰기 계약·셀렉터·현재 값)를 그대로 렌더링해 하네스별·범위별로 조정하는 화면입니다. 값은 모두 예시이며 실제 설정 값을 담지 않았습니다. 버튼·토글·입력은 실제로 동작합니다(저장은 흉내만).

1진입점: 기존 설정 팝오버에 “워크플로 설정” 섹션 추가

지금의 설정 팝오버(dashboard.tmpl:124-126, 300px)는 레이아웃·입력·테마·언어처럼 이 브라우저에만 저장되는 항목뿐입니다. 37개 노브를 300px 팝오버에 넣는 대신, 팝오버 맨 아래에 요약과 “열기” 버튼을 두고 넓은 시트로 넘깁니다.

왜 팝오버 안에 다 넣지 않나
  • 37개 노브 중 12개는 Claude 어댑터, 15개는 Pi 어댑터 전용이고, 4개는 하네스마다 값이 따로입니다. 300px 폭에서는 “하네스 × 범위 × 값” 세 축을 함께 보여 줄 수 없습니다.
  • 기존 항목(브라우저 로컬)과 새 항목(설정 파일)은 저장 위치가 다르므로 섹션과 각주로 분리합니다. 지금의 “이 브라우저에 저장됩니다.” 문구는 위 섹션에만 걸리게 됩니다.
  • 요약 칩: 이 레일이 보고 있는 작업공간, 기본값이 아닌 노브 수, 하네스별로 값이 갈리는 노브 수.
  • 시트는 모달로 열리며 Esc·바깥 클릭으로 닫힙니다. 저장하지 않은 변경이 있으면 닫기 전에 확인합니다.

2워크플로 설정 시트 · Claude 탭 · 저장 위치 “프로젝트” · 저장하지 않은 변경 있음

하네스 탭은 보기 필터이자 편집 대상 버킷입니다. Claude 탭에서는 공통 노브 + Claude 버킷 + Claude 어댑터 설정만 보이고, 하네스별 노브(화이트보드, 트래커, 프롬프트 재정의, 모델 티어)는 Claude 버킷을 편집합니다. 오른쪽 열은 실제로 적용되는 값의 출처를 저장 위치와 비교해 보여 줍니다(“전역에서 상속”, “프로젝트에 저장됨”, “기본값”). 변경은 바로 쓰지 않고 아래 바에 모았다가 한 번에 저장합니다.

3전체 탭 · “하네스별 설정만” 필터 · 저장 위치 “전역”

전체 탭에서 하네스별 노브는 Claude / Codex / Pi / 공통(*) 네 칸으로 펼쳐져 한눈에 비교됩니다. 각 칸은 해당 하네스에 실제로 적용되는 값과 출처를 보여 줍니다. 저장 위치를 “전역”으로 두었을 때 더 높은 범위(프로젝트)에 값이 있으면 “프로젝트 값이 우선” 경고로 “바꿔도 효과 없음”을 미리 알립니다. 해석 순서는 실제 코드와 같습니다: 하네스 버킷(모든 범위) → 공통 버킷(모든 범위) → 기본값 (mcp/config_registry.go:166-182). 그래서 공통 버킷의 프로젝트 값은 Claude 버킷의 전역 쓰기를 가리지 않으며, 경고도 같은 버킷 안에서만 뜹니다(트래커 행 참고).

4긴 프롬프트 재정의 편집: 목록에는 미리보기만, 편집은 측면 편집기

프롬프트 재정의와 캡션 스타일 같은 긴 문자열은 목록에 두 줄 미리보기와 글자 수만 보여 주고, “편집…”을 누르면 시트 오른쪽에 편집기가 열립니다. 편집기 안에서 하네스 버킷을 바꿔 가며 같은 노브의 다른 버킷을 고칠 수 있고, 기본 블록(seed)과 비교할 수 있습니다. “변경 대기열에 추가”는 바로 쓰지 않고 시트 하단의 변경 묶음에 넣습니다.

5스키마 → 컨트롤 매핑 (config.list 37개 노브 전수)

6구현 시 바뀌는 것

필요한 데몬 라우트

  • 지금은 없음. 대시보드 데몬의 라우트 등록(wsdashboard/daemon.go:729-776, Handler)에 config 읽기·쓰기 라우트가 없고, wsdashboard 패키지는 wsconfig를 전혀 import하지 않습니다. 기존 설정 팝오버는 브라우저 로컬 저장만 씁니다: 레이아웃·입력은 localStorage(dashboard.js:40-48, 키 ws.dashboard.layout · ws.dashboard.input dashboard.js:408), 언어는 쿠키 ws_dashboard_lang(dashboard.js:443). 팝오버 열기는 dashboard-rail-popovers.js:442-447.
  • 추가할 것 (제안): GET /config?root=<작업공간> — config.list JSON과 같은 모양(카탈로그 + 범위별 값, 세션 키 없이). POST /config/tune — {key, harness?, scope, value | reset, root} 묶음을 받아 config.tune과 같은 검증·쓰기 경로로 처리하고 노브별 결과를 돌려줌. 시트의 “저장”은 한 번의 POST로 여러 변경을 보냅니다.
  • 게이트: 두 라우트 모두 기존 TrustedWrite(wsdashboard/access.go:162-171: 이 컴퓨터의 브라우저 + same-origin, LAN 토큰만으로는 불가)를 씁니다. GET도 프롬프트 재정의 원문을 담으므로 LAN에서는 숨기는 편이 맞습니다.
  • 로직 위치: config.list/config.tune은 MCP 서버 메서드에 묶여 있습니다(mcp/server.go:971-1003 list, :1009- tune, buildTuningCatalog :2864, 어댑터 노브 mcp/config_manifest.go:468-494). 데몬이 직접 부르려면 카탈로그 생성과 쓰기 검증을 공유 패키지로 옮겨야 합니다. 살아 있는 세션의 MCP로 프록시하는 대안은 세션이 없을 때 동작하지 않아 비권장.

호환성 등급: T0 예상 (추가만)

  • 새 HTTP 라우트와 새 시트는 순수 추가입니다. 구버전 바이너리는 이 라우트를 모르고, 쓰지도 않습니다.
  • 쓰는 파일은 config.tune과 같습니다: 전역 ~/.ws/config.json, 프로젝트 ~/.ws@<id>/config.json, 저장소 <repo>/.ws-workflow/config.json (wsconfig/scope.go:9-26). 조건: 데몬이 wsconfig의 기존 쓰기 경로를 재사용해야 합니다. 자체 직렬화로 파일을 통째로 다시 쓰면 모르는 필드가 사라져 T0이 깨집니다(AGENTS.md 기준 복구 경로 없는 전체 파일 손실은 T2도 아님).
  • UI를 위해 config.list에 필드(type, minimum, label 등)를 더하면 JSON 추가 필드이므로 구버전 소비자는 무시합니다(T0). 기존 필드의 의미를 바꾸지는 않습니다.

config.list가 UI에 주지 않는 것 (스키마 공백)

  1. G1. 값 타입·범위가 기계 판독 불가. 내장 노브는 “Value as a string: an integer of at least 1”처럼 산문으로만 말합니다. 어댑터 매니페스트에는 type/minimum/maximum/pattern이 있지만(agents-plugin/config-manifest.json, mcp/config_manifest.go:68-78) 카탈로그로 옮길 때 default만 남고 나머지는 버려집니다(config_manifest.go:468-494, tuningField는 name/description/enum/required뿐 server.go:2842-2847).
  2. G2. 내장 노브의 기본값 필드 없음. default는 어댑터 노브에만 있고 내장 노브는 설명 산문(“builtin off”)에 묻혀 있습니다(server.go:2816-2818). “기본값으로” 미리보기에 필요합니다.
  3. G3. 짧은 라벨·그룹·다국어 없음. id와 긴 영어 설명뿐입니다. 대시보드는 11개 언어로 현지화되어 있으므로 라벨/설명의 번역 소유자가 필요합니다(질문 Q5). 이 목업의 한국어 라벨과 그룹은 손으로 만든 것입니다.
  4. G4. 하네스별 현재 값이 불완전. 화이트보드·트래커는 버킷 노브인데도 current가 호출한 세션의 하네스 하나의 {value, scope}뿐입니다(currentHarnessBucketedValue server.go:3252-3258, s.currentHarness()). 프롬프트 재정의는 버킷별로 주지만 빈 버킷은 생략합니다. 4칸 매트릭스를 그리려면 버킷 × 범위 전부가 필요합니다.
  5. G5. 이긴 값만 있고 범위별 스택이 없음. current와 resolved_overrides 모두 승자 하나만 줍니다. “전역에 있는 값이 프로젝트 값에 가려짐”, “지우면 무엇으로 돌아가나”를 보여 주려면 범위별 값 목록이 필요합니다.
  6. G6. 카탈로그가 호출자에 따라 달라짐. 어댑터 노브는 그 MCP 인스턴스를 띄운 패키지의 매니페스트(WS_MCP_CONFIG_MANIFESTS, config_manifest.go:17-27)에서만 옵니다. 그래서 Claude 세션의 config.list에는 pi.* 15개가 없고, 실제로 resolved_overrides에는 pi.* 값이 보이는데 노브 목록에는 없습니다. 하네스 무관한 데몬은 설치된 패키지(ws·wsflow·pi) 매니페스트의 합집합이 필요합니다. 같은 키라도 패키지마다 기본값이 다릅니다(예: claude.mailbox_drain은 ws 매니페스트가 direct, 이 세션의 카탈로그는 notice).
  7. G7. 셀렉터 enum 불일치. 공통 버킷이 프롬프트·화이트보드·트래커는 *, 모델 티어는 default, 저장 키(repo_key)는 all입니다. 또 scope enum에 repo가 있어도 repo_scope:false인 키(dashboard.lan_enabled 등)가 있어 두 필드를 함께 봐야 합니다.
  8. G8. 적용 시점 정보 없음. workflow.*는 “다음 워크플로 매뉴얼 로드부터”, 어댑터 설정은 세션 재시작, dashboard.port는 데몬 재시작이 필요하지만 설명 산문에만 있습니다. 저장 토스트에 “언제 적용되는지”를 말하려면 필드가 필요합니다.
  9. G9. 프롬프트 재정의의 기본 블록(seed) 원문 없음. 설명 한 줄만 있어 편집기의 “기본 블록 보기/변경 비교”를 채울 수 없습니다.
  10. G10. writer 계약이 MCP 도구 이름. writer.tool = "config.tune"은 MCP 호출 계약이라 브라우저에는 그대로 쓸 수 없습니다. HTTP 라우트가 같은 인자 모양을 받는다면 매핑은 기계적입니다.

위험

  • 기본 저장 범위. 시트는 세션 밖에서 열리므로 세션 범위는 의미가 없습니다(세션 키가 없으면 세션 값도 안 보입니다). 남는 선택은 전역 · 프로젝트(작업공간마다 다름) · 저장소(커밋되는 파일). 기본값을 무엇으로 둘지는 제품 결정입니다(Q1).
  • 버킷 우선순위 함정. Claude 버킷의 전역 값이 공통 버킷의 프로젝트 값보다 이깁니다(하네스 버킷을 모든 범위에서 먼저 찾음, config_registry.go:166-182). 사용자 직관(“프로젝트가 전역을 이긴다”)과 어긋나므로 출처 배지에 버킷까지 표시해야 합니다.
  • 저장소 범위 쓰기는 작업 트리를 더럽힘. config.tune처럼 스테이징하지 않으므로 git 서랍에 ±로 나타납니다. 시트에서 저장소 범위를 고르면 “커밋 대상 파일” 경고가 필요합니다.
  • 권한 모델 우회. config.tune은 일부 키에 리드 세션 키를 요구합니다(server.go:1043-1052). 대시보드 저장은 사용자의 직접 조작이라 정당하지만, 그 게이트 밖의 새 쓰기 경로가 생깁니다. TrustedWrite로 이 컴퓨터의 브라우저로만 묶어야 합니다.
  • 실행 권한을 담은 노브. worktree.profile.*의 훅은 argv 명령을 실행하고, agent.profile.*은 도구·권한을 정하고, agent.git_search_roots는 읽기 범위를 넓힙니다. 1차는 읽기 전용을 제안합니다(Q4).
  • 동시 편집. 리드가 config.tune을 하는 사이 대시보드가 저장하면 마지막 쓰기가 이깁니다. GET 응답에 파일별 수정 시각/해시를 주고 POST에서 비교해 충돌을 알리는 편이 안전합니다.
  • 적용 시점 오해. 저장 직후 아무 변화가 없으면 사용자는 실패로 읽습니다. G8이 해결되기 전까지는 노브 그룹별 고정 문구로라도 적용 시점을 보여 줘야 합니다.
