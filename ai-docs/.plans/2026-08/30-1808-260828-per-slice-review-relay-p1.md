# Plan: 260828-refactor-per-slice-review-relay — Phase 1: Atomically replace the multi-cycle slice loop

## Relevant Ticket Contract
- Normal loop: review #1 -> one repair relay -> closeout, with no default review #2 (Decisions).
- Every non-clean Critical/Important finding from review #1 gets exactly one recorded disposition marker: `[fixed]`, `[won't fix: <reason>]`, `[deferred: <reason>]`, or `[escalate: <reason>]` (Decisions).
- Critical exception: if review #1 contains any Critical finding, one repair relay is followed by a Critical-scoped review #2; a remaining Critical after that is a hard stop/escalation with durable evidence, not a third relay (Decisions; Phase 1 body).
- Do not invoke `review-adjudicator` or the elevated-implementer path in the normal one-relay flow; retain/reshape them only where the Critical exception demonstrably needs them (Decisions; Constraints).
- Binding surface is the generated Go instruction text plus its tests — changing shared prose alone is insufficient (Constraints).
- Preserve `Critical`/`Important`/`Minor` vocabulary; do not introduce a `fatal` severity (Constraints).
- Preserve the existing risk-based `lead-only`/`single`/`partitioned` allocation resolver; `lead-only` must not gain relay vocabulary (Constraints).
- Atomicity: land the default one-relay path and the Critical-only branch together — do not ship the former without the latter (Phase 1 body).
- Verification boundary (Phase 1): generated instructions + focused Go tests prove `single`/`partitioned` issue exactly one ordinary relay after review #1, preserve `[won't fix]`, and expose no re-review/adjudication instructions on the ordinary path; `lead-only` stays free of relay terms; tests cover no-Critical closeout after one relay, Critical causing exactly one scoped re-review, an unresolved Critical not scheduling another relay, and the generated instruction giving an explicit hard-stop handoff with durable evidence paths.

## Risk Signals
- Structural finding (not stated verbatim in the ticket, derived from the Decisions text): the Critical branch's "one repair relay" is the *same* relay as the ordinary path's, not an additional one — the ticket's phrasing is "one repair relay followed by a Critical-scoped review #2," and there is exactly one relay slot in the entire new model, ordinary or Critical. That means `implementer-elevated`'s "next relay" trigger and `review-adjudicator`'s "before the next review" trigger have no relay slot to fire into anywhere in the new model, not only on the ordinary sub-path. Recommendation: drop both clauses entirely rather than reshaping either into a narrow Critical-branch reference. The ticket phrases this as "evaluate whether ... has a narrowly justified role" rather than mandating removal, so flagging this reasoning for lead/implementer confirmation before finalizing — the one alternate reading is that `review-adjudicator` could dispute an implementer's `[won't fix: <reason>]` on a Critical finding before the hard stop fires, but the ticket's "a remaining Critical finding stops the slice from merging" wording reads as unconditional, not disputable.
- The instruction text is generated once by `enter.implement`, before review #1 has run, from verdict fields that cannot know whether review #1 will surface a Critical finding. The Critical branch therefore must be stated as conditional prose inside the single generated instruction string ("if review #1 contains a Critical finding, then ..."), the same way today's clauses already state conditional behavior (e.g. the final-cycle clause's "after the last budgeted cycle returns..."). No new runtime branch-selection mechanism is needed or in scope.
- The hard-stop outcome has no existing analog to reword — Verification requires "the generated instruction gives the lead an explicit hard-stop handoff with durable evidence paths," which is new text. Model it on the existing file-first evidence pattern already used by the clauses being replaced, consistent with the Decision to keep findings/dispositions file-first (paths, not copied bodies).
