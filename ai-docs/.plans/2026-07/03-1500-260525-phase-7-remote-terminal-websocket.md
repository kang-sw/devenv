## Codebase Findings (from reference worktree draft, verified design, re-verify exact current-tree line numbers before implementing)
- `tokio-tungstenite = "0.29"` is ALREADY a workspace dependency (`ws-dashboard/Cargo.toml`), currently only wired as a **dev-dependency** in `crates/daemon/Cargo.toml` (used by existing local-terminal-websocket tests). This phase must promote it to a normal dependency (remove the dev-dependency line, add it to `[dependencies]`) since production code (the upstream relay client) now needs it, not just tests.
- Draft design for the new server-scoped WebSocket handler (`servers.rs`):
  - `server_scoped_terminal_websocket(state, (server_route, terminal_id), Query<TerminalWebSocketQuery>, WebSocketUpgrade) -> Response`: for `server-local`, dispatches in-process to the existing `terminal_websocket` handler unchanged. For linked servers, resolves via `resolve_server_scoped_forwarding` (same refusal semantics as every other phase — dot-free, auth-required 409, unreachable 502, etc., BEFORE ever attempting the upgrade), then opens an upstream WebSocket connection to the linked daemon (`tokio_tungstenite::connect_async` with the bearer token as an `Authorization` header on the upgrade request) and, only on successful upstream connect, calls `upgrade.on_upgrade(...)` to complete the browser-side upgrade and relay frames.
  - Upstream URL construction: reuse the existing `remote_url(endpoint, legacy_path)` helper (already used by Phase 2+ one-shot forwarding) to build `http(s)://.../api/dashboard/terminals/{terminal_id}/socket?after={after}`, THEN swap the scheme to `ws`/`wss` (http→ws, https→wss) — the draft's first pass used `url.set_path(...)` directly (dropping any path prefix baked into the stored endpoint), which its own follow-up commit `82b86660` had to fix to go through `remote_url` first. Implement it correctly the first time using `remote_url`, do not repeat that mistake.
  - Frame relay: split both the axum `WebSocket` (browser side) and the `tokio_tungstenite::WebSocketStream` (upstream side) into sender/receiver halves, then `tokio::select!` loop relaying frames bidirectionally with explicit type conversion between axum's `ws::Message` and tungstenite's `Message` (Text/Binary/Ping/Pong/Close mapped 1:1; tungstenite's raw `Frame` variant has no axum equivalent and should be dropped/ignored, not error). On EITHER side closing or erroring, break the loop and best-effort send a Close frame to the other side, then let both sockets drop (implicit cleanup, consistent with Phase 4/5's SSE proxy cleanup philosophy).
  - Upstream connection failure handling: `tokio_tungstenite::connect_async` returning `TungsteniteError::Http(response)` means the upstream rejected the upgrade (map to that status, e.g. propagate as a bounded refusal) — the browser-side upgrade must NOT be completed at all in this case (respond with a normal HTTP error response, not a broken WebSocket). Any other connection error (network unreachable, TLS failure, etc.) maps to `502 BAD_GATEWAY`.
- `router.rs`: register the new `/api/dashboard/servers/{server_route}/terminals/{terminal_id}/socket` route next to the existing scoped terminal routes from Phase 6. The socket route was intentionally left unregistered by Phase 6 — this phase is what registers it.
- `terminal.rs`: `TerminalWebSocketQuery.after` field needs to be `pub` (currently private in the pre-Phase-7 tree, per the draft's tiny 1-line visibility fix) so `servers.rs` can read it when building the upstream URL.
- Tests (`a2af58b1`-analog for Phase 7 is folded into `3a84ba6f`+`82b86660` themselves): route/auth refusal tests (dot-free, unknown-server 404, auth-required 409, unreachable 502 — all BEFORE upgrade, i.e. these should return normal HTTP error responses, not attempt a WebSocket handshake); a real end-to-end WebSocket relay test using two real spawned daemon instances (matching Phase 6's `linked_server_terminal_forwarding_preserves_lifecycle` pattern) that creates a terminal, connects the server-scoped WebSocket, sends typed input through it, and asserts output arrives relayed through the gateway; a bidirectional non-text-frame relay test (binary/ping/pong, per the draft's `82b86660` hardening — the first pass apparently only tested text frames); a cleanup test proving that closing either side (browser close or upstream close) tears down the other side's connection without hanging.
- Given this is the LAST phase, plan for a final ticket-wide check after closeout: confirm no phase left an inconsistent spec statement, and that the `## API Inventory` section's "Must become server-aware" list is now fully covered (cross-check against Phases 2-7's landed routes).
