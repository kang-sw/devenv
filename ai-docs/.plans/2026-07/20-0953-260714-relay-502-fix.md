# Plan: Linked-server terminal WebSocket relay 502 (260714-bug-linked-terminal-ws-relay-502) — Phase 2 (real fix): frontend selection-stickiness (server-scoped D5 pattern) + OPEN-socket cleanup guard

## Relevant Ticket Contract

- Confirmed root cause (frontend, not backend): a linked server's poll refresh
  can momentarily omit the currently-selected `gitLinkedWorktree` child's
  `workRoot` entry from an otherwise non-null resource tree.
  `resolveWorkbenchSelection` (`resourceModel.ts:441-490`) then can't match
  `selectedId` anywhere in the walked tree and silently returns `fallback`
  (the first root walked, `:474`, returned `:489`) — normally the primary
  root. Selection flips to the primary root, the sub-worktree's wrapper gets
  `display:none`, the 100ms `focusWatchdog` sets `paneVisible=false`, and the
  terminal socket effect's cleanup closes the by-then-OPEN socket. Next poll
  the entry reappears, selection flips back, a new socket opens for the same
  `terminalId` — repeating on the ~5s poll cadence (~4s observed).
- Two-pronged fix required (both must land):
  1. **Prong 1** — re-provide selection stickiness for "the currently-selected
     root disappeared from an otherwise-present tree", modeled on the
     already-vetted **server-scoped D5 pattern**
     (`withLastNonNullResourcesByServer`/`resolveActiveResources`,
     `resourceModel.ts:236-261`). Must NOT reintroduce the D3-deleted unscoped
     `lastActiveRootKeyRef`/`lastActiveRootServerIdRef` cross-render ref
     memory (sibling ticket `260714-refactor-dashboard-active-root-atomic-select-pure-derivation`,
     decision D3 — that shape caused 4 regressions).
  2. **Prong 2** — hardening at `App.tsx:8615`: a `paneVisible` flip must not
     `close()` an OPEN socket for a terminal that is still logically open.
     Mechanism must be stated explicitly (not "mirror CONNECTING" by
     analogy) and must not leak connections on a genuine hide/unmount.
- Distinguishing signal for Prong 1 (ticket-specified): the server's resource
  tree itself is still non-null and present in `resourcesByServer` (D2's
  slot-level fallback does not engage) but the previously-selected root's
  entry is absent from that tree on this one poll. A genuine removal is
  distinguished from a transient omission by persisting across **more than
  one** poll cycle — the sticky cache must expire once the omission repeats,
  not hold indefinitely.
- Prong 2 constraint (ticket-specified): prefer keying teardown on **logical
  terminal presence** rather than transient `paneVisible`; the ticket
  explicitly includes "pane hidden behind another Dockview tab" as a case
  that must NOT tear down an OPEN socket — this is a real (if narrow)
  behavior change, not just anti-churn.
- RU1 (`App.tsx:4400-4424` keep-alive/background raw lookup): must be
  confirmed during implementation as either folded into this fix or
  documented as not-implicated — not left unexamined.
- RU2 (unlanded atomic `selectRoot` refactor): explicitly OUT of scope; do
  not implement it here.
- Acceptance/Verification boundary (ticket-specified): frontend
  build/typecheck; a unit test for `resolveWorkbenchSelection`/
  `deriveWorkbenchView` stickiness under a transient single-poll omission; a
  test or lighter-weight check for the `App.tsx` OPEN-socket cleanup guard;
  dogfood no-churn confirmation (>=5 min, no ~4s recreation loop, no 8-pane
  bursts) — **the human runs the Windows frontend for this**, not the
  executor.

## Codebase Findings

- `ws-dashboard/frontend/src/resourceModel.ts#L236-261` — the vetted D5
  pattern to model Prong 1 on: `withLastNonNullResourcesByServer` writes a
  per-server last-good cache only when a fresh non-null value differs from
  what's cached; `resolveActiveResources` reads `raw ?? cache ?? null`. Both
  are pure, server-keyed, and already unit-tested
  (`resourceModel.test.ts:461-513`).
- `ws-dashboard/frontend/src/resourceModel.ts#L441-490` — `resolveWorkbenchSelection`.
  Returns early on workspace-id match (`:456-464`), root-id match (`:476-478`
  via `rootSelection` computed at `:468-473`), or nested instance match
  (`:480-485`). `fallback` is set to the FIRST root walked (`fallback ??= rootSelection`,
  `:474`) and returned only if nothing above matched (`:489`). Today there is
  no way for a caller to tell "matched `selectedId` exactly" apart from
  "fell through to fallback" — both return the same `WorkbenchSelection`
  shape. This distinction must be added (additively) for Prong 1 to work,
  without breaking the existing exported `resolveWorkbenchSelection` callers.
- `ws-dashboard/frontend/src/resourceModel.ts` — only 3 call sites of
  `resolveWorkbenchSelection` exist project-wide: `App.tsx:807` (feeds
  `workbenchSelection`/`selection` prop — IN SCOPE for stickiness),
  `App.tsx:1036` (the RU2 sync-mount hack — OUT OF SCOPE, leave non-sticky),
  and internally inside `deriveWorkbenchView` (`workbench/openRootLookup.ts:148`
  — IN SCOPE, must use the same stickiness so the two derivations cannot
  disagree, which is exactly the "two derivations, two data paths" class the
  sibling ticket's D2 already had to close once).
- `ws-dashboard/frontend/src/workbench/openRootLookup.ts#L130-164` —
  `deriveWorkbenchView(state)`. Takes `{resourcesByServer,
  lastNonNullResourcesByServer, selectedServerId, selectedId, openWorkRootKeys,
  openWorkRootRefs}`, internally recomputes `activeResources` via
  `resolveActiveResources` (`:143-147`) and `selection` via
  `resolveWorkbenchSelection` (`:148`), and returns `selectedRootKey`/
  `openInstanceKeys`/`effectiveActiveRootKey`. This is a PURE function (no
  ref writes) — it must receive the already-advanced sticky cache as an
  added committed-state field and call the sticky resolver internally
  (mirrors how it already receives `lastNonNullResourcesByServer` as an
  already-advanced value rather than advancing it itself).
- `ws-dashboard/frontend/src/App.tsx#L560-587` — where the D5 ref is owned
  and advanced today: `lastNonNullResourcesByServerRef` (`useRef`, `:560`) is
  written via `withLastNonNullResourcesByServer` (`:561-565`) BEFORE
  `activeResources` is read (`:566-570`) and BEFORE `deriveWorkbenchView` is
  called (`:580-587`, passing the just-advanced ref value at `:582`). The new
  sticky-selection cache must follow the identical shape: a new
  `useRef<LastMatchedSelectionByServer>({})` advanced once here (after
  `activeResources` resolves, since the sticky resolver needs the already
  D2-fallback-resolved tree), then both `workbenchSelection` (`App.tsx:806-809`)
  and `deriveWorkbenchView`'s call (`:580-587`, needs a new field added to its
  input object) must read the SAME already-advanced ref value — never
  recompute the cache twice per render, or the two derivations can diverge
  again (the exact bug class D2/D3 in the sibling ticket exist to prevent).
- `ws-dashboard/frontend/src/App.tsx#L806-809` — `workbenchSelection =
  useMemo(() => resolveWorkbenchSelection(activeResources, selectedId), [activeResources, selectedId])`,
  passed to `WorkbenchShell` as the `selection` prop (`App.tsx:1423`). This is
  the value that must become sticky; the existing `useMemo` should be
  replaced by directly consuming the sticky-resolver's result computed
  earlier (near `:560-587`), same non-memoized-every-render pattern already
  used for `activeResources` at `:566-570` (recomputing a pure function on
  every render is the established style here, not a correctness concern).
- `ws-dashboard/frontend/src/App.tsx#L3779-3787` — `selectedWorkRootStateKey`
  is derived from `selection.root...` — automatically inherits stickiness
  once `selection` (workbenchSelection) is sticky; no separate change needed
  here.
- `ws-dashboard/frontend/src/App.tsx#L5985` — `effectiveActiveRootKey =
  selectedWorkRootStateKey` — automatically inherits stickiness; no change
  needed here either (confirms the D3 "pure, ref-free" design is preserved —
  stickiness lives in the resolver, not as a new ref-based override at this
  line).
- `ws-dashboard/frontend/src/App.tsx#L4386-4424` — **RU1 evidence, confirmed
  real gap.** `openWorkRootInstances` resolves the SELECTED entry via
  `selection.root` (`:4388-4399`, inherits Prong 1's fix once `selection` is
  sticky) but every OTHER (keep-alive/background) member resolves via
  `findOpenWorkRoot(resourcesByServer[ref.serverRoute] ?? null, ref)`
  (`:4404-4407`) — a RAW lookup with **no fallback at all**, not even the
  existing D5 `lastNonNullResourcesByServer` cache that is already in scope
  one function up. Any keep-alive root that momentarily vanishes from
  `resourcesByServer[ref.serverRoute]` for one poll gets filtered out
  (`:4422-4424`) and its Dockview instance is dropped from
  `openWorkRootInstances` for that render — the same transient-omission
  mechanism as the reported bug, but for a background root instead of the
  selected one. This confirms RU1 is a live second unmount/remount source,
  not ruled out. `WorkbenchShell` does not currently receive
  `lastNonNullResourcesByServer` as a prop (confirmed absent from its props
  list, `App.tsx:3596-3673`), so the minimal fix is: thread
  `lastNonNullResourcesByServerRef.current` down as a new `WorkbenchShell`
  prop and change `:4405` to
  `resourcesByServer[ref.serverRoute] ?? lastNonNullResourcesByServer[ref.serverRoute] ?? null`
  — reusing the existing D5 cache, no new cache needed for this part.
- `ws-dashboard/frontend/src/App.tsx#L8104-8142` — `TerminalPaneBody({pane, actions})`,
  `const terminalId = pane.session.terminalId` (`:8142`). This
  component is mounted per terminal pane and stays mounted (with its wrapper
  `display:none`'d) while the OWNING ROOT is not the active root — it is
  NOT unmounted by a mere selection/visibility flip. It IS unmounted when the
  terminal is genuinely removed from the daemon-reported session list feeding
  `placeTerminalSessions`/`terminalPanes` (`App.tsx:7921-7966`, `:3687-3689`).
  This means **React's own mount lifetime of `TerminalPaneBody` already IS
  "logical terminal presence"** — no new boolean/flag needs to be invented;
  keying the socket-teardown effect's cleanup on component unmount (i.e. not
  re-running it on `paneVisible` changes) directly implements the ticket's
  "logical terminal presence" mechanism.
- `ws-dashboard/frontend/src/App.tsx#L8491-8617` — the single effect that
  currently conflates two concerns: (1) visibility bookkeeping
  (`onVisibilityGated` marking `:8492-8505`, corrective refit `:8519-8530`)
  and (2) WebSocket create/teardown (`:8531-8616`), all under deps
  `[terminalId, paneVisible]` (`:8617`). The early return at `:8492-8504`
  means NO socket exists at all while `paneVisible` is false, and the cleanup
  at `:8603-8616` closes any non-CONNECTING socket on every dep change,
  including a pure `paneVisible` flip.
- `ws-dashboard/frontend/src/terminals.ts#L611-618` — `shouldPollTerminalOutput`
  already requires `socketStatus !== "connecting" && socketStatus !== "connected"`
  before considering HTTP-poll fallback at all; `visibilityGated` is a
  secondary condition only relevant once the socket has actually gone to a
  non-connected status. Once Prong 2 stops closing the socket on a
  `paneVisible` flip, the socket stays `"connected"` while hidden, so
  `shouldPollTerminalOutput` already returns `false` via the socket-status
  clause regardless of `visibilityGated` — **no change needed to
  `onVisibilityGated`/`visibilityGated`/`shouldPollTerminalOutput`**; leave

- `ws-dashboard/frontend/src/workbench/deriveWorkbenchView.test.ts#L1-165` —

## Implementation Plan

1. **`resourceModel.ts`** — add match-detection without changing the public
   `resolveWorkbenchSelection` signature/behavior:
   - Extract the existing tree-walk into an internal helper that also
     returns whether `selectedId` was matched exactly (workspace id, root id,
     or nested instance) vs. fell through to `fallback`.
   - Keep `resolveWorkbenchSelection(resources, selectedId): WorkbenchSelection | null`
     exported exactly as today (thin wrapper over the helper), so
     `App.tsx:1036`'s out-of-scope call site is unaffected.
   - Add a new export, e.g. `resolveWorkbenchSelectionWithMatch(resources, selectedId): { selection: WorkbenchSelection | null; matched: boolean }`,
     for the two in-scope call sites.
2. **`resourceModel.ts`** — add the server-scoped sticky cache (D5 shape
   applied to selection), near `withLastNonNullResourcesByServer`/
   `resolveActiveResources` (`:236-261`):
   - New type, e.g. `LastMatchedSelectionByServer = Record<string, { selectedId: string; selection: WorkbenchSelection; bridged: boolean }>`.
   - New pure function `resolveStickyWorkbenchSelection(resources, selectedId, selectedServerId, lastMatchedSelectionByServer): { selection: WorkbenchSelection | null; nextLastMatchedSelectionByServer: LastMatchedSelectionByServer }`:
     - If `resources` is `null`, return `{ selection: null, nextLastMatchedSelectionByServer: lastMatchedSelectionByServer }` unchanged — this case is already fully owned by D5/D2 and must NOT be touched by the new cache (only bridge "tree present, entry missing", never "tree itself absent").
     - Call `resolveWorkbenchSelectionWithMatch(resources, selectedId)`.
     - If `matched` (and `selectedId` non-null): seed/refresh the cache entry
       for `selectedServerId` with `{selectedId, selection, bridged: false}`
       and return the fresh `selection`.
     - If not matched: look up `lastMatchedSelectionByServer[selectedServerId]`.
       - If it exists, `selectedId` matches, and `!bridged` — this is the
         first miss for this selection: return the CACHED `selection` (the
         bridge) and advance the cache entry's `bridged` to `true` (so a
         second consecutive miss does not bridge again).
       - If it exists, `selectedId` matches, and `bridged` is already `true`
         — this is the second consecutive miss: treat as genuine removal,
         drop the cache entry, and return the fresh (non-sticky) `selection`
         (the natural fallback).
       - Otherwise (no entry, or `selectedId` itself changed — a real user
         re-selection): return the fresh `selection` unchanged, cache
         unchanged.
   - Keep this fully pure — no `useRef`/`useState` inside `resourceModel.ts`.
3. **`workbench/openRootLookup.ts`** — update `deriveWorkbenchView`
   (`:130-164`):
   - Add `lastMatchedSelectionByServer: LastMatchedSelectionByServer` to its
     input `state` type.
   - Replace the internal `resolveWorkbenchSelection(activeResources, state.selectedId)`
     call (`:148`) with `resolveStickyWorkbenchSelection(activeResources, state.selectedId, state.selectedServerId, state.lastMatchedSelectionByServer).selection`
     (discard the returned `nextLastMatchedSelectionByServer` here — this
     function stays pure/non-advancing, matching how it already treats
     `lastNonNullResourcesByServer` as a read-only input).
4. **`App.tsx`** — wire the sticky cache at the single owning site
   (`:560-587`, alongside `lastNonNullResourcesByServerRef`):
   - Add `const lastMatchedSelectionByServerRef = useRef<LastMatchedSelectionByServer>({})`.
   - After `activeResources` resolves (`:566-570`), call
     `resolveStickyWorkbenchSelection(activeResources, selectedId, selectedServerId, lastMatchedSelectionByServerRef.current)`,
     store `.nextLastMatchedSelectionByServer` back into the ref, and keep
     `.selection` as the new `workbenchSelection` value.
   - Replace the `useMemo` at `:806-809` with this already-computed value
     (delete the now-redundant separate `resolveWorkbenchSelection` call
     there); confirm no other consumer of `workbenchSelection` between
     `:587` and `:806` needs the pre-sticky raw value instead (scan the
     gap once at implementation time — expected: none, since nothing else
     reads workbench selection in that range per this survey's read).
   - Pass `lastMatchedSelectionByServerRef.current` (the just-advanced value)
     into the `deriveWorkbenchView` call at `:580-587` as the new
     `lastMatchedSelectionByServer` field.
   - Leave `App.tsx:1036`'s `resolveWorkbenchSelection` call (the RU2
     sync-mount hack) untouched and non-sticky, per Out of Scope.
5. **RU1 fix** (`App.tsx:3596-3673` props, `:4400-4424` usage): thread
   `lastNonNullResourcesByServer: ResourcesByServer` as a new prop into
   `WorkbenchShell` (pass `lastNonNullResourcesByServerRef.current` from the
   call site), and change the keep-alive lookup at `:4404-4407` from
   `findOpenWorkRoot(resourcesByServer[ref.serverRoute] ?? null, ref)` to
   `findOpenWorkRoot(resourcesByServer[ref.serverRoute] ?? lastNonNullResourcesByServer[ref.serverRoute] ?? null, ref)`.
   Record the RU1 disposition ("confirmed live gap, fixed" — not "not
   implicated") in the Phase 2 Result.
6. **`App.tsx` Prong 2** — split the combined effect at `:8491-8617` into two:
   - Effect A (visibility bookkeeping only), deps `[paneVisible]`: keep the
     `onVisibilityGated` true/false calls (`:8492-8505`) and the corrective
     refit block (`:8519-8530`) reading `fitNowRef.current?.()`/
     `forwardSizeRef.current?.()`. No socket creation/teardown here.
   - Effect B (socket lifecycle), deps `[terminalId]` ONLY (drop
     `paneVisible` from this effect's deps): move the `new WebSocket(...)`
     construction and all its listeners (`:8531-8601`) and the cleanup
     (`:8603-8616`) here unchanged, EXCEPT remove the `if (!paneVisible) { ...; return; }`
     early return that currently gates socket creation on visibility
     (`:8492-8504` conceptually moves to Effect A; Effect B always connects
     once mounted, regardless of `paneVisible`).
   - Net effect: the socket connects once per `terminalId` (mount or a real
     terminal-id change) and is torn down only on a `terminalId` change or
     the component's genuine unmount (which — per the Codebase Findings
     above — only happens on actual terminal removal, i.e. "logical terminal
     presence" ending). A `paneVisible` flip (root deselected, or a
     different Dockview tab brought to front within the same root) no
     longer touches the socket at all. The existing CONNECTING-guard comment
     at `:8606-8614` becomes describing "component unmount mid-handshake",
     still correct and still needed (unmount can still race a CONNECTING
     socket).
   - Explicitly verify (per the ticket's "no naive OPEN guard" constraint) that
     the ONLY teardown path for an OPEN socket after this change is genuine
     `TerminalPaneBody` unmount or a `terminalId` change — i.e. there is no
     leaked-connection path, since unmount always runs the same cleanup that
     already correctly closes non-CONNECTING sockets.
7. Do not touch `onVisibilityGated`/`visibilityGated`/`shouldPollTerminalOutput`
   (`terminals.ts:558-618`) — confirmed no change needed (Codebase Findings).
