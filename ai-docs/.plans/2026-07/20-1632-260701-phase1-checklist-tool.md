# Plan: 260701-feat-write-ticket-lever-b-mcp-tools — Phase 1: Checklist-as-todo for On: Apply Ticket Content and On: Intent Review

## Relevant Ticket Contract
- Goal: new MCP tool `ws/tickets.checklist(type, phase: "content"|"intent")` returns each phase's item list as data.
- The playbook installs exactly **one** todo per phase (2 total) via `todo.append`; each todo's `Instruction` carries the full multi-item text for that phase (mirrors `enter.implement`'s per-step granularity, not per-checklist-item).
- The todo is checked only after the whole phase is satisfied, not per item.
- `On: Open Decision Queue` is explicitly out of scope — already gated by `judge: needs-open-decision-queue`.
- Once the tool exists and is wired in, the corresponding static prose for `On: Apply Ticket Content` and `On: Intent Review` becomes deletable from `agents-plugin/rsrc/lead-write-ticket/lead-write-ticket.md` (constraint: "each phase wires its new tool(s) into the playbook and deletes the superseded prose in the same file").
- Rejected alternative: one todo per checklist category — rejected as disproportionate ceremony.
- Verification (from ticket): exercise `lead-write-ticket` end to end on a real ticket edit; confirm both todos install, carry full checklist text, get checked only on phase completion; confirm deleted prose leaves no dangling references.
- Constraint: preserve doctrine text verbatim; do not touch it.
- Constraint: Phase 1 and Phase 2 are independent, no ordering dependency.
- Constraint: spec addressing for the new tool contract is deferred to promotion time (ticket stays `todo/`/`ready/` without a spec-address gate for this ticket itself) — no spec file to write in this phase.

## Out of Scope
- Phase 2 (`tickets.sage_gate` / `tickets.sage_record`, the ~235-line Sage Review block, the three Blocked Section Templates) — separate phase, no dependency.
- `On: Open Decision Queue` — already mechanically gated, explicitly excluded from this migration.
- The golden-reference "Judgment delegation" dedup items (e.g. collapsing the Capture category list stated in Invariants/Apply-Ticket-Content/Doctrine into one place) — these are epic-wide diet items from `ai-docs/.plans/2026-07/20-1610-write-ticket-diet-target.md`, not named by Phase 1's own text; leave Invariants/Capture prose untouched.
- A CLI mirror for `tickets.checklist` — no existing `tickets.template` CLI mirror exists either (confirmed absent from both `runtime.json` `commands` sections), and the ticket does not request one.
- Running `agents-plugin-tool/scripts/bump-ws-version.sh` — that is a separate dev-merge step per `AGENTS.md`; this phase only adds the new tool key to `runtime.json`, matching sibling entries' current version-range value.

## Codebase Findings
- `agents-plugin-tool/internal/wsdoc/tickets_template.go#L147-L163` — `TicketTemplate(typeStr string) (string, error)` is the closest existing precedent: a pure, root-free switch-on-category function returning canned markdown text, with a uniform "unknown type" error listing accepted values. `tickets.checklist(type, phase)` should follow the same shape (switch on `phase`, then `type` where content differs), living in a new sibling file e.g. `agents-plugin-tool/internal/wsdoc/tickets_checklist.go`.
- `agents-plugin-tool/internal/mcp/server.go#L1186-L1189` — dispatch case for `tickets.template` is trivial: parses `type` from arguments, calls the wsdoc function, returns via `toolTextResponse`. No `resolveToolRoot`/`session_key` involved. `tickets.checklist`'s dispatch case should be added directly after it (~L1189) following the identical pattern but parsing both `type` and `phase`.
- `agents-plugin-tool/internal/mcp/server.go#L3621-L3630` — `tickets.template`'s `tools()` schema entry (name/description/inputSchema with a `type` string property, required). Add the new `tickets.checklist` schema entry immediately after this block, with `type` and `phase` (enum `content`/`intent`) properties, both required.
- **Risk signal — "root-aware" framing mismatch**: the task authority describes `tickets.checklist` as "a new root-aware `tickets.*` MCP tool," but `tickets.template` — the one existing `tickets.*` tool with an identical pure-lookup-by-category shape — is explicitly NOT root-aware (no `session_key`, no `resolveToolRoot`, not gated by `isLeadOnlyTool` or `noAgentHiddenTool`; confirmed absent from both gate functions at `server.go#L66` and `server.go#L4107`). `tickets.checklist(type, phase)` needs no ticket-file or repo-root access — it is a static data lookup exactly like `TicketTemplate`. Recommendation: follow the `tickets.template` precedent (no `session_key`/root) rather than the "root-aware" framing; flagged in report below rather than silently overridden.
- `agents-plugin-tool/internal/mcp/tickets_template_test.go` (whole file) — test pattern precedent: call the wsdoc function directly for each accepted `(type[, phase])` combination, assert non-empty text and expected substrings, assert the unknown-type error message shape. `tickets.checklist` tests should mirror this: one test per `(type, phase)` combination checking for expected checklist substrings (e.g. "Open Decision Queue" appears in `phase:"content"` item 2; "fresh implementer" test text appears in `phase:"intent"`; epic/workset-specific branch text in `phase:"intent"` for those categories only).
- `agents-plugin/rsrc/lead-write-ticket/lead-write-ticket.md#L83-L106` — the two prose blocks to source the checklist text from and then delete: `## On: Apply Ticket Content` (2 items) and `## On: Intent Review` (7 items, including the category-conditional item 5 for `epic`/`workset`). These bullets are the literal content the Go function must reproduce as returned text (the ticket requires the checklist item content, including the generative "fresh implementer" test, to travel verbatim into the todo `Instruction`).
