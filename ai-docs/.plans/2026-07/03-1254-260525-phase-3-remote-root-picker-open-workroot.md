# Plan: 260525-feat-ws-dashboard-server-scoped-operation-forwarding — Phase 3: Remote root picker and open WorkRoot

## Relevant Ticket Contract
- Phase 3 goal: make the server row folder/open-root affordance available for connected linked servers; opening it launches a root picker scoped to that server that can list, navigate, create directories, pin/unpin, and submit `open workRoot`, forwarding through the local gateway for linked servers.
- Opening a remote WorkRoot must return a resources view rewritten to the linked Server Route and refresh/select that linked server **without mutating local host registry state**. Server-local behavior must remain unchanged.
- Decisions/Constraints that bind this phase: root-picker/open paths are remote host paths when `serverRoute != server-local`, so UI labels/placeholders must make the selected-server context explicit; UI must keep the selected Server Route visible enough that remote vs local is not confused; browser must never call the linked endpoint directly (all traffic through local gateway); no ad-hoc URL construction in components — use the Phase 1 helpers.
- Implementation Strategy: reuse phase-7 draft source commits `4614200a`, `1bbf4fe3`, `294f7c1b`, `e760ecf8` via cherry-pick rather than reimplementing; apply the `serverId`->`serverRoute` rename and dot-free validation **within** this phase's own diff so the landed diff is Decisions-compliant.
- Deferred scope (out of this phase): credential persistence, remote deployment, public endpoint hardening.

## Out of Scope
- Backend forwarding for root-picker / directories / pins / open-work-root / activation: **already landed in Phase 2** (`ac4f4556`, Result `cd1f2b56`). Routes exist at `ws-dashboard/crates/daemon/src/router.rs#L98-L110` (`server_scoped_root_picker`, `server_scoped_root_picker_pins`, `server_scoped_open_work_root`) with in-process `server-local` dispatch, allowlisted forwarding, resource-view rewriting, and bounded gateway errors. Do NOT reimplement backend forwarding for these routes.
- SSE/document events, files, Activity, Git, terminals (Phases 4-7).
- Phase 1 frontend helpers and identity scoping — already landed; this phase only calls them.

## Codebase Findings
- `ws-dashboard/frontend/src/App.tsx#L1192-L1247` — current `OpenWorkRootControl` takes **no** `server` prop and calls `fetchRootPicker(path)` / `requestOpenWorkRoot(requestedPath)` / `createRootPickerDirectory` / `pinRootPickerDirectory` / `unpinRootPickerDirectory` with **no** `serverRoute` argument (lines 1228, 1338, 1371, 1409, 1429). This is the core gap: for a linked server the picker currently hits local routes. Wiring is genuinely missing.
- `ws-dashboard/frontend/src/App.tsx#L2588-L2596` — the `<OpenWorkRootControl variant="icon" .../>` call site inside `ServerRows` has `server` in scope (used at L2582 for `ServerActionButton`) but does not pass it down. Draft adds `server={server}` here.
- `ws-dashboard/frontend/src/App.tsx#L456-L476` — `handleWorkRootOpened` (the `onOpened` handler) already selects `openedView.server.id`, applies the rewritten resource view via `applyExternalResources`, and re-fetches; it does not touch the linked-server registry. So the "refresh/select linked server without mutating registry" behavior is **already generic** — it selects whatever Server Route the gateway returns. No change needed here beyond ensuring the open call carries `serverRoute`.
- `ws-dashboard/frontend/src/rootPicker.ts#L52-L142` and `openWorkRoot.ts#L11-L46` — all helpers (`fetchRootPicker`, `requestOpenWorkRoot`, `createRootPickerDirectory`, `pin/unpinRootPickerDirectory`) already accept an optional `serverRoute?: string | null` and build `localCompatibleDashboardApiRoute` URLs. `requestOpenWorkRoot` returns `{ view, openedWorkRootId }`. Ready to use as-is.
- `ws-dashboard/frontend/src/resourceModel.ts#L20-L85` — identity helpers exist under Phase-1 names: `LOCAL_DASHBOARD_SERVER_ROUTE` (`"server-local"`), `dashboardServerRoute(...)`, `isLocalDashboardServerRoute(...)`. The draft commits use the pre-rename `dashboardServerId` / `isLocalDashboardServerId` and a `pickerServerId` local — these MUST be applied as `dashboardServerRoute` / `isLocalDashboardServerRoute` / `pickerServerRoute` during cherry-pick (server row `server.id` is the wire field that carries the Server Route, so `dashboardServerRoute(server?.id)` is correct).
- Draft commit `4614200a` (App.tsx +48) — adds the `server` prop, derives `pickerServer*` context, resets picker session state on server-context change (`useEffect` keyed on the picker server), threads the route through all five helper calls, and updates button title / summary / dialog heading / current-path placeholder to name the selected-server context ("this host" vs the server label). This directly satisfies the "labels/placeholders must make remote-vs-local explicit" constraint.
- Draft commits `1bbf4fe3`, `294f7c1b`, `e760ecf8` (App.tsx +16/+25/+3) — add a **stale-response guard**: a request sequence + open-ref so a late picker fetch response after close, server-context reset, or successful open cannot repopulate hidden picker state. This is a real race in the current single-picker-per-row model made worse by switching picker servers; recommend including it. Bulk of these commits' line count is `e2e/dashboard-acceptance.spec.ts` and `commands.test.ts` coverage.
- `ws-dashboard/crates/daemon/src/router.rs#L98-L110` — confirms backend Phase 3 routes already registered (see Out of Scope).
- Risk signal (low): draft base was App.tsx `989979bf` (pre-Phase-1). Current App.tsx is post-Phase-1/2 rename, so a raw `git cherry-pick` of these four commits WILL conflict. This is expected per the ticket's Implementation Strategy; resolve by porting the logic and applying the `serverRoute` rename inline, not by dropping either side. Not a research-level uncertainty.

3. Port `1bbf4fe3` command-payload change: thread the selected picker server route into the root-picker/open command builders (`onCommand` payloads) so logical command identity carries server route while host paths stay in request bodies only. Apply rename to `commands.test.ts` additions.

5. Port the accompanying test additions: `rootPicker.test.ts`, `openWorkRoot.test.ts`, `commands.test.ts`, and `e2e/dashboard-acceptance.spec.ts`, applying the `serverId`->`serverRoute` rename to assertions and asserting linked-server calls stay on `/api/dashboard/servers/{serverRoute}/...`.
