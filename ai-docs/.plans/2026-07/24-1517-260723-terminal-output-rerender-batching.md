# Plan: 260723-bug-dashboard-terminal-frontend-output-oN-rerender — Phase 1: batch output-cursor writes and stop the revalidation effect from keying on per-chunk cursor churn

## Relevant Ticket Contract

- Change 1: stop calling `setTerminalPanes` synchronously per `"output"` message in `applyTerminalSocketMessage`'s output branch (`App.tsx:5512-5524`). Instead accumulate pending `(logicalKey -> chunkSequence)` advances in a `ref` (`Map<string, number>`) and flush all pending entries into a single `setTerminalPanes` call (applying `markTerminalOutputCursor` per pending logicalKey) on the next `requestAnimationFrame`.
- `markTerminalOutputCursor` (`terminals.ts:577-584`) itself must not change; only its call site/cadence changes.
- **Correctness requirement (must ship in this phase, not deferred):** the pending Map must be flushed synchronously (apply via the same updater immediately + `cancelAnimationFrame` the scheduled frame), at minimum:
  - before the debounced visual-capture callback (`terminalPaneBody.tsx:703-707`) reads `liveRef.current.pane.nextSequence`, OR have that read consult the pending Map directly instead;
  - on any non-`"output"` socket message for that pane (`App.tsx:5526-5537`, the status/exit branch via `appendTerminalWebSocketMessage`);
  - on pane unmount / `closeTerminalPane` (`App.tsx:5608-5628`).
- Change 2: stop the `App.tsx:3881-4063` revalidation effect from re-running on cursor-only `terminalPanes`/`agentChatPanes` changes, via two memo layers:
  - a cheap per-render string "pane identity signature" built from sorted `{paneId, workRootId, serverRoute}` triples (change-detector only);
  - a `useMemo`-computed STRUCTURED array of `{paneId, workRootId, serverRoute}`, keyed on that signature string.
  - The effect's dependency array (currently `terminalPanes`/`agentChatPanes` at `App.tsx:4050`/`4054`) must depend on the STRUCTURED memoized arrays, not the bare signature string. `liveTerminalPaneIds`/`liveAgentChatPaneIds` (`App.tsx:3897-3905`, `3921-3929`) must be built from those structured arrays.
- Out-of-scope note carried forward as a non-goal: `App.tsx:4833-4848`'s `livePollPanesRef` scan is explicitly left unchanged this phase (lag-by-one-frame is acceptable, deduped by `Math.max` merge in `appendTerminalWebSocketMessage`).
- Verification boundary (from ticket): a unit test in `terminals.test.ts` for the batching helper (N pending advances, duplicates/out-of-order → one patch, max-sequence-per-key); a close-mid-burst regression test (pending advance flushed synchronously before the close/exit is processed); an rAF-lifecycle test (frame cancelled on unmount/close, no flush against a torn-down pane); a manual/e2e perf check that the revalidation effect fires at most once per frame and does not scale with idle roots/terminals.
- Spec impact: none — internal render-performance change only; no change to terminal output delivery/cursor/replay wire contract (`ai-docs/spec/ws-web-dashboard/index.md` §260516-ws-web-dashboard-terminal-registry-pty-spawn unaffected).

## Implementation Plan

1. In `App.tsx`, near the `terminalPanes` state (`App.tsx:3607-3609`), add two refs: `pendingOutputCursorRef = useRef<Map<string, number>>(new Map())` and `pendingOutputCursorFrameRef = useRef<number | null>(null)`. On accumulate, store `Math.max(existing ?? -1, chunkSequence)` per logicalKey (not overwrite) so out-of-order/duplicate chunks within one frame still converge to the max.
2. Extract a pure helper into `terminals.ts` (alongside `markTerminalOutputCursor`, e.g. `flushPendingOutputCursors(panes: Record<string, TerminalPaneState>, pending: Map<string, number>): Record<string, TerminalPaneState>`) that applies `markTerminalOutputCursor` for every pending `(logicalKey, chunkSequence)` pair against `panes`, guarding missing keys the same way the existing `setTerminalPanes` call sites do (`current[pane.logicalKey] ? ... : current`), and returning the same object reference if nothing actually advanced (mirroring `markTerminalOutputCursor`'s own no-op contract) so an all-no-op flush does not force an extra render.
3. In `App.tsx`'s `applyTerminalSocketMessage` output branch (`App.tsx:5512-5524`), replace the direct `setTerminalPanes` call with: write into `pendingOutputCursorRef.current`, and if no frame is scheduled, schedule one (`requestAnimationFrame`) that calls a shared `flushPendingOutputCursors()` closure (`setTerminalPanes((current) => flushPendingOutputCursors(current, pendingOutputCursorRef.current))`, then clear the Map and the scheduled-frame ref).
4. Define that shared flush closure once (function declaration in the component body, referencing the refs) so it can be called both from the rAF callback and from the synchronous flush points below; the synchronous path must also `cancelAnimationFrame(pendingOutputCursorFrameRef.current)` and null it out, so a stale scheduled frame never re-flushes an already-cleared Map.
5. Wire the synchronous-flush call sites:
   - In the non-`"output"` branch of `applyTerminalSocketMessage` (`App.tsx:5526-5537`), call the synchronous flush before/alongside the existing `setTerminalPanes(appendTerminalWebSocketMessage(...))` call for that pane's logicalKey (flushing the whole pending Map is acceptable per the ticket's "flush the pending Map" wording — do not scope it down to a single key).
   - In `closeTerminalPane` (`App.tsx:5608-5628`), call the synchronous flush at the top of the function, before `closeTerminal(...)` is invoked.
6. Resolve the visual-capture read (`terminalPaneBody.tsx:692-707`): prefer exposing the pending cursor value through `TerminalPaneActions` (`terminalPaneBody.tsx:23-63`) — add a function such as `getPendingNextSequence: (pane: TerminalPaneState) => number` (App.tsx implementation reads `Math.max(pane.nextSequence, (pendingOutputCursorRef.current.get(pane.logicalKey) ?? -1) + 1)`), have the sole construction site (`App.tsx:4208-4235`) supply it, and change `terminalPaneBody.tsx:706` to use `liveRef.current.actions.getPendingNextSequence(liveRef.current.pane)` instead of the bare `liveRef.current.pane.nextSequence`. This avoids relying on a same-tick flush-then-read ordering across the App/child boundary. No changes are needed in `workbench/editorGroups.ts` or `workbench/terminalWorkbenchPane.tsx` (pure pass-through of `TerminalPaneActions`).
7. Add pane-unmount cleanup: ensure whatever effect owns the socket lifecycle for a pane (or the `closeTerminalPane` path from step 5) also flushes/clears any pending entry for that pane's logicalKey so an unmounted pane's stale pending advance cannot leak into a later flush against a re-created pane sharing the same key; also cancel the scheduled rAF on `App`'s own unmount (top-level cleanup effect) as a defensive backstop.
8. In `App.tsx`, build the per-render "pane identity signature" string from sorted `{paneId, workRootId, serverRoute}` triples for both `terminalPanes` and `agentChatPanes` (or one combined signature covering both, matching how the effect already merges them) — a plain string computed every render, not memoized itself.
9. Add a `useMemo` producing the STRUCTURED array of `{paneId, workRootId, serverRoute}` per pane, keyed on the signature string from step 8, replacing the raw `terminalPanes`/`agentChatPanes` reads used to build `liveTerminalPaneIds`/`liveAgentChatPaneIds` inside the effect body (`App.tsx:3897-3905`, `3921-3929`).
10. Replace `terminalPanes` (dep array `App.tsx:4050`) and `agentChatPanes` (`App.tsx:4054`) with the two structured memoized arrays from step 9 in the effect's dependency array (`App.tsx:4049-4063`); leave every other dependency in that array untouched.
11. Do not touch `App.tsx:4833-4848` (`livePollPanesRef`) — explicitly out of scope.
