# Plan: 260725-feat-dashboard-pty-agent-attention-notification — Phase 4: token store and the callback endpoint

## Relevant Ticket Contract

- Daemon-owned token store at `terminal-tokens/<terminal_id>.json`; `boot_reconcile` must repopulate the in-memory token -> terminal lookup BEFORE serving; `TerminalSession` construction currently has no auth-material slot.
- The route pair from `## Decisions`: a SINGLE local route, `POST /api/dashboard/terminals/{terminal_id}/turn-state`, body `{ "token": "<opaque>", "state": "working|ready|idle" }`, token checked in the handler, route registered OUTSIDE `require_owner_auth`. Deliberately NOT paired with a server-scoped sibling (an agent always posts to the daemon that spawned it).
- GC sweep over `agent-profiles/` reclaiming directories with no live terminal record; keys off TERMINAL liveness (a config may legitimately outlive an agent that exited inside a surviving terminal). ORDERING is load-bearing: sweep strictly AFTER `boot_reconcile` completes, trigger is boot-after-reconcile plus a periodic tick.
- Verification, ALL with owner auth ENABLED: valid token accepted; wrong/absent token rejected; token for terminal A cannot post for terminal B; orphaned profile directory reclaimed; sweep does not touch a directory belonging to a helper adopted by `boot_reconcile`.
- Restart verification must cover the URL, not just the token: after a daemon restart on a DIFFERENT port with a live helper still running, a callback from that helper must still arrive.
- On-disk layout, all `0600`: `terminal-tokens/<terminal_id>.json` (token store), `agent-profiles/<terminal_id>/settings.json` (vendor config, no secret), `agent-profiles/<terminal_id>/callback.json` (`{baseUrl, terminalId, token}`, kept separate from vendor config).
- The token never touches helper argv or `TerminalRegistryEntry` (no registry schema change; helper argv is `ps`-visible).
- Callback URL cannot be baked at spawn time (`--port` defaults to `0`); base URL must be resolvable at hook-fire time via the daemon's own rewrite of `callback.json`, not a well-known shared file.
- Identity privacy: the callback token is a new daemon-private credential class, distinct from `wsSessionKey`.
- Owns the `#260515-ws-web-daemon-foundation` spec amendment (the "pairing route is the only unauthenticated browser entrypoint" sentence, `ai-docs/spec/ws-web-dashboard/index.md:38-39`, anchor `{#260516-ws-web-dashboard-token-free-pairing-landing}`) and the matching in-source CONTRACT comment at `router.rs:97-98`.

## Out of Scope

- Phase 5 (the `tokio::sync::broadcast` SSE hub, server-scoped stream, snapshot-on-connect) and all later phases (6-8). Phase 4's callback handler validates and accepts a turn-state POST but does NOT persist or broadcast the state value anywhere durable/observable — there is nothing yet to hand it to. This is a deliberate phase boundary, not an oversight: none of Phase 4's own verification bullets (valid/wrong/absent token, cross-terminal, GC sweep, restart survival) require the state value to have any downstream effect.
- Any `TerminalRegistryEntry` schema change (hard constraint; confirmed empty diff required, same discipline as Phases 1-3).
- Removing `terminal-notify`'s silent-exit-0 design (`260726-bug-dashboard-terminal-notify-silent-failure-no-expiry` owns that separately).
- Token rotation during a terminal's lifetime. One token, generated once at fresh spawn, valid until the terminal closes; never regenerated on adoption (see Design Answer 1).
- Windows ACL hardening for the new `0600`-on-Unix files. Out of scope per repo precedent (`terminal_registry_file.rs`, `agent_callback.rs`, `agent_hook_config.rs` are all `#[cfg(unix)]`-gated for mode bits, with no Windows ACL equivalent anywhere in this codebase); record as a residual, pre-existing-shape risk in the Result, not something to newly invent here.
- A Codex profile, model selection exposure, MCP injection, Web Push, or a distinct `SurfaceKind` for agent terminals — all already out of scope at the ticket level.

## Codebase Findings

### Auth boundary (the riskiest edit)
- `router.rs:96-104` — `build_router`'s CONTRACT comment currently says only "`/pair` and daemon-to-daemon link auth stay outside the protected browser router." Must be amended to name a third class: token-authed, non-browser, per-terminal.
- `router.rs:466-469` — the exact insertion point: `Router::new().route("/pair", get(pair)).route("/api/dashboard/link-auth", post(remote_link_auth)).merge(protected)`. Add `.route("/api/dashboard/terminals/{terminal_id}/turn-state", post(post_terminal_turn_state))` to this SAME outer chain, before `.merge(protected)` — this is what puts it outside `require_owner_auth` structurally, not via a runtime flag.
- `router.rs:473-482` (`pair`) and the servers-module `remote_link_auth` are the existing precedent for a handler taking `State<AppState>` while living outside `protected` — the new handler follows the identical shape.
- `ai-docs/spec/ws-web-dashboard/index.md:38-39` (anchor `{#260516-ws-web-dashboard-token-free-pairing-landing}`) — "The pairing route is the only unauthenticated browser entrypoint." Must be tiered to name the callback route as a second, non-browser class.

### Where the base URL already lives in memory (constraint 3)
- `server.rs:69-70` — `bound_addr` is computed from `listener.local_addr()` and `base_url = format!("http://{}", display_addr(bound_addr))` is already constructed at `server.rs:80`, BEFORE `boot_reconcile` runs at `server.rs:113-118`. Phase 4 must thread this SAME string into `TerminalRegistry::boot_reconcile`/`TerminalRegistry::new` rather than reading `bound-base-url.json` back.
- `agent_callback.rs:88-100` (module CONTRACT on `write_bound_base_url`) explicitly warns Phase 4 against deriving `callback.json`'s `baseUrl` from this shared file — quoted directly: "if Phase 4 derives a per-terminal `callback.json`'s `baseUrl` by READING this file instead of from the `bound_addr` the daemon already holds in memory at bind time, the rejected multi-daemon steal is reintroduced."
- `server.rs:108-118` — `TerminalRegistry::boot_reconcile(...).await` is a single straight-line statement that fully resolves before `build_router`/`axum::serve` is ever reached later in the same function. This is the existing structural guarantee Phase 4 rides for token-lookup-before-serving; no new wiring is needed for that specific ordering (only for the GC sweep, which is a *new* task spawned after this line — see below).

### `TerminalRegistry`/`TerminalSession` construction (no auth-material slot yet)
- `terminal.rs:152-157` — `TerminalRegistry` struct: `sessions`, `helper_binary`, `registry_dir`, `connect_timeout`. No `state_dir`, no `base_url`, no token map.
- `terminal.rs:179-187` (`new`) / `terminal.rs:196-219` (`boot_reconcile`) — both constructor paths need new parameters: `state_dir: Option<PathBuf>` (mirrors the existing `persistent_state::default_state_dir()` degrade-gracefully branch already used at `terminal.rs:1055-1091`) and `base_url: String`.
- `terminal.rs:221-290` (`reconcile_entry`) — the adopt arm (`AdoptLive | AdoptGrace`, line 242) calls `TerminalSession::from_connection` with `profile_id: None` (line 273) and a CONTRACT comment documenting that profile provenance is PERMANENTLY lost on restart because nothing re-announces it. Phase 4 must NOT repeat this pattern for the token: unlike profile_id, the token is recoverable — read it back from `terminal-tokens/<terminal_id>.json` inside this same arm, and pass it into `from_connection`. If `agent-profiles/<terminal_id>/callback.json` exists on disk for this id, also rewrite it with the fresh `base_url` (token unchanged) — this existence check is what naturally skips plain shell terminals, which never had a profile dir.
- `terminal.rs:449-465` (`TerminalSession` struct) — `profile_id: Option<String>` (line 459) is the exact precedent shape to mirror for a new `callback_token: Option<String>` field: provenance-like, not persisted to `TerminalRegistryEntry`.
- `terminal.rs:1013-1160` (`TerminalSession::spawn`) — the `hook_config` branch at `terminal.rs:1044-1092` is the ONLY place a `callback_path`/`materialize_hook_config` call currently exists; token generation, the token-store write, and the per-terminal `callback.json` write (with `terminalId`/`token` populated) belong in this SAME branch, right before `materialize_hook_config` is called, so a plain-shell spawn (`hook_config: None`) is untouched by construction — same "no branch taken" discipline as `resolve_create_command`'s absent-profile path (`terminal.rs:996-997`).
- `terminal.rs:310-333` (`insert`/`insert_unchecked`) and `terminal.rs:335-368` (`remove`/`remove_for_work_roots`) — the four existing choke points where sessions enter/leave `self.sessions`. The new `tokens: HashMap<String, String>` map (terminal_id -> token) must be mutated at these SAME four points (insert on `insert`/`insert_unchecked`, using `session.callback_token`; delete on `remove`/`remove_for_work_roots`, also best-effort deleting the on-disk `terminal-tokens/<id>.json`), keeping both maps in lockstep without adding new call sites.
- `terminal.rs:836-851` (`close_terminal`) is the one HTTP handler that reaches `remove`; no change needed there beyond what `remove` itself does.

### Existing atomic-write / 0600 precedents to reuse, and the one to deliberately diverge from
- `agent_callback.rs:101-139` (`write_bound_base_url`) and `agent_hook_config.rs:32-82` (`materialize_hook_config`) both create the temp file at umask-default mode and chmod to `0600` only AFTER `fs::write` — both files carry an explicit forward-note CONTRACT flagging this as a brief world-readable window that is "harmless" for their own secret-free content but "load-bearing" the moment a real credential uses the same sequence. Phase 4's token-store writer and per-terminal `callback.json` writer must NOT copy this sequence; create at the restrictive mode directly (`OpenOptions::new().mode(0o600)` on Unix) rather than chmod-after.
- `terminal_registry_file.rs:42-55` (`write_registry_entry`) is the atomic temp-rename shape (still chmod-after, same as the two above) — reuse the atomic-rename mechanics, not the chmod-after ordering, for the new credential-bearing writer.
- `agent_callback.rs:146-154` (`unique_temp_path`) is the per-writer-unique temp-name pattern needed if a single well-known path could be written by two daemons; NOT needed for `terminal-tokens/<terminal_id>.json` or per-terminal `callback.json`, since both paths are already namespaced by a fresh random `terminal_id` (mirrors `agent_hook_config.rs:59-65`'s own reasoning for why `settings.json.tmp` needs no such suffix).
- `agent_callback.rs:24-32` (`CallbackTarget`) already reserves `terminal_id: Option<String>` and `token: Option<String>` fields — Phase 4 populates these for real for the first time; no shape change needed, just a new writer that fills them.

### Terminal id / token generation precedent
- `terminal.rs:2478-2485` (`opaque_terminal_id`) is the existing `thread_rng()` + `Alphanumeric` pattern (18 chars, `term_` prefix) already imported at `terminal.rs:14-15` (`rand::distributions::Alphanumeric`, `rand::{thread_rng, Rng}`). The new token generator reuses the same crate/import, just a longer output (see Design Answer 1) and no prefix (it is never displayed or logged, unlike the terminal id).

### GC sweep — no existing sweep or periodic-tick task to reuse
- `terminal_registry_file.rs:68-71` (`delete_registry_entry`) is per-entry only, invoked from `reconcile_entry`'s `KillVerified`/drop rows (`terminal.rs:277-289`) — confirmed no directory-sweep exists anywhere in this crate today (`grep` for `read_dir` under `agent-profiles` finds only the Phase-3 write path, never a scan).
- `grep -rn "tokio::time::interval"` across `crates/daemon/src/*.rs` returns nothing — there is no existing periodic-background-task precedent in this codebase; the sweep's `interval.tick()` loop is a net-new pattern, not a reuse of an existing one. Flag as new but low-risk: the loop body is a single bounded `fs::read_dir` pass, no recursion, no unbounded work per tick.
- `agent-profiles/<terminal_id>/` directory count is implicitly bounded by `MAX_TERMINAL_SESSIONS = 16` (`terminal.rs:32`) live sessions at any time, plus whatever has accumulated since the last successful sweep — never unbounded within a single tick's scan.

### Restart-survival test harness to reuse
- `crates/daemon/tests/terminal_lifetime.rs:93-148` (`DaemonProcess`, `spawn_real_daemon`) is the existing two-real-OS-process restart pattern: spawns `ws-dashboard serve --port 0` (fresh ephemeral port every time), scrapes its startup URL from stderr, hard-`SIGKILL`s the first daemon, and a second daemon binds to the SAME `WS_DASHBOARD_STATE_HOME`. This is the exact shape Phase 4's restart-survival test needs, with two adjustments: (a) it currently passes `--no-auth`; Phase 4's own verification bullet requires owner auth ENABLED, so a new test (or a parameterized variant) must scrape the `owner pairing URL: ...` line (same regex `frontend/e2e/daemonHarness.ts:257` uses: `/owner pairing URL:\s*(\S+)\r?\n/`) and hit `/pair?token=...` to get a session cookie before creating a terminal; (b) it must create the terminal with `profile_id: "claude"` (has `hook_config`, so `callback.json`/token get materialized) rather than a bare shell — Phase 2's own finding 3 (ticket Phase 2 Result) already proved the daemon returns its HTTP response before the helper attempts to spawn the resolved command, so using the unavailable `claude` binary here costs nothing and keeps the test free of a real vendor-binary dependency, exactly like `agent-spawn-profile.spec.ts` already relies on.
- `frontend/e2e/daemonHarness.ts:257` — the pairing-URL scrape regex to mirror in the new Rust test (same startup-output contract, `server.rs:86`: `eprintln!("ws-dashboard owner pairing URL: {}", info.pairing_url)`).
- `frontend/e2e/dashboard-acceptance.spec.ts:167-171` sets `process.env.WS_DASHBOARD_STATE_HOME` before the harness spawns its daemon child, confirming a Playwright spec can also read daemon-private files under that same state home directly from Node if a browser-level test needs to inspect (not merely exercise) the GC sweep or token store — useful for the orphan-reclaim and sweep-skips-adopted verification bullets if done at the Playwright layer instead of purely in Rust.

### Response shape precedent for the new handler
- `terminal.rs:1638-1648` (`terminal_error`, `terminal_access_error`) and the handler bodies at `terminal.rs:736-851` (`terminal_output`, `terminal_input`, `terminal_resize`, `terminal_websocket`, `close_terminal`) are the exact "look up session, `terminal_error(StatusCode::X, "message")` on failure" shape to reuse for the new callback handler — including reusing `terminal_error(StatusCode::UNAUTHORIZED, "unauthorized")` verbatim for both "unknown terminal_id" and "wrong token" (see Design Answer 3).

## Implementation Plan

1. **`agent_token_store.rs` (new module)** — mirrors `agent_callback.rs`'s I/O shape but writes at `0600` from creation (no chmod-after): `token_store_path(state_dir, terminal_id) -> PathBuf` (`state_dir.join("terminal-tokens").join(format!("{terminal_id}.json"))`), `write_token(state_dir, terminal_id, token) -> io::Result<()>` (atomic temp-rename, `OpenOptions::new().mode(0o600)` on Unix for the temp file directly), `read_token(state_dir, terminal_id) -> Option<String>` (tolerant: missing/malformed file returns `None`, logged, never panics — mirrors `terminal_registry_file::scan_registry_dir`'s tolerance), `delete_token(state_dir, terminal_id)` (best-effort `fs::remove_file`, mirrors `delete_registry_entry`).
2. **`agent_callback.rs` — new per-terminal writer.** Add `write_callback_target(profile_dir: &Path, base_url: &str, terminal_id: &str, token: &str) -> io::Result<()>`, same atomic-rename shape as `write_bound_base_url` but creating the temp file already at `0600` (no chmod-after window) since this file now carries a real credential. Do not change `CallbackTarget`'s shape (`terminal_id`/`token` are already `Option` fields, reserved since Phase 3) or `write_bound_base_url`/`resolve_callback_target` (both stay exactly as-is; `resolve_callback_target`'s no-caching CONTRACT is unaffected).
3. **Constant-time compare + turn-state parsing (new small pure module, e.g. `agent_turn_state.rs`)** — a `TurnState` enum (`Working`/`Ready`/`Idle`) with `#[derive(Deserialize)]`/`#[serde(rename_all = "lowercase")]` for the POST body's `state` field (independent of `cli::TurnStateArg`, which is clap-only and has no `Deserialize`), plus a `tokens_match(a: &str, b: &str) -> bool` constant-time byte comparison (XOR-accumulate over bytes, padded/short-circuited only on LENGTH not content, so timing does not leak a partial match — no new crate dependency needed for a comparison this small).
4. **`TerminalRegistry` widening (`terminal.rs:152-219`)** — add `tokens: Arc<RwLock<HashMap<String, String>>>` (terminal_id -> token), `state_dir: Option<PathBuf>`, `base_url: String` fields. Thread `state_dir`/`base_url` through `new`/`boot_reconcile`/`Default` (source from `persistent_state::default_state_dir()` and the same `bound_addr`-derived string `server.rs:80` already builds — pass it down instead of recomputing). Update every existing test call site in `terminal.rs`'s `#[cfg(test)]` module and `crates/daemon/tests/routes.rs` that constructs a `TerminalRegistry` directly (mechanical, same shape as Phase 2's `TerminalSession::spawn` arg-list widening).
5. **`TerminalSession` gets `callback_token: Option<String>` (`terminal.rs:449-465`)** — mirrors `profile_id`'s exact shape. Threaded through `from_connection` (`terminal.rs:1162-1197`) and `spawn` (`terminal.rs:1013-1160`).
6. **Fresh-spawn token generation (`terminal.rs:1044-1092`, inside the existing `hook_config` branch)** — right before calling `materialize_hook_config`: generate a token (`thread_rng()` + `Alphanumeric`, see Design Answer 1 for length), call `agent_token_store::write_token`, call the new `agent_callback::write_callback_target` (using the registry's threaded-in `base_url`, not a re-read of `bound-base-url.json`), then proceed to materialize the vendor `settings.json` unchanged. Pass the generated token into `from_connection` as `callback_token`.
7. **`insert`/`insert_unchecked`/`remove`/`remove_for_work_roots` (`terminal.rs:310-368`)** — on insert, if `session.callback_token` is `Some`, insert into `self.tokens`; on remove, delete the matching `self.tokens` entry AND best-effort `agent_token_store::delete_token` on disk (only meaningful when `state_dir` is `Some` and a token existed).
8. **`reconcile_entry`'s adopt arm (`terminal.rs:221-290`)** — for `AdoptLive`/`AdoptGrace`: check whether `agent-profiles/<entry.terminal_id>/callback.json` exists under the registry's `state_dir`; if yes, read the token via `agent_token_store::read_token`, rewrite `callback.json` via `write_callback_target` with the FRESH `base_url` (token unchanged), and pass the recovered token into `from_connection`'s new `callback_token` parameter; if no (plain shell terminal, or state_dir unresolved), pass `None` — unlike `profile_id`, this is NOT a permanent loss, and the CONTRACT comment near line 254-273 must be corrected/extended to say so explicitly for the token (do not let a future reader assume token provenance is lost the same way profile_id is).
9. **The route + handler.** Add `post_terminal_turn_state` to `terminal.rs` (same module as the other terminal handlers, since it needs `state.terminals`'s new private `tokens` map): parse `{terminal_id}` from the path and the JSON body (`{token, state}`); look up `state.terminals.tokens` for `terminal_id`; if absent OR `!tokens_match(...)`, return `terminal_error(StatusCode::UNAUTHORIZED, "unauthorized")` (same message/status for both cases — never distinguish "unknown terminal" from "wrong token"); otherwise parse `state` into `TurnState` (reject an unrecognized value with `terminal_error(StatusCode::BAD_REQUEST, "invalid turn state")`, only reachable after the token check passes); on success return `StatusCode::NO_CONTENT` — no persistence, no broadcast (Phase 5's job). Register it in `router.rs:466-469`'s outer chain, in the SAME `Router::new()...merge(protected)` expression, so it structurally sits outside `require_owner_auth`.
10. **Router CONTRACT comment (`router.rs:96-104`)** — amend to name three classes outside `protected`: `/pair` (one-time browser pairing), `/api/dashboard/link-auth` (daemon-to-daemon), and the new per-terminal turn-state callback (token-authed, non-browser, handler-level check).
11. **Spec amendment (`ai-docs/spec/ws-web-dashboard/index.md:38-39`, anchor `{#260516-ws-web-dashboard-token-free-pairing-landing}`)** — tier "The pairing route is the only unauthenticated browser entrypoint" into two classes: the pairing route (browser-facing, one-time, cookie-issuing) and the new callback route (non-browser, token-authed per terminal, never issues a cookie or touches session state).
12. **GC sweep (new module, e.g. `agent_profile_gc.rs`)** — pure candidate-selection function `orphaned_profile_ids(profile_root_entries: impl Iterator<Item = String>, live_ids: &HashSet<String>) -> Vec<String>` (unit-testable without touching a filesystem), skipping/logging (never deleting) any directory name that fails a basic sanity check (non-empty, no path separators, no `..`). An async driver `sweep_agent_profiles(state_dir: &Path, registry: &TerminalRegistry)` wraps the actual `fs::read_dir`/`remove_dir_all` + matching `agent_token_store::delete_token` in `spawn_blocking`, using `registry`'s in-memory `sessions` keys (NOT a second on-disk registry scan) as the liveness source — this is what makes "keys off TERMINAL liveness" (any status, including exited-but-in-grace) rather than `is_live()`'s strict Running-only check.
13. **Wiring the sweep in `server.rs`** — immediately after `let terminals = TerminalRegistry::boot_reconcile(...).await;` (`server.rs:113-118`) and strictly BEFORE `build_router`, spawn one background task: run `sweep_agent_profiles` once immediately, then loop on `tokio::time::interval(SWEEP_PERIOD).tick().await` (period on the order of minutes; no precedent in this codebase to match, pick a value generous enough that it never contends with normal terminal churn — e.g. 5 minutes). The straight-line placement (this spawn statement textually and temporally AFTER the already-awaited `boot_reconcile` line) is itself the reader-facing proof of correct ordering; back it with the regression test in Verification Plan item 3.
14. **Follow the ticket's own instruction to correct the reconcile-entry token CONTRACT comment** (item 8 above) so a later reader does not conflate token recovery with the permanently-lost `profile_id` case right next to it.
