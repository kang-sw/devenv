# Plan: 260525-feat-ws-dashboard-server-scoped-operation-forwarding — Phase 4: Remote files, documents, and document events

## Relevant Ticket Contract
- Forward file listing, file read, file write, and document-event SSE through Server Route-scoped routes so the file explorer, read-only/code/markdown views, edit mode, save/revert, stale/conflict handling, and document content-change fan-out work for remote WorkRoots as for local.
- Document pane identity, document event subscriptions, and write conflict keys must include `serverRoute`. Remote file write responses must preserve content hash and conflict semantics.
- SSE routes require proxying stream semantics, not one-shot fetch forwarding (ticket Constraints). This is the one genuinely new backend mechanism in this phase.
- Mutating remote operations (file writes) must preserve owner-auth gating at the local gateway and bearer auth to the linked daemon (already provided by the Phase 2 resolver/forwarding path).
- Backend forwarding must stay allowlisted: register explicit server-scoped routes only; do not add a wildcard proxy. Unregistered server-scoped paths keep 404-ing through the protected router.
- Naming/validation: land this phase's diff already reading as `serverRoute`/`server_route` with dot-free validation in place (the draft source commits predate the rename and use `server_id`; apply the rename inside each cherry-pick). Dot-free refusal is already enforced by `resolve_server_scoped_forwarding`.
- Reuse draft source commits `b6ebae74`, `d5d02e42`, `1201cf8d` (oldest first) from the phase-7 reference worktree rather than reimplementing; re-author docs/spec/closeout against current docs.
- Verification: pure endpoint tests, daemon forwarding tests for list/read/write, SSE proxy tests or browser smoke coverage for document events, and remote Windows dogfood editing a small markdown/text file.

## Out of Scope
- Document translation provider forwarding — stays local-gateway-owned. Do not collapse remote and local document source/cache identity if translation cache identity ever includes source identity (it must include the source Server Route). No change required this phase; just do not regress it.
- Activity SSE, terminal HTTP lifecycle, terminal WebSocket, Git, workspace mutations — Phases 5–7. Document-event SSE is the only stream this phase proxies; all other unregistered server-scoped paths must keep returning 404.
- Frontend identity/helper work — already landed in Phase 1 (see findings); no new frontend source change is expected beyond confirming wiring in verification.

- `ws-dashboard/Cargo.toml#L32` — `reqwest` currently has features `["json", "rustls-tls"]`. Draft adds `"stream"` (enables `bytes_stream()` for SSE passthrough via `Body::from_stream`). This is the only dependency change; `futures_util::Stream` is already a dep.
- SSE proxy design (draft `request_remote_document_events` + `forward_server_scoped_document_events` + `RemoteDocumentEventsResponse`/`RemoteDocumentEventStream`): opens a bearer-authenticated upstream `text/event-stream` GET, validates the upstream content-type is `text/event-stream` (else `502 BAD_GATEWAY` `InvalidStream`), forwards non-success upstream bodies as bounded errors, and re-streams raw bytes via `Body::from_stream(response.bytes_stream())`. It is an **opaque byte passthrough** — it does not parse or rewrite SSE frames. This is correct here: document-event payloads carry only `source.workRootId`/`path`/`contentHash`, and the browser scopes events by *subscription* (the server-scoped endpoint URL it connected to), so no per-frame serverRoute rewrite is needed. Cleanup is implicit: when the browser disconnects, the axum body stream drops, dropping the upstream `reqwest` response.
- `ws-dashboard/frontend/src/workRootFiles.ts#L182-L308` — `workRootFilesEndpoint`, `workRootFileReadEndpoint`, `workRootFileWriteEndpoint`, `workRootDocumentEventsEndpoint`, `fetchWorkRootTextFile`, `writeWorkRootTextFile` **already accept `serverRoute`** and build server-scoped URLs (verified by `workRootFiles.test.ts#L97-L113`). Pane identity (`readOnlyFilePaneId`/`readOnlyFilePaneLogicalKey`/`readOnlyFilePaneSourceKey`) and the source-key/apply helpers all include `serverRoute`. Frontend for Phase 4 is effectively complete from Phase 1.
- `ws-dashboard/frontend/src/App.tsx#L3867-L3888` (document-event `EventSource` uses `workRootDocumentEventsEndpoint(rootId, selectedWorkRootServerId)`), `#L3324-L3362` (read paths thread `serverRoute`), `#L6571-L6591` (write threads `pane.serverRoute`; conflict via `baseContentHash`/`contentHash`). All file/document call sites already carry `serverRoute`. This makes Phase 4 backend-only, mirroring Phase 3 being frontend-only.
- `ws-dashboard/crates/daemon/tests/routes.rs#L2600` (`linked_server_one_shot_forwarding_preserves_bearer_errors_and_rewrites_resources`), `spawn_test_server`, `LinkedServerSessions`/`LinkedServerTunnels::record_only_for_tests()`, `PersistedLinkedServer` — the forwarding test harness (mock upstream daemon + persisted linked server + injected bearer session) already exists and is the pattern for list/read/write forwarding tests and the SSE proxy test. Draft commits `d5d02e42`/`1201cf8d` add exactly these route tests plus the e2e coverage.
- `ai-docs/spec/ws-web-dashboard/index.md#L289-L292` — spec currently states unregistered server-scoped paths "(SSE, terminal WebSocket, unlisted operations) fall through the protected router as `404` rather than proxying". **This is now partially false for document events** and must be corrected/extended: add a subsection documenting that document-event SSE proxies as a stream (bearer-authed upstream `text/event-stream`, opaque byte passthrough, `502` on missing/non-event-stream upstream content-type, upstream errors preserved) while Activity SSE and terminal WebSocket remain deferred/404. Extend the existing `{#260703-...}` anchor per the ticket's "extend, don't duplicate" pattern from Phases 2/3.
