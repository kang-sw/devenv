# Plan: 260722-feat-dashboard-settings-panel — Phase 1: Settings modal shell, section registry, shared prefs store, Terminal-style section

## Relevant Ticket Contract

- Global, dashboard-wide Settings modal (react-aria `ModalOverlay`/`Modal`/`Dialog`, following `GitWorktreeRemoveModal`), reachable and closable regardless of which/whether a workRoot is focused.
- Section-registry architecture: sections register id/title/render surface; shell has no knowledge of section internals. Registry contract must visibly accommodate a hypothetical future section (hotkey-rebind) without shell code changes — do not build that section now.
- First concrete section: Terminal style (font family, font size, background theme), persisted via a new shared namespaced-prefs helper generalizing the existing `browserStorage()` + `"ws-dashboard.<feature>.v<N>"` versioned-JSON, defensive-parse pattern (`hotkeys.ts` is the model to generalize, not necessarily to retrofit).
- Font-family control is free-text CSS family string **prepended** to the existing hardcoded fallback stack (`App.tsx:9108-9111`); unset must reproduce today's exact hardcoded look.
- **Live fan-out (sage-derived, hard constraint):** each terminal pane subscribes to the shared prefs store/context and applies `terminal.options.fontFamily/fontSize/theme = ...` on change via a standard React subscription — construction-time-only wiring is explicitly disallowed. New terminal panes read the persisted value at construction time.
- **Protected zone (sage-derived, hard constraint):** the live-update subscription must not touch the terminal restore/reattach mount effect (`App.tsx:9098-9429`, ticket's approximate anchor `9083-9230` — see drift note in Codebase Findings).
- Must not regress terminal visual-restore/reattach behavior.
- Panel must be keyboard-operable: open, navigate sections, close — without a mouse.
- Acceptance: modal opens/closes cleanly from any workroot context; Terminal font/size/theme changes apply live to open panes and persist across reload; sections are independently registered; no restore/reattach regression.
- Mental model rule (`ws-web-dashboard.md` Domain Rules #1): any change to visible browser UI needs browser-level (Playwright) verification, not just TS/unit tests.

## Out of Scope

- Phase 2 hotkey-rebind editor section — do not build; only keep the registry contract able to host it later.
- Retrofitting `hotkeys.ts`, `workNavOrder.ts`, `terminals.ts`, `layoutRestore.ts` onto the new shared prefs helper — ticket asks the helper to *generalize* the existing pattern, not migrate existing consumers.
- Adding a new leader-hotkey binding for opening Settings (see risk signal below) — the visible topbar affordance alone satisfies the "keyboard-reachable" acceptance criterion.
- Any change to the terminal restore/reattach mount-effect body beyond substituting the 3 hardcoded `Terminal(...)` constructor option values for prefs-derived reads (see Implementation Plan step 4) — no other line in that effect changes.

## Implementation Plan

1. `ws-dashboard/frontend/src/settingsStore.ts` (new file): generic namespaced-prefs helper generalizing `hotkeys.ts:459-574` — `loadNamespacedPrefs<T>(key: string, version: number, parse: (raw: unknown) => T | null, defaults: T, storage = browserStorage()): T` and `saveNamespacedPrefs<T>(key: string, version: number, value: T, storage = browserStorage()): void`, importing `browserStorage` from `./workRootFiles.js`. Same try/catch-swallow, `{version, ...}` JSON shape, defensive-parse-falls-back-to-defaults behavior as the precedent. Also export the `SettingsSectionDescriptor` type (`{ id: string; title: string; Component: ComponentType }`, using `ComponentType` from `"react"` — plain type import, no JSX, stays a `.ts` file) for the section registry contract.

2. `ws-dashboard/frontend/src/terminalPrefs.ts` (new file): `TerminalStylePrefs` type (`fontFamilyOverride: string`, `fontSize: number`, `themeBackground: string`), `DEFAULT_TERMINAL_STYLE_PREFS` reproducing today's hardcoded values (empty override, `12`, `"#0b0d10"`), `TERMINAL_FONT_FALLBACK_STACK` constant (the literal string currently inline at `App.tsx:9108-9111`), `loadTerminalStylePrefs()`/`saveTerminalStylePrefs()` built on `settingsStore.ts`'s helper under key `"ws-dashboard.settings.terminal.v1"`, and a pure `buildEffectiveTerminalFontFamily(override: string): string` — returns `TERMINAL_FONT_FALLBACK_STACK` unchanged when `override` is empty/whitespace, else `` `${override.trim()}, ${TERMINAL_FONT_FALLBACK_STACK}` ``.

3. `App.tsx`: add `export const TerminalPrefsContext = createContext<TerminalStylePrefs>(DEFAULT_TERMINAL_STYLE_PREFS);` at module scope (new `createContext` import from `"react"`). In `App()`, add `const [terminalPrefs, setTerminalPrefs] = useState(() => loadTerminalStylePrefs());` and wrap the existing `<main className="app-shell">` return value in `<TerminalPrefsContext.Provider value={terminalPrefs}>...</TerminalPrefsContext.Provider>`.

4. `App.tsx` `TerminalPaneBody` (`9044+`): only-in-protected-zone change — extend the existing `liveRef.current = { pane, actions };` line (`9079-9080`, just above the mount effect, itself not inside it) to `{ pane, actions, terminalPrefs }` (add `const terminalPrefs = useContext(TerminalPrefsContext);` near the top of the component and a matching field to the `useRef({...})` initializer). Inside the mount effect (`9104-9114`, the ONLY line range touched inside 9098-9429), replace the 3 hardcoded `Terminal({...})` field values with `fontFamily: buildEffectiveTerminalFontFamily(liveRef.current.terminalPrefs.fontFamilyOverride)`, `fontSize: liveRef.current.terminalPrefs.fontSize`, `theme: { background: liveRef.current.terminalPrefs.themeBackground }`. No other line in the effect body or its cleanup changes.

5. `App.tsx` `TerminalPaneBody`: add a NEW `useEffect(() => { const terminal = terminalRef.current; if (!terminal) return; terminal.options.fontFamily = buildEffectiveTerminalFontFamily(terminalPrefs.fontFamilyOverride); terminal.options.fontSize = terminalPrefs.fontSize; terminal.options.theme = { background: terminalPrefs.themeBackground }; }, [terminalPrefs]);` declared textually AFTER "Effect B" (after `9509+`, end of the component body) so on first mount it runs after the protected mount effect has set `terminalRef.current`. This is the live-fan-out subscription the ticket requires; it never touches 9098-9429.

6. `commands.ts`: add `"settings.open" | "settings.close"` to `DashboardCommandId`, add `{ type: "settings.open" } | { type: "settings.close" }` to `DashboardCommandPayload`, and add `buildSettingsOpenCommand()`/`buildSettingsCloseCommand()` builders (no target id — global command), following `buildWorktreeRemoveOpenCommand`/`buildWorktreeRemoveCloseCommand` shape (`commands.ts:272-289`) minus the `workRootId`/`serverRoute` args.

7. `App.tsx` `App()`: add `const [settingsOpen, setSettingsOpen] = useState(false);`. In the existing command-registration `else if` chain (pattern at `App.tsx:1317-1336`), add `else if (command.payload.type === "settings.open") { executableHandlers[command.commandId] = () => setSettingsOpen(true); }` and the `"settings.close"` counterpart.

8. `App.tsx` `ResourceNavigation`'s `.server-nav-toolbar` (`3701-3721`): add a second `ChromeIconButton` (`commandId="settings.open"`, `icon={SettingsIcon}` — import `Settings as SettingsIcon` from `lucide-react`, no existing name collision, `label="Settings"`) next to "Add server", dispatching `onCommand(buildSettingsOpenCommand(), { "settings.open": onOpenSettings })` where `onOpenSettings` is a new prop threaded from `App()` the same way `onOpenAddServer` already is.

9. `App.tsx` (new top-level component, alongside `GitWorktreeRemoveModal`): `SettingsModal({ open, sections, onCommand, onClose }: { open: boolean; sections: readonly SettingsSectionDescriptor[]; onCommand: DashboardCommandDispatcher; onClose: () => void })`. Mirrors `GitWorktreeRemoveModal`'s `ModalOverlay`/`Modal className="root-picker-modal settings-modal"`/`Dialog aria-label="Settings" className="root-picker-dialog"` shell, titlebar with `Heading` "Settings" + close `ChromeIconButton` (`commandId="settings.close"`). Body is `.root-picker-content`-styled two columns: left `<nav>` mapping `sections` to `<button>` items (local `useState` for `activeSectionId`, default `sections[0]?.id`), right pane renders `<ActiveSection.Component />` for the selected descriptor. Mount as `<SettingsModal open={settingsOpen} sections={SETTINGS_SECTIONS} onCommand={executeCommand} onClose={() => setSettingsOpen(false)} />` next to `GitWorktreeRemoveModal` (`App.tsx:1912` area), inside the `TerminalPrefsContext.Provider` from step 3.

10. `App.tsx`: add `const SETTINGS_SECTIONS: readonly SettingsSectionDescriptor[] = [{ id: "terminal", title: "Terminal", Component: TerminalStyleSection }];` at module scope, and a new `TerminalStyleSection()` component: reads `terminalPrefs`/`setTerminalPrefs` (either via the same `TerminalPrefsContext` for display, or simpler — have `SettingsModal` receive `terminalPrefs`/`onTerminalPrefsChange` as props from `App()` and pass them down to `TerminalStyleSection` via the section's render props, since `App()` already owns `terminalPrefs` state and must call `saveTerminalStylePrefs` on change). Renders: free-text font-family input (`<input type="text">`, reusing `.root-picker-input` styling), font-size number input, theme-background color/text input; on any change, compute the next `TerminalStylePrefs`, call `setTerminalPrefs(next)` (drives the Context, live-applies to open panes via step 5's effect) and `saveTerminalStylePrefs(next)` (persists).

11. `styles.css`: add `.settings-modal .root-picker-dialog { grid-template-rows: auto auto minmax(240px, 1fr); }` (no toolbar/context/footer rows needed, unlike the worktree-remove form) following the `.git-worktree-modal .root-picker-dialog` override precedent (`styles.css:3571`); add minimal section-nav/section-body classes reusing existing `.root-picker-places`/`.root-picker-content` tokens where the shapes match, adding new classes only where they don't (e.g. active-section-button state).

12. `App.tsx`: import `Settings as SettingsIcon` and `createContext`/`useContext` (extend existing `"react"` and `"lucide-react"` import statements at the top of the file rather than adding new import statements).
