# Plan: 260722-bug-e2e-terminal-resize-frame-assertion-fails — Phase 1: Forward terminal resize over the socket on WS open

## Relevant Ticket Contract
- Locked fix strategy (not open for reinterpretation): the WebSocket `"open"` handler must trigger a resize forward over the now-open socket, and `forwardSize()`'s early-return/no-op gate (governed by `lastForwardedSizeRef`) must become transport-aware so this socket-open catch-up send is not suppressed just because a prior HTTP-fallback forward already latched the ref to the same dimensions.
- Constraint: behavior-preserving. The re-sent dimensions must be identical to what the daemon already holds via the HTTP fallback (`session.resize()` is idempotent on identical dims) — resulting PTY size and all user-observable behavior are unchanged; only the transport changes.
- Do not touch the client message schema (`terminals.ts:49-51`) or daemon deserialization (`terminal.rs:280-285`) — both already correct and not implicated.
- Completion boundary: `ws-dashboard/frontend/e2e/dashboard-acceptance.spec.ts` reaches the `spec.ts:2714` resize-frame assertion green, full suite run introduces no new failures elsewhere.
- Spec anchor already covers the target contract, no spec change: `ai-docs/spec/ws-web-dashboard/index.md#remote-terminal-websocket-gatewaying` ("carries PTY output, input, resize, ping/pong, and close frames").

## Out of Scope
- Any change to `terminals.ts` client message schema or `terminal.rs` daemon deserialization/resize handling — ticket explicitly excludes these, both already match.
- Any change to the HTTP fallback path itself (`liveRef.current.actions.onResize`) beyond what's needed to record its transport.
- Reworking `scheduleResizeForward`, `paneVisible` effect, or `terminalPrefs` effect invocation sites (~402-412, ~483-510, ~629-648) — they already call `forwardSize()`/`forwardSizeRef.current?.()` correctly and are unaffected by this fix.
- The unrelated `spec.ts:2588` prompt-content mismatch under zsh/starship — documented as an environment artifact, not part of this ticket; addressed only by running the daemon subprocess with `SHELL=/bin/bash`, not by a code change.

## Implementation Plan
1. In `ws-dashboard/frontend/src/terminalPaneBody.tsx`, change the `lastForwardedSizeRef` type at L85-87 from `{ columns: number; rows: number } | null` to `{ columns: number; rows: number; transport: "socket" | "http" } | null`.
2. In `forwardSize()` (L341-394): compute `const socketOpen = socketRef.current?.readyState === WebSocket.OPEN;` immediately before the gate at L358 (reusing the read rather than duplicating readyState logic separately from L364-365). Change the gate at L358-361 to also require the transport to match: `if (prev && prev.columns === next.columns && prev.rows === next.rows && prev.transport === (socketOpen ? "socket" : "http")) return;`. This preserves the existing debounce/no-op behavior when the transport is unchanged, while letting a same-dimension call through when the transport differs (the socket-open catch-up case, and symmetrically an HTTP-fallback retry after a prior socket-send).
3. In the same function's socket-send success path (L373-384), change the `lastForwardedSizeRef.current = next;` assignment (L383) to `lastForwardedSizeRef.current = { ...next, transport: "socket" };`.
4. In the HTTP-fallback success path's `.then()` callback (L388-390), change `lastForwardedSizeRef.current = next;` to `lastForwardedSizeRef.current = { ...next, transport: "http" };`.
5. In the WS `"open"` listener (L548-562), after the existing `liveRef.current.actions.onSocketStatus(liveRef.current.pane, "connected", null);` call and still inside the non-`disposed` branch, add `forwardSizeRef.current?.();` to trigger the catch-up resize forward now that the socket is open. Do not add this call before the disposed check or outside the `if (disposed) {...}` early-return branch — that branch already returns early after closing the orphaned socket.
6. No changes needed to `scheduleResizeForward` (L402-412), the `paneVisible` effect (L483-510), the `terminalPrefs` effect (L629-648), `terminals.ts`, or `terminal.rs` — all out of scope per the locked strategy and already correct.
