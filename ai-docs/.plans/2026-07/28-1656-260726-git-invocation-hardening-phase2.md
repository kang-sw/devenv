# Plan: 260726-refactor-ws-dashboard-long-uptime-leak-hardening — Phase 2: git invocation hardening (no-prompt + descendant-process containment)

## Relevant Ticket Contract

- Primary requirement (Phase 2 body): at the `git_text`/`run_git` seam, set `GIT_TERMINAL_PROMPT=0` and disable interactive credential prompting so a credential-required fetch fails fast instead of blocking for the full timeout budget.
- Scope update (2026-07-26, commit `0c48065a`): the bounded-timeout half is already shipped via `git_exec::capture` (deadline + kill on expiry + concurrent pipe drain). Only the no-prompt half and two named additions remain.
- Cross-Child Decision ("git policy is uniform"): apply `GIT_TERMINAL_PROMPT=0` (+ disable interactive askpass) once at the seam, not per call site.
- Addition A (containment): the detached reader threads left running past a timeout/truncation are a deliberate, currently-*unbounded* leak (`git_exec.rs:577-598`, `:650-668`). Ticket requires picking one of: (a) process-group/Job-Object teardown, (b) cap outstanding detached threads and refuse/queue past the cap, or (c) explicit accept-and-document with no code change.
- Addition B (unkillable child): `kill()`/`wait()` after a timeout is itself unbounded against a child wedged in uninterruptible I/O. Ticket requires either detecting/reporting that case or explicitly documenting it as out of reach.
- Verification boundary (ticket text): a hung/prompting remote returns an error within the timeout (already true via the shipped bound); a credential-required fetch fails fast rather than consuming the full budget (not yet true — this is what Phase 2 must deliver); the chosen containment mechanism demonstrably bounds an *immortal* descendant (not just an ordinary one finishing on its own); the unkillable-child case is detected/reported or explicitly documented as out of reach.
- `GitFailure`/`GitOutcome`/`GitSpawnStats` behavior contracts from the already-shipped seam (`git_exec.rs`) must not regress: `run_git` (status-only) ignores `output_truncated`; `git_text`/discovery probes must never read a truncated buffer as a complete answer; every `capture` call still increments `stats.total`/`by_subcommand` regardless of outcome.

## Out of Scope

- Phase 1 (terminal reaper) and Phase 3 (`DocumentWriteLocks`, WS heartbeat, reqwest timeout) — separate phases, already/not-yet in progress.
- The "optional single-flight" item — already struck from the ticket (covered by `GitStateCache`'s existing per-key single-flight).
- Test-fixture-only direct `git` spawns that bypass `git_exec::capture` (`discovery.rs`'s `#[cfg(test)] mod tests`, `crates/daemon/tests/routes.rs`'s own `run_git`/`init_git_repo` fixtures) — these seed repo state for tests and are explicitly not part of the production seam; no change needed.
- `core.askPass` / repo-local git config overrides of the env-based no-prompt controls — not raised by the ticket, real but narrow residual risk noted below, not required to close.
- Windows-specific live verification of a Job-Object containment path (rejected in favor of a portable cap-based mechanism — see Codebase Findings and rationale below), matching this ticket's own prior precedent (Phase 1) of accepting narrower, lower-risk fixes over deeper platform-specific mechanisms where both satisfy the stated boundary.

## Codebase Findings

- `ws-dashboard/crates/daemon/src/git_exec.rs#L482-L520` — `capture_with_program` builds the `Command` with `.stdin(Stdio::null())` but sets **no environment variables**. `GIT_TERMINAL_PROMPT`/`GIT_ASKPASS`/`GIT_SSH_COMMAND` are not set anywhere in the crate today. This confirms the no-prompt half is genuinely unshipped, not already covered by `Stdio::null()`: git's own terminal-prompt path opens `/dev/tty` directly rather than checking the child's stdin fd, so redirecting stdin does not suppress it — the env var is the only lever.
- `git_exec.rs#L288-L303` — `git_timeout_from_env()` is the established pattern for a once-per-process env-derived setting (`OnceLock`, parsed once, mirrors `discovery.rs`'s `git_probe_ttl_from_env`). A new `GIT_SSH_COMMAND` (with `BatchMode=yes` appended) should follow the same shape rather than re-reading `env::var` per call.
- `git_toolbar.rs#L797-L825` (`git_text`/`run_git`, the seam the ticket names) both delegate directly to `git_exec::capture` with no other `Command` construction — the real single change point is `capture_with_program`, which every call site (`git_toolbar.rs`, `discovery.rs`, `work_root_watch.rs`) routes through (confirmed via `grep -rn "git_exec::capture\|use crate::git_exec"` across `crates/daemon/src`).
- `git_exec.rs#L90-L99` — `GitFailure` enum (`Spawn`/`Timeout`/`Status`) has no exhaustive external `match`; every call site outside `git_exec.rs` itself uses `.ok()`/`.map_err(|_| ())`/`matches!`. Adding a new variant (for a cap-refusal) is safe with no call-site changes required (confirmed via `grep -n "GitFailure::"` — only hits inside `git_exec.rs`).
- `git_exec.rs#L577-L605` (hard-timeout path) and `#L631-L668` (output-truncated path) — both already carry extensive, deliberate documentation ("DELIBERATE THREAD LEAK") explaining *why* the two reader threads are left detached and uncollected rather than joined: joining would re-introduce the exact unbounded wait the seam exists to remove. This is precedent, not a bug to "fix away" — Addition A must add *containment*, not remove the detach.
- `git_exec.rs#L402-L417` (`spawn_reader`) — spawns via `thread::Builder` (not `thread::spawn`) specifically so an OS thread-refusal doesn't panic-unwind with a live child. Any new bookkeeping added here must preserve that error path (`reader_spawn_failed`, `#L422-L437`).
- `crates/daemon/src/terminal_platform.rs#L21-L156` — the crate already has a fully-built, tested, cross-platform "put a child in its own kill-able group" mechanism: Unix `setsid()` + double-fork (`unix::spawn_detached`) and Windows `CREATE_BREAKAWAY_FROM_JOB`/`CreateJobObjectW`+`JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE` (`windows::create_kill_on_close_job`/`assign_into_job`). This is real, relevant precedent for Addition A's option (a) — but it solves a different problem (detaching a helper so it *survives* the daemon) and would need new per-git-child Job Object plumbing (Windows has no `killpg`-equivalent without a fresh Job Object per spawn) plus `unsafe` `pre_exec`/`setpgid` wiring on Unix. This is correctness-sensitive surgery on the *only* seam every git spawn in the daemon goes through — a mistake here (e.g. a process-group id collision, or breaking signal delivery to the daemon's own children) has a much larger blast radius than the leak it fixes, for a leak class (immortal ssh `ControlPersist`/credential-cache masters) whose frequency this same phase's no-prompt half already reduces.
- `git_exec.rs#L202-L221` (`GitSpawnStats` struct) — counters are plain atomics (`AtomicU64`), not individually `Arc`-wrapped, and `capture`/`capture_with_program` take `stats: &GitSpawnStats` (a borrow), not `Arc<GitSpawnStats>`. `AppState.git_spawn_stats: Arc<GitSpawnStats>` (`router.rs#L94`) is the only `Arc`-wrapped instance; every `git_exec.rs`/`git_toolbar.rs` test constructs a bare `GitSpawnStats::default()` (no `Arc`). Changing `capture`'s signature to take `Arc<GitSpawnStats>` (needed only if a *detached reader thread* itself must reach `stats`) would force wrapping every one of those test constructions — real but avoidable churn.
- Because of the above, option (b)'s cap is implementable **without** any signature change: add one `detached_readers: Arc<AtomicU64>` *field* inside `GitSpawnStats` (the field owns its own `Arc`, so `stats.detached_readers.clone()` yields an independently-owned, `'static`-capable handle regardless of how long the `&GitSpawnStats` borrow lives) and pass that cloned handle into `spawn_reader`'s thread closure. A live increment-on-spawn / decrement-on-thread-exit gauge (rather than a "detect abandonment via failed channel send" scheme) is simpler and matches the resource being bounded exactly: ordinary fast reads increment-then-decrement near instantly and net to ~0; only a reader genuinely wedged behind an immortal descendant (its `read_to_end` never returns) stays counted — precisely the case the cap must catch.
- `git_toolbar.rs#L399-L435` (`mutate_no_body`) confirms `push`/`fetch`/`pull --ff-only` (the credential/network-touching commands) all route through `run_git` → `capture`, all already inside `tokio::task::spawn_blocking` (`git_toolbar.rs:169,192,216,281,406`; also `discovery.rs`, `work_root_watch.rs:1192`) — confirms the ticket's "ties up spawn_blocking worker threads" framing is accurate and that the fix belongs in `capture_with_program` (one place) rather than per call site.
- **Risk signal (scope interpretation, flagged for reviewer):** the ticket's literal Phase-2 text and Cross-Child Decision name `GIT_TERMINAL_PROMPT=0` + "disable interactive askpass" but do not explicitly mention SSH transport. `GIT_TERMINAL_PROMPT`/`GIT_ASKPASS` only cover git's own HTTPS credential-fill prompt; they do **not** stop `ssh` (invoked by git for `git@`/`ssh://` remotes) from opening `/dev/tty` directly for a password/passphrase/host-key prompt when the daemon process has a controlling terminal (the realistic dogfood case: a foreground dev daemon). Closing that path needs `GIT_SSH_COMMAND` with `-o BatchMode=yes`, which the ticket text does not name explicitly. This plan includes it (preserving any inherited `GIT_SSH_COMMAND` by appending the flag rather than overwriting) because leaving it out would leave the ticket's own motivating scenario (a blocking prompt during heavy dogfood use) only half-fixed for the common SSH-remote case, and "git policy is uniform" reads as intending full coverage at the one seam. Flagging so the lead can confirm this reading is in scope.

## Implementation Plan

1. **No-prompt env vars** (`git_exec.rs`, `capture_with_program`, ~`L494-L505`): add to the `Command` builder, unconditionally (harmless for the non-`git` test-injected `program`, so no `if program == "git"` guard needed, unlike the existing `-C` flag guard):
   - `.env("GIT_TERMINAL_PROMPT", "0")`
   - `.env("GIT_ASKPASS", "")` and `.env("SSH_ASKPASS", "")` — an empty program string never spawns/hangs on either platform, and covers git's HTTPS credential-fill prompt and any non-`GIT_SSH_COMMAND` ssh askpass fallback.
   - `.env("GIT_SSH_COMMAND", ssh_command_from_env())` — new helper mirroring `git_timeout_from_env()`'s `OnceLock` shape (~`L288-L303`): read `GIT_SSH_COMMAND` from the daemon's own environment once; if set, append `" -o BatchMode=yes"`; if unset, default to `"ssh -o BatchMode=yes"`. This is the lever that actually stops ssh from opening `/dev/tty` for host-key/passphrase prompts (see risk signal above).
   - Update the module doc comment (`L1-L25`) and `capture`'s doc comment (`L439-L467`) to add "no interactive prompt (terminal, askpass, or ssh) — every credential path fails fast instead of blocking" to the bulleted contract list.
2. **Bounded detached-reader cap** (Addition A, option (b) — see rationale in Codebase Findings):
   - `GitSpawnStats` (~`L202-L221`): add `detached_readers: Arc<AtomicU64>` field, `Default` gives `Arc::new(AtomicU64::new(0))`. Add a `fn outstanding_readers(&self) -> u64` getter (relaxed load).
   - Add a `MAX_OUTSTANDING_GIT_READERS: u64` constant near the other tuning constants (~`L262-L286`); pick and state a concrete value (propose 32 reader-thread pairs = 16 stuck calls' worth — small enough to keep a targeted unit test's wall-clock bounded at a 200ms-timeout budget, large enough not to trip under ordinary transient network blips).
   - `spawn_reader` (~`L402-L417`): add an `outstanding: Arc<AtomicU64>` parameter. Increment (`fetch_add(1, Relaxed)`) immediately before `thread::Builder::spawn`; inside the spawned closure, decrement (`fetch_sub(1, Relaxed)`) as the last statement (after the `tx.send(...)` line), so the gauge tracks "reader threads currently alive," not "collected vs. abandoned" — a wedged reader (its `read_to_end` never returns) simply never reaches the decrement and stays counted forever, which is exactly the leak the cap must bound.
   - `capture_with_program` (top of function, right after `stats.record_spawn(subcommand)`, before `Command::new(program).spawn()`): if `stats.outstanding_readers() >= MAX_OUTSTANDING_GIT_READERS`, call `stats.record_failure()`, `tracing::warn!(...)`, and `return Err(GitFailure::TooManyDetachedReaders)` without spawning the child at all.
   - Both `spawn_reader` call sites (~`L530-L538`) pass `stats.detached_readers.clone()`.
   - `GitFailure` enum (~`L90-L99`): add `TooManyDetachedReaders` variant (no payload needed — the cap value is a constant, not per-call data).
3. **Unkillable-child documentation** (Addition B — accept-and-document, no code change): extend the doc comment at `capture`'s `L450-L453` (which already says "Modulo an unkillable child: `wait()` after `kill()` blocks...") and add a short comment at the hard-timeout `child.kill(); child.wait();` call site (~`L596-L597`) explicitly stating: a child wedged in uninterruptible I/O (stale 9p/NFS/CIFS mount under WSL) makes this `wait()` block the calling `spawn_blocking` thread indefinitely; portably detecting that state (Linux `D`-state via `/proc/<pid>/stat`, no cross-platform equivalent) is out of reach for this phase; accepted with no code change, consistent with the same disposition already made for a materially identical concern in commit `0c48065a`'s "Minor #2 and #4 accepted with no action" note.
4. **Tests** (`git_exec.rs` `#[cfg(test)] mod tests`):
   - New: assert the env vars actually reach the child — inject a shell program (`sh -c 'printf "%s:%s:%s" "$GIT_TERMINAL_PROMPT" "$GIT_ASKPASS" "$GIT_SSH_COMMAND"'` on unix; a `powershell -Command` equivalent on windows, mirroring `EMIT_AND_EXIT_ZERO`'s existing per-platform pattern) and assert the captured stdout matches `0::ssh -o BatchMode=yes` (test the `GIT_SSH_COMMAND`-preserved-and-appended variant separately, by setting the env var before the call).
   - New: unix-only, drive `MAX_OUTSTANDING_GIT_READERS`-worth of induced timeouts (reuse the existing `sh -c "sleep 5 & sleep 5"` grandchild-holds-pipes pattern from `capture_times_out_within_budget_when_a_grandchild_still_holds_the_pipes`) and assert the next call returns `Err(GitFailure::TooManyDetachedReaders)` immediately (bounded wall-clock, no new child spawned).
   - Keep all existing pins (`capture_kills_and_reports_timeout_for_a_child_that_outlives_its_budget`, `capture_times_out_within_budget_when_a_grandchild_still_holds_the_pipes`, `a_descendant_holding_the_pipes_yields_a_truncated_but_real_zero_exit`, `a_descendant_holding_the_pipes_preserves_a_non_zero_exit_status`, `a_zero_budget_capture_collects_output_at_child_exit_without_timing_out`) passing unmodified — none of them assert on `Command`'s env or thread count, so they should be unaffected; each test constructs its own `GitSpawnStats`, so no cross-test contention on the new counter.
