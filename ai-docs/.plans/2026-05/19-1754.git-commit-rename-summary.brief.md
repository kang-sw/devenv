# Brief: 260515-bug-git-commit-rename-status-summary

## Intent

Fix `ws/git.commit` ticket-change summaries when a ticket status move is staged
as add/delete records instead of a native Git rename because the moved ticket was
heavily edited.

## Scope Boundary

Implement Phase 1 only: reconstruct unambiguous same-stem ticket add/delete
pairs as ticket status moves in the `git.commit` `ticket_changes` summary. Do
not change native Git commit behavior, staging behavior, or ambiguous add/delete
handling.

## Caller-Visible Contract

When `git.commit` sees staged ticket changes shaped as one added
`ai-docs/tickets/<to-status>/<stem>.md` and one deleted
`ai-docs/tickets/<from-status>/<stem>.md`, and the pair is unambiguous, the
returned ticket change reports:

- `from_status` from the deleted path;
- `to_status` from the added path;
- `path` as the added destination path;
- `old_path` as the deleted source path.

If a `### Result` or `#### Edition` heading is detected for the same stem, that
result evidence is merged into the reconstructed move. Ambiguous add/delete sets
remain non-move ticket changes and must not invent a destination status.

## Implementation Strategy Decisions

- Treat this as a summary-layer fix only; native Git add/delete output remains
  valid input.
- Preserve existing `R...` rename handling and prefer explicit rename records
  over synthesized add/delete moves.
- Synthesize moves only for exactly one added and exactly one deleted ticket path
  for the same stem with different recognized statuses.
- Keep result-heading merge keyed by stem from corrupting destination status.

## Rejected Alternatives

- Do not reject commits when ticket summary inference is ambiguous; the commit is
  valid even if the workflow summary is less specific.
- Do not infer moves across multiple adds or deletes for the same stem.
- Do not use content similarity or full file comparison in the workflow wrapper.

## Approach

- Extend ticket name-status parsing or post-processing in
  `agents-plugin-tool/internal/wsgit/git.go`.
- Add unit tests for explicit rename preservation, add/delete move
  reconstruction, result-heading merge, and ambiguity guards.
- Add MCP JSON coverage only if core result behavior is not already exercised
  through existing server tests.

## Constraints

- Exact ticket stem and recognized status directory parsing must remain the
  source of truth.
- Existing ticket Result/Edition detection must keep working for non-move
  tickets.
- Existing `ticketChangeSummaries` output should naturally produce the move
  summary once `from_status` and `to_status` are correct.

## Out of scope

- Changing CLI arguments or MCP schemas.
- Changing `ws/tickets.status`.
- Handling non-ticket file renames or arbitrary Git rename detection.
