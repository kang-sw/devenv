# Brief: 260523-bug-ws-dashboard-activity-console-dogfood-usability Phase 1

## Intent

Repair the first usability blockers from Activity Console dogfood: opening
WorkRoot Activity should use the support split instead of displacing the
agent/terminal-side split, and transcript scrolling should behave like a live
tailing view without snapping the user back to the top during refreshes.

## Scope Boundary

Implement only Phase 1: WorkRoot Activity pane placement and transcript
scroll/tail stability. Leave Phase 2 compact transcript summary quality and
Phase 3 Codex native transcript coverage untouched except where existing tests
need harmless fixture updates for Phase 1.

## Caller-Visible Contract

Opening the WorkRoot Activity detail from the selected workRoot's top-bar badge
focuses an existing Activity pane if present. A first open prefers the
second/support split when that split exists or can be created by existing
workbench placement policy. Closing remains reversible and has no daemon-side
agent or transcript side effect.

The selected transcript view tail-follows by default for newly selected or live
updated activity. If the user scrolls away from the tail, the view preserves the
user's scroll position and does not snap upward during feed refresh, transcript
refresh, selected transcript refresh, or Dockview split rerenders. The user can
return to the tail to resume follow behavior.

The Activity Ribbon remains horizontally scrollable at constrained widths.

## Contract Instructions

Update the dashboard frontend placement path for `workRootActivity` surfaces:
the top-bar badge command must still route through dashboard command dispatch
and `decideSurfaceOpenWithDynamicGroups`, but new Activity panes must no longer
depend on a hard-coded group-1 exception. Preserve duplicate-open focus behavior
for the same logical Activity pane and preserve reversible close semantics.

Do not only change the placement policy. The rendered WorkRoot Activity pane
must appear in the chosen group, so App-owned group/pane state must represent
the Activity pane's group instead of rendering it only for `index === 0`.
Reuse existing workbench placement/group helpers before adding new ad hoc
Dockview or pane-routing state.

Update the transcript viewer so refreshes do not unmount/remount the scroll
container unnecessarily when a prior transcript is available. Add explicit
auto-follow state or equivalent scroll policy: follow while the user is at the
tail, pause when the user scrolls away, and resume when the user returns to the
tail. Keep load-more behavior safe and avoid repeated load loops.

If initial transcript pagination cannot yet fetch the latest tail from the
backend, make that limitation explicit in the implementation report instead of
pretending top-of-transcript loading is solved. Do not change backend transcript
source adapters in this phase.

## Integration Test Instructions

Extend focused frontend tests around:

- workbench placement policy and App wiring so a new WorkRoot Activity pane
  lands in group 2/support split while duplicate opens focus the existing pane;
- transcript scroll policy helpers or component behavior proving default
  tail-follow, pause when scrolled away, and no snap-back on refresh/update.

Extend browser-level daemon-served acceptance coverage for visible behavior:

- opening Activity Console from the badge creates/focuses the pane in group 2
  in the default two-split layout;
- the horizontal ribbon remains scrollable at constrained width;
- transcript scroll remains stable across an Activity refresh or streamed
  selected transcript update instead of returning to the top.

Run the relevant frontend test command(s), browser gate, and build command used
by the dashboard frontend when UI behavior changes.

## Implementation Strategy Decisions

- Prefer existing support-split placement policy over a new Activity-specific
  placement mechanism.
- Preserve command-routed visible controls; do not introduce direct click-only
  behavior.
- Treat transcript scroll behavior as browser-local UI state. Do not add daemon
  acknowledgement or read-receipt state.
- Keep Activity Console read-only. No start, interrupt, cancel, erase, retry, or
  exec-job control actions are in scope.

## Rejected Alternatives

- Keeping Activity as a group-1 exception: dogfood feedback found this poor for
  lead-agent monitoring.
- Fixing only the active-pane target while leaving the rendered pane hard-coded
  in group 1: that would make visible layout and state disagree.
- Solving scroll snap-back by disabling live refresh: live updates are part of
  the Activity Console contract.

## Approach

- Remove or narrow the WorkRoot Activity group-1 exception in workbench
  placement and App rendering.
- Persist or derive the Activity pane's group from the same dashboard-owned
  placement state used by other workbench surfaces.
- Keep existing transcript blocks visible during replacement refreshes when
  safe, and apply scroll-to-tail only when the user is following.
- Add small pure helpers for scroll-at-tail/follow decisions if that keeps tests
  focused and avoids brittle DOM-only assertions.
- Update browser acceptance fixtures only as needed for Phase 1 behavior.

## Constraints

- Do not expose host paths, cache paths, session ids, transcript paths, or raw
  backend records in UI state or tests.
- Do not add Phase 2 compact summary changes or Phase 3 Codex parser coverage.
- Do not bypass Dockview through raw panel/group handles; keep dashboard-owned
  adapter and placement policy as the visible layout authority.
- Do not remove fallback polling or stream teardown guards.

## Out of scope

- Compact transcript one-line summary quality.
- Codex native prompt/interruption/MCP/patch transcript parsing.
- Exec job Activity Console integration.
- Native filesystem watcher mode beyond the current polling fallback.
- Agent control actions from the dashboard Activity Console.
