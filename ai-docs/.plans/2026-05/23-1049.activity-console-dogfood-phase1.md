## Constraints
- Activity open must continue through command dispatch: the badge uses `data-command-id="workbench.openActivity"` and dispatches from toolbar actions in `ws-dashboard/frontend/src/App.tsx#L2107-L2121` and `ws-dashboard/frontend/src/App.tsx#L2199-L2214`.
- Close semantics are reversible and browser-only for Activity: `closeActivityPane` only updates local open/order state in `ws-dashboard/frontend/src/App.tsx#L1944-L1955`, while the registry marks no confirmation in `ws-dashboard/frontend/src/workbench/surfaceRegistry.ts#L99-L108`.
- Activity Console must stay read-only/source-neutral: the mental model binds it to route-backed feed/transcript state and forbids daemon acknowledgement/control authority in `ai-docs/mental-model/ws-web-dashboard.md#L117-L123`.
- Live updates refresh selected transcripts through feed-level invalidation only: `applyActivityConsoleEvent` returns `transcriptActivityId` without block streaming in `ws-dashboard/frontend/src/workRootActivity.ts#L247-L268`.
- Browser-level UI evidence is required for visible dashboard changes: `ai-docs/spec/ws-web-dashboard/index.md#L468-L528` and `ai-docs/mental-model/ws-web-dashboard.md#L12-L18` both say pure TypeScript/build evidence is insufficient.

## Risk Signals
- `ws-dashboard/frontend/src/workbench/policy.ts#L174-L213` — Possible contract risk: current code and comments hard-code WorkRoot Activity as a group-1 exception, directly opposite Phase 1's support-split placement contract.
- `ws-dashboard/frontend/src/App.tsx#L2435-L2456` — Possible shortcut risk: even if policy returns group 2, `buildWorkbenchEditorGroups` still renders Activity only for `index === 0`, so visible Dockview placement may not match placement state.
- `ws-dashboard/frontend/src/App.tsx#L1916-L1942` — Possible reuse/state risk: opening Activity persists only `activityPaneOpenByRoot: true`; unlike file/terminal panes, no Activity pane-order/group state is stored for later rendering.
- `ws-dashboard/frontend/src/ActivityConsole.tsx#L213-L222` and `ws-dashboard/frontend/src/ActivityConsole.tsx#L447-L461` — Possible test/UX risk: replace refresh clears prior transcript and unmounts the scroll container into a loading placeholder, matching the snap-back/unmount behavior the brief calls out.
- `ws-dashboard/frontend/src/workRootActivity.ts#L501-L515` and `ws-dashboard/frontend/src/ActivityConsole.tsx#L462-L475` — Possible load-loop risk: existing load-more triggers near the bottom; adding tail-follow scroll-to-bottom while `hasMore` is true may repeatedly invoke load-more unless the new policy distinguishes tail-follow from pagination triggering.
- `ws-dashboard/crates/daemon/src/work_root_activity.rs#L901-L912` and `ws-dashboard/crates/daemon/src/work_root_activity.rs#L1033-L1049` — Possible contract-limit risk: backend pagination starts at offset 0, so a frontend-only tail-follow repair may still initially show the top page when transcripts exceed the first page.
- `ws-dashboard/frontend/e2e/dashboard-acceptance.spec.ts#L500-L526` and `ws-dashboard/frontend/e2e/dashboard-acceptance.spec.ts#L900-L905` — Possible test drift risk: browser acceptance currently asserts Activity opens in group 1 in two places.

## Opinion
- The placement repair likely touches both policy tests and App rendering state; changing only `policy.ts` would leave visible behavior stale.
- Scroll repair has enough existing pure helpers/tests to add focused policy coverage without DOM-heavy tests, but browser evidence is still required for snap-back and Dockview rerender behavior.
- Phase 1 cannot honestly claim newest-tail pagination unless the backend contract changes; the surveyed backend currently exposes forward offset pagination only.
