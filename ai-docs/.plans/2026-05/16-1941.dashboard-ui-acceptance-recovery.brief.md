# Brief: 260516-bug-ws-web-dashboard-ui-acceptance-recovery

## Intent

Recover the dashboard workRoot UI so the current workRoot IO implementation can
be judged from the daemon-served browser flow, not from API and helper tests
alone. The result must make terminal tabs selectable, remove mock or placeholder
terminal surfaces from the real opened-workRoot flow, restore real terminal
emulator behavior, make the file explorer conventional, and leave browser-level
evidence that the known failures were checked.

## Scope Boundary

Implement all phases of
`ai-docs/tickets/ready/260516-bug-ws-web-dashboard-ui-acceptance-recovery.md`
as one cohesive recovery slice:

- Phase 1: browser-level acceptance gate.
- Phase 2: terminal tab selection and non-mock initial state.
- Phase 3: browser terminal rendering, input, and sizing.
- Phase 4: conventional read-only file explorer affordance.
- Phase 5: Sonnet frontend design verification and bounded tweak pass after
  primary implementation and before normal review.
- Phase 6: daemon-served product-flow dogfood and merge-decision evidence.

Do not implement a full filesystem picker, agent presets, write-back editing,
broad file-manager verbs, named-agent controls, or unrelated visual redesign.

## Caller-Visible Contract

Dashboard frontend UI work that changes visible browser behavior has a
browser-level acceptance gate against the daemon-served production frontend
after owner pairing. Pure TypeScript tests, Vite build, route tests, curl
evidence, and fixture-only dogfood are insufficient to close this UI-facing
work.

Opening a real workRoot through the current raw path-input opener is acceptable
for this ticket, but the production browser flow must not show mock workspaces
or placeholder terminals after the real workRoot is opened. Prefer an explicit
empty workbench with a clear `New Terminal` affordance over automatically
creating a daemon terminal when the workRoot opens.

Every visible terminal tab label is selectable and focuses the corresponding
terminal pane. Terminal input and output stay isolated by session.

The browser terminal behaves as a real emulator surface for daemon-owned PTY
sessions: PTY output renders ANSI colors/control behavior through the emulator,
keyboard input comes from the focused terminal surface, output returns to that
same surface, and the terminal fills the available pane.

The workRoot file explorer presents familiar read-only tree/list affordances:
directories and files are visibly distinct, expansion and refresh are
recognizable, selected workRoot identity stays visible, and previewable file
opening remains read-only.

Dogfood evidence must start from the daemon-served browser frontend after owner
pairing and record daemon command, browser automation or manual steps, viewport
sizes, terminal commands used for color/control verification, generated
screenshot or trace paths when present, and pass/fail checks for each known
reported failure.

## Implementation Strategy Decisions

Use a persistent browser automation path if feasible, preferably Playwright or
an equivalent project-local browser gate. The gate should expose a runnable
project command such as `npm run test:browser`, `npm run test:e2e`, or the
closest local equivalent, and it must exercise the daemon-served production
frontend rather than a Vite-only component or dev-server check.

Start by capturing fail-first evidence for at least the reported behavior set,
or record why fail-first evidence cannot be captured on this branch.

First verify whether the current terminal pane actually uses xterm.js
correctly. If not, rebuild the pane around the established xterm package
pattern such as `@xterm/xterm` plus fit-addon or a project-local equivalent.
PTY output must flow into the emulator (`terminal.write(...)` or equivalent),
and input must flow from the emulator data callback (`onData(...)` or
equivalent) to the daemon input route.

Terminal layout work is in scope. Ensure the terminal container, xterm viewport,
and workbench body use stable flex/grid sizing with constraints such as
`min-height: 0`, `height: 100%`, or equivalent so the terminal fills the pane.
Resize forwarding to the daemon must remain bounded rather than continuously
rewriting logical PTY size during visual drag.

After the primary implementation for Phases 1-4, register a ws named agent on a
Sonnet model for one frontend design verification and bounded autonomous tweak
pass before normal correctness/fit/test review. That pass must inspect the
daemon-served browser flow using the browser gate, make scoped UI tweaks when
needed, commit one logical checkpoint, and report evidence and remaining design
concerns.

## Rejected Alternatives

- Do not treat API/curl dogfood as sufficient UI evidence.
- Do not hide the initial-state issue by auto-creating terminal sessions on
  workRoot open.
- Do not render terminal output as raw text nodes or a separate prompt surface.
- Do not replace the recovery with a broad root picker, full file manager,
  write-back editor, agent preset surface, or unrelated redesign.
- Do not commit bulky generated screenshots or traces by default; record paths
  and observations in the dogfood artifact unless a later convention requires
  committing them.

## Approach

- Add or wire a daemon-served browser acceptance command and evidence path.
- Fix terminal workbench tab selection and initial workbench state.
- Wire terminal output/input through the actual emulator and make the terminal
  fill the pane.
- Revise the file explorer toward conventional read-only tree/list interaction.
- Run the Sonnet design verification/tweak pass and commit its bounded changes.
- Run final browser dogfood and persist the evidence artifact.

## Constraints

- Preserve daemon-owned terminal lifecycle: create/list/output/input/resize/
  close remain daemon APIs, and explicit close terminates the session.
- Preserve opened workRoot resource identity and host-path privacy. Browser
  routes and raw paths must not become authoritative over resource ids.
- Preserve token-free paired browser navigation and owner authentication.
- Preserve terminal close-as-terminate behavior.
- Preserve dark-first dashboard visual-system direction and existing workbench
  layout constraints.
- Keep screenshots/traces out of commits unless they are intentionally small
  and necessary for review; otherwise commit textual evidence with paths.

## Out of Scope

- Full filesystem picker or browser.
- Broad file-manager operations: delete, rename, move, copy, chmod, recursive
  deletion.
- Write-back editor behavior.
- Agent presets, named-agent controls, or ws runtime control surfaces.
- Multi-user, public deployment, or authentication redesign.
