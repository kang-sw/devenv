# Plan: Pi adapter: push every child report into the lead session and retire `ws-agent-wait` — Phase 1: Push channel + `ws-agent-wait` removal

## Relevant Ticket Contract

- Six push families (`ws-agent-report`, `ws-agent-settled`, `ws-agent-question`, `ws-agent-approval`, `ws-agent-advisory`, `ws-agent-orphaned`), each a `pi.sendMessage(..., {deliverAs, triggerTurn:true})` custom message with `display:true` and `details` carrying `agent_id` + payload + a status line, issued by whichever process owns the child (`isLeadOrFork` gate).
- Fan-in status line `N of M ... still running`: M = registry members that are running/idle-but-not-settled-since-last-prompt and not thread-bound (excludes dormant/stopped/exited/thread-bound/explore); N = the M subset that is running and has not yet sent `final`/`question` this turn (`terminalThisTurn`). `running` is set at prompt-issue time via a new `promptAgent` wrapper over every `client.prompt` call site, cleared on settle/stop/exit/spawn-failure.
- `record.threadBound` (new): set by `ask.ts` in `ensureRespondent`/`openThread` (every open/reopen) and `handleForkRaisedQuestion` (question registration); cleared only on thread close (`/done`, fork final, `ws-resolve`). While set: no settle/advisory push, excluded from N and M.
- `record.reportLog` (new, bounded) replaces `pendingReports` as the input to `fork.ts`'s `isIdleWithoutFinal`, filtered to entries since `record.lastLeadPromptAt` (a nudge does not update that timestamp); also feeds `ws-agent-list`'s last-report time.
- Liveness probe: `client.getState()` on every registry transition and on a ~30s timer while N>0, plus any in-flight-request rejection, treated as "dead" → push `ws-agent-settled` reason `exited`.
- `ws-agent-wait` is deleted outright (not deprecated), along with `pendingReports`, `idlePending`, `settleWaiters`'s use on `RpcAgentRecord`, and the approval-pending wake/`waiterWoken` plumbing. `ws-agent-list` stays and gains last-report time; `ws-agent-send`/`ws-agent-stop`/`ws-agent-transcript` are unchanged in tool shape.
- Shutdown sidecar: `session_shutdown` writes `<leadSessionFile>.ws-agents.json` (non-dormant records only) before `stopAll()`; `session_start` (lead-or-fork, same session file) reads+deletes it, re-registers each as a dormant record with full resume fields, re-arms role wiring, and pushes one `ws-agent-orphaned`. New file `agents-plugin-pi/src/agent-sidecar.ts` holds the pure `serializeOrphans`/`parseOrphans`.
- Registry exposed to factory scope via a `session_start`-filled ref (the existing `wsBlockRef` pattern in `index.ts`) for Phase 2 — Phase 1 only wires the ref, Phase 2 consumes it.
- Guide text (`pi-lead-guide.md`), the `260904` fork-raised notice (`ask.ts`), and tool descriptions naming `ws-agent-wait` are rewritten to the push model.
- Golden rule unchanged: `agents-plugin-tool/` (Go) and `agents-plugin/skills/` are never touched.

## Out of Scope

- Phase 2 (goal-loop yield to running children) — only the `session_start`-filled registry ref is prepared here, no `goal-loop.ts` change.
- `ai-docs/spec/pi-adapter-runtime.md` / `ai-docs/mental-model/plugin-runtime.md` anchor rewrites named under the ticket's "Spec Impact" section — the Phase 1 task text itself never names touching the spec file (only `pi-lead-guide.md`/tool descriptions/`ask.ts` notice); treated as a follow-up docs pass, not part of this phase's code change.
- The always-visible running-agent list (`260905-feat-ws-pi-live-agent-widget`).
- Keeping children alive across `/reload`/session switch — sidecar + `ws-agent-orphaned` is the recovery path, not live persistence.
- Live TUI/tmux verification items (spawn-three-workers turn grouping, mid-turn approval interrupt latency, fork-raised question routing, kill-process liveness, `/reload`/`/new` sidecar behavior) — all owner-run manual checks, not offline-verifiable.

Change `record.onFinalReport`'s type to `(record, message) => boolean | void`, returning `true` when the hook fully handled the report (suppress the `ws-agent-report` push). `armFinalReportHook` `#L1032-1039` wraps `handleRespondentFinalReport`; change `handleRespondentFinalReport` `#L1007-1025` to return `true` for the `"lead-ask"` branch (both the overlay-open and overlay-closed sub-paths — it always calls `closeThreadOnDone`/`overlay.closeWithSummary` which end in the injection) and `false` for `"fork-raised"` (the real task completion — its own final report is the signal the lead is supposed to see, per the ticket's "a `fork-raised` final ... is not consumed ... the push then proceeds").
