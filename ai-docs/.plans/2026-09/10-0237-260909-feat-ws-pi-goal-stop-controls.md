# Plan: 260909-feat-ws-pi-goal-stop-controls — Phase 1: Add explicit goal stop aliases with race-safe disarming

## Relevant Ticket Contract

- `/goal stop`, `/goal clear`, and `/goal reset` are three exact aliases for one idempotent stop operation; each clears active goal state, reports that automatic continuation stopped, and leaves ordinary `/goal <text>` entry unchanged.
- Stopping must not abort the current lead response, terminate children, delete history, or suppress child-report delivery. It must cancel automatic reminder/rearm work that has not started, and a stale async callback must check current armed state before sending another automatic turn.
- A later explicit goal must rearm normally. Recovery, compaction, and a replacement session must not revive a stopped goal or a stale queued reminder.
- The phase verification boundary includes all aliases, ordinary goal text, repeated stop, active lead response, running child, pending reminder, compaction, stale callback after stop/new goal, recovery, and explicit rearm. The owner separately performs the live child-report acceptance check.

## Out of Scope

- No change to model-invoked `goal-achieved`, `goal-blocked`, or the non-terminal `goal-compact-and-continue` contract beyond routing owner stop through their established disarming/cancellation lifecycle.
- No interruption or teardown of current lead work, child agents, held child reports, conversation history, Pi compaction, or the shared Go ws-mcp runtime.
- Do not weaken pending-reminder suppression to timer cancellation alone. Any solution must also cancel or suppress a reminder Pi has accepted but has not started; it must preserve unrelated owner and child-report queue entries.
- Later ticket phases, spec/ticket/shared-resource changes, model calls, merge, and push are excluded.

## Codebase Findings

### Adapter mechanisms and all reminder origins

- `agents-plugin-pi/src/goal-loop.ts` owns `GoalLoopState`, `armGoal`, `disarmGoal`, and `registerGoalLoop`. The registered `/goal` handler trims input, rejects busy replacement goals, cancels the settle timer, and sends the announcement. Stop aliases must branch before the busy replacement check.
- `armSettleTimer`, `onSettleTimerFire`, `dispatchSettleDecision`, and `fireReminder` form one production reminder path with injected `scheduleTimer`/`clearTimer`. Ordinary settle, lever-originated `pendingRearm`, and `settleSwallowedWhileCompacting` replay all reach `fireReminder`; compaction carry and failure prose are consumed there. Its current `sendUserMessage(..., { deliverAs: "followUp" })` transfers ownership before execution is assured.
- `releaseAfterCompaction` is reached both by deferred `session_compact`/`session_compact_failed` handlers and by the lever's `onComplete`/`onError` callbacks. Old completions must release the independent compaction hold and permit child reports, but must never attach old carry/failure/rearm intent to a newly armed goal.
- `agents-plugin-pi/src/spawner.ts` owns `reserveWakeStart`, `clearWakeStart`, `leadWakeStartPendingRef`, and `heldPushQueue`. The one shared wake reservation serves both reminders and child reports. `fireReminder` installs recovery that prioritizes held pushes, otherwise retries the goal. Stopping a goal cannot indiscriminately clear this shared reservation or discard its child-delivery recovery. Goal-generation checks must fence only its goal branch; timer-instance checks must stop an obsolete callback from clearing a newer timer/reservation.
- `GoalLoopShutdownHandle.resetCompactionStateForShutdown` and `agents-plugin-pi/src/index.ts`'s shutdown handler already perform teardown. A future implementation must invalidate old goal callbacks as well as clear timers; ordinary owner stop must not reuse teardown that releases ongoing compaction or resets child-delivery state.
- `agents-plugin-pi/test/goal-loop.test.ts` uses registered commands/events and the real scheduler seam; `agents-plugin-pi/test/push-wake.test.ts` covers independent wake/report delivery. Its fake `sendUserMessage` alone cannot prove suppression after actual Pi queue acceptance.

### Installed Pi 0.84.4: supported interfaces and execution boundaries

All following host paths are relative to `agents-plugin-pi/node_modules/@earendil-works/pi-coding-agent/`; this installed package's `package.json` reports version `0.84.4`. No dependency or host source was edited.

- `dist/core/extensions/types.d.ts:971` exposes `ExtensionAPI.sendMessage` and `sendUserMessage` as void-returning operations. User-message options contain delivery mode and prompt expansion only; there is no cancellation signal, message handle, selective queue removal, or atomic idle-only user-prompt operation. `ExtensionContext` exposes no system-prompt setter. `ContextEventResult` changes messages only; `BeforeAgentStartEventResult` changes system prompt/adds a custom message but cannot cancel a run.
- `dist/core/agent-session.js:821`, `AgentSession.prompt`: extension commands run immediately even during streaming, then input interception is awaited before the streaming branch at line 859. `sendUserMessage` at line 1161 calls this method with source `extension`, including when prompt expansion is false. The registered adapter `input` handler means the asynchronous interception path is reachable in normal lead sessions, even when its lead-role branch immediately returns undefined.
- `dist/core/extensions/runner.js:974`, `ExtensionRunner.emitInput`: every handler result is awaited, even a synchronous return. A synchronous armed/idle check inside an input handler cannot atomically cover subsequent admission: another microtask can stop the goal and start unrelated work before `prompt` resumes. An additional asynchronous extension only enlarges this window. The hook runs at admission, never when an already accepted follow-up is consumed.
- `dist/core/agent-session.js:1062`, `_queueFollowUp`: appends to `_followUpMessages` and calls `agent.followUp`; the host now owns the reminder. `clearQueue` at line 1195 clears all steering/follow-up entries. Its interface is not exported to extensions, and its semantics would destroy unrelated owner/child input even if reached privately. Queue entries have no adapter ownership handles.
- `dist/core/agent-session.js:881` through `_runAgentPrompt` at line 772: idle user-prompt preflight may await auth, compaction, and `emitBeforeAgentStart` before the agent actually starts. Omitting `deliverAs` avoids one busy-queue branch but cannot prevent an old idle preflight from starting after stop. No cancellable preflight is exposed. At `dist/core/extensions/runner.js:881`, `emitBeforeAgentStart` catches handler errors and continues; throwing there is not a cancellation primitive.
- `dist/core/agent-session.js:1099`, `sendCustomMessage`, gives a real synchronous alternative: a fresh idle check followed without an intervening await by `sendMessage(..., { triggerTurn: true })` calls `_runAgentPrompt`, then the installed `node_modules/@earendil-works/pi-agent-core/dist/agent.js` methods `prompt` (line 226), `runPromptMessages`, and `runWithLifecycle` (line 325). They set session run-active state, `activeRun`, and `isStreaming`, and enter `runAgentLoop`'s `agent_start` emission before returning across an asynchronous boundary. Thus an adapter-owned reminder could remain cancellable until this dispatch starts, without entering a host queue. `dist/core/messages.js`, `convertToLlm`, converts custom content to user-role text. This is an actual mechanism, not an invented API, but it fails the bootstrap contract below.

### Why synchronous custom dispatch is not an acceptable replacement

- `agents-plugin-pi/src/lead-bootstrap.ts`, `registerLeadBootstrap`'s `before_agent_start` handler, composes the ws manual/guide/live skills from the current base prompt for every lead run. `ai-docs/spec/pi-adapter-runtime.md` anchor `260905-pi-lead-bootstrap-system-prompt` explicitly requires this per-run composition, including idle wake delivery; it prohibits starting an idle push run directly with a custom message. Goal-loop anchor `260904-pi-goal-loop-arming-settled-levers` also specifies follow-up user-turn delivery.
- `AgentSession.sendCustomMessage` bypasses input, auth/compaction preflight, and `emitBeforeAgentStart`. The previous `agent.state.systemPrompt` can retain ws text for the first response, which can make a shallow fixture falsely appear to work. However, `_runAgentPrompt`'s `finally` at line 781 clears `_systemPromptOverride`. `_installAgentNextTurnRefresh` at line 286 later sets the next response's system prompt to `_systemPromptOverride ?? _baseSystemPrompt`; a custom-started tool/continuation run therefore loses the ws block. `setActiveToolsByName` at line 659 likewise rebuilds `agent.state.systemPrompt` from that cleared override/base while idle, so even the first custom response need not retain ws text.
- Reusing a cached ws block or putting it into reminder/context text cannot preserve system-prompt precedence, the chained hooks from other extensions, or live tool/skill composition. Calling `before_agent_start` handlers privately, writing provider-specific payloads, monkey-patching host internals, or duplicating Pi preflight in the adapter would change canonical bootstrap behavior. These are rejected bypasses, not presentation choices.
- Context filtering after dequeue may remove reminder text, but does not suppress the automatic turn itself; converting it to a placeholder wake has the same defect. Starting and then aborting the run violates the no-interruption requirement. No blanket queue clear, timer-only scope reduction, or asynchronous input-hook armed check closes the full contract.

## Implementation Plan

Implementation is blocked on a supported host admission capability. The following is a dependency order, not permission to implement a narrowed adapter subset.

1. Establish an upstream Pi user-prompt contract that preserves the full existing input and `before_agent_start` lifecycle while allowing cancellation until actual execution. Preferred contract: ownership-specific admission identity/cancellation covering asynchronous preflight, private queue residence, and the final consume/start boundary. Cancellation must be idempotent, report already-started work without aborting it, and leave unrelated queue entries in order. An alternative is cancellable, atomic idle-only admission: pending reminders remain adapter-owned; after all preflight awaits the host atomically rechecks cancellation and idleness and either starts or returns a non-started result without enqueueing. Merely returning a promise or rejecting busy input at the initial check is insufficient. These are proposed host semantics, not API names available in 0.84.4.
2. Once the capability is released and its supported dependency target is selected, update this plan with the actual public signature and verified host lifecycle tests before touching product source. Neither shared Go changes nor private host patches solve this adapter/host boundary. Do not preemptively change package dependencies or canonical bootstrap to unblock the ticket.
3. In `agents-plugin-pi/src/goal-loop.ts`, extend `registerGoalLoop` through its existing lifecycle: exact trimmed stop/clear/reset aliases before the idle-only replacement check; a common goal-only invalidation operation for stop, replacement, terminal levers, force-stop, and shutdown; status/help/completion updates. Introduce goal-generation and scheduled-work identity fencing so stale timer/recovery/compaction callbacks cannot mutate a stopped or replacement goal. Preserve unrelated running work and report delivery.
4. In the same file, route `fireReminder` through the decided host admission seam and retain the existing single settle evaluation path for all origins. Define successful-start versus cancelled/non-started bookkeeping for carry, failure prose, and runaway streak using the actual host result. Owner stop cancels every old goal-owned admission, including preflight and queued-but-not-executing reminders. Explicit goal announcement remains ordinary owner entry; old announcement settlement must not rearm a stopped generation.
5. Keep `releaseAfterCompaction`'s hold release/report flush independent of goal-generation validity. Fence its deferred goal effects at capture and use, including manual/automatic/lever compaction success and failure and duplicate completion routes. In `spawner.ts`'s wake lifecycle, preserve held-push recovery while making any needed reservation-identity checks specific to the obsolete callback; do not clear the shared child-report queue or child registry on goal stop. Shutdown invalidates the old loop before its remaining callbacks can run.
6. Add production-seam adapter and host lifecycle verification below. No source implementation, dependency upgrade, or phase-result claim is authorized by this blocked research plan alone.
