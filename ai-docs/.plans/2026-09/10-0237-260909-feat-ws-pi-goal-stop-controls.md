# Plan: Stop Pi goal reinjection without interrupting current work — Phase 1: Add explicit goal stop aliases with race-safe disarming

## Relevant Ticket Contract
- `/goal stop`, `/goal clear`, and `/goal reset` are three exact aliases for one idempotent stop operation; each clears active goal state, reports that automatic continuation stopped, and leaves ordinary `/goal <text>` entry unchanged.
- Stopping must not abort the current lead response, terminate children, delete history, or suppress child-report delivery. It must cancel automatic reminder/rearm work that has not started, and a stale async callback must check current armed state before sending another automatic turn.
- A later explicit goal must rearm normally. Recovery, compaction, and a replacement session must not revive a stopped goal or a stale queued reminder.
- The phase verification boundary includes all aliases, ordinary goal text, repeated stop, active lead response, running child, pending reminder, compaction, stale callback after stop/new goal, recovery, and explicit rearm. The owner separately performs the live child-report acceptance check.

## Out of Scope
- No change to model-invoked `goal-achieved`, `goal-blocked`, or the non-terminal `goal-compact-and-continue` contract beyond routing owner stop through their established disarming/cancellation lifecycle.
- No interruption or teardown of current lead work, child agents, held child reports, conversation history, Pi compaction, or the shared Go ws-mcp runtime.
- Do not weaken pending-reminder suppression to timer cancellation alone. Any solution must also cancel or suppress a reminder Pi has accepted but has not started; it must preserve unrelated owner and child-report queue entries.
- Later ticket phases, spec/ticket/shared-resource changes, model calls, merge, and push are excluded.

## Codebase Findings
- `agents-plugin-pi/src/goal-loop.ts#L266-L287` — `GoalLoopState`, `armGoal`, and `disarmGoal` already provide the single active-goal lifecycle; the missing behavior is owner-command recognition and stop-specific lifecycle cleanup, not a second goal state.
- `agents-plugin-pi/src/goal-loop.ts#L401-L424` and `#L512-L536` — the production seam is the one pending settle timer plus injected `scheduleTimer`/`clearTimer`; production uses real `setTimeout`/`clearTimeout`, and tests use the same seam. This is the genuine gap before source work: `/goal` only treats every nonempty argument as replacement text, so it cannot call the existing cancellation seam for the three reserved words.
- `agents-plugin-pi/src/goal-loop.ts#L647-L729` — `onSettleTimerFire` rechecks compaction, idleness, child state, wake ownership, and then `state.active`/`state.goal` before lever-originated delivery. Stop must also fence every remaining rearm origin (`pendingRearm`, swallowed settle, carry, and wake-retry callback) so no stale callback can dispatch after stop or after a replacement goal is armed.
- `agents-plugin-pi/src/goal-loop.ts#L730-L846` — `/goal` is a declarative Pi command; `agent_settled` owns delayed reminder arming and `agent_start` owns timer/wake cancellation. The stop branch must be accepted while work is active without calling the existing idle-only replacement-goal rejection, otherwise it cannot meet the non-interruption requirement.
- `agents-plugin-pi/src/goal-loop.ts#L848-L994` and `agents-plugin-pi/src/index.ts#L698-L739` — compaction completion is deferred with `setImmediate`, and shutdown already calls `resetCompactionStateForShutdown`; the stop path must make these deferred paths inert without weakening shutdown cleanup or compaction observation.
- `agents-plugin-pi/src/spawner.ts#L1510-L1640` and `agents-plugin-pi/test/push-wake.test.ts#L138-L184` — child reports use the independent held-push/wake channel. It must continue to deliver after stop; stopping a goal may cancel only goal-owned timer/rearm state, never `heldPushQueue` or child registry state.
- `agents-plugin-pi/test/goal-loop.test.ts#L574-L620` and `#L1354-L1475` — the existing fake Pi and fake clock execute `registerGoalLoop`'s production registration paths and can prove cancellation by observed `clearTimer` calls and by manually firing captured callbacks. Existing coverage handles terminal levers, replacement goals, and shutdown but has no owner stop-alias matrix.
- `agents-plugin-pi/node_modules/@earendil-works/pi-coding-agent/dist/core/agent-session.js#L859-L871`, `#L1060-L1073`, and `#L1191-L1214` — a streaming `sendUserMessage(..., { deliverAs: "followUp" })` is accepted into Pi's private follow-up queue, then into the agent queue. Core has only all-or-nothing `clearQueue()`, which drops every steering and follow-up message; it cannot preserve unrelated owner input or child reports.
- `agents-plugin-pi/node_modules/@earendil-works/pi-coding-agent/dist/core/extensions/types.d.ts#L906-L983` and `#L1179-L1186` — `ExtensionAPI.sendUserMessage` returns `void` and exposes no queue inspection, message handle, `clearQueue`, or selective cancellation. The adapter cannot observe whether a specific automatic reminder is accepted, pending, or later dequeued.
- `agents-plugin-pi/node_modules/@earendil-works/pi-coding-agent/dist/core/agent-session.js#L826-L852`, `#L1161-L1188`, and `agents-plugin-pi/node_modules/@earendil-works/pi-coding-agent/dist/core/extensions/types.d.ts#L654-L677` — the extension `input` hook runs before a message is queued, including extension-originated input; it has no dequeue/delivery interception. `/goal stop` commands run immediately before input processing while streaming, so they can race an already accepted follow-up but cannot retract it through that hook.

## Implementation Plan
- Escalate to research before execution. Decide the supported Pi seam for identifying and selectively cancelling an already accepted extension-originated follow-up (or for intercepting it at dequeue), without clearing unrelated steering/follow-up entries. Then specify how the adapter retains timer cancellation, generation fencing, exact aliases, busy-stop behavior, and independent child-report delivery against that seam.

## Verification Plan
- After the queue-cancellation seam is decided, run `cd agents-plugin-pi && env -u WS_PI_SPAWN_ROLE -u WS_PI_EXPLORE_MODE node --test test/goal-loop.test.ts test/push-wake.test.ts`, then the package's full `npm test`; read complete output.
- Add the production-seam command matrix through registered `/goal`: exact case-sensitive `stop`, `clear`, and `reset` each disarm and notify; repeated stop with no goal is harmless; whitespace-trimmed aliases follow the same branch; `stopping`, `reset plan`, and other ordinary text remain replacement goals; empty input retains usage/help that names the aliases.
- Add active-work preservation cases: issue stop while `ctx.isIdle()` is false and prove it neither calls an abort/compact path nor rejects as busy; stop while a child is running and prove the child predicate/report channel remains live, then its report settles normally with no goal reminder.
- Add timer, host-queue, and stale-callback cases using the existing fake clock plus the decided real Pi queue seam: stop with a pending settle timer calls `clearTimer`; stop after a reminder has been accepted into Pi's follow-up queue removes or suppresses that exact reminder without removing unrelated owner/child entries; firing a previously captured callback produces no automatic send. Stop followed by `/goal <new goal>` cannot deliver the old reminder, carry, failure text, or advance the old runaway streak, while a fresh settle delivers only the new goal's reminder.
- Add compaction/rearm race cases: stop while `pendingRearm`, swallowed-settle, or deferred `session_compact`/`session_compact_failed` release is outstanding; run the deferred callback and any timer and prove no goal reminder/rearm occurs, no status remains, and compaction/push cleanup remains balanced. Verify a stopped carry-forward payload is never emitted later.
- Add recovery boundary cases: invoke the shutdown handle/session-shutdown cleanup with a stopped goal and a pending callback, construct/register the replacement loop, then prove neither old callback nor replacement-session settle resurrects it; explicitly entering a new goal after that recovery arms and re-injects normally.
- Add independent-child-report preservation coverage in `agents-plugin-pi/test/push-wake.test.ts`: after stop, a held/settled child report still follows its existing delivery/ordering rules, and goal stopping neither clears `heldPushQueue` nor cancels its wake recovery.
- Owner live check (separate from automated tests): in Pi, arm a goal, start a child, issue `/goal stop` while the child runs, wait for the child report, and confirm the report arrives and no automatic goal continuation follows; then enter a new explicit `/goal <text>` and confirm normal rearming.

## Escalations
- Confidence: medium.
- Reason: the existing real timer/callback seam cancels work before `sendUserMessage` accepts it, but cannot satisfy the ticket's pending-reminder requirement after Pi has accepted a `followUp`. Pi core's only discovered retraction method is all-queue `clearQueue()`, and its extension API exports neither that method nor a selective queue handle; using it would drop unrelated owner/child messages and violate the contract.
- Research should decide: whether Pi has a supported selective extension-message cancellation/dequeue interception seam outside the installed public type surface; if not, the minimal host API contract for an opaque tagged message handle or selective cancellation that preserves unrelated queue entries, and the adapter test harness that proves acceptance-to-stop suppression.
