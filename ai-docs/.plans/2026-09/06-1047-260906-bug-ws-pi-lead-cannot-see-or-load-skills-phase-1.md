# Plan: Pi lead cannot see or self-load ws skills because removing native read/bash drops Pi's skills block from the system prompt — Phase 1: ws-skill tool and lead skills block

## Relevant Ticket Contract

- **Skill source of truth**: `pi.getCommands()`, not a ws-tree scan. Its `SlashCommandInfo[]` entries with `source: "skill"` carry `name: "skill:<n>"`, `description`, `sourceInfo.path` (the SKILL.md path). Both the block and `ws-skill` resolve against this same list — ws skills and any other installed skill alike.
- **`ws-skill(name, args?)` tool** (lead + fork): looks `name` up in that list, reads the SKILL.md at `sourceInfo.path`, returns the body (frontmatter stripped) with `User: <args>` appended when `args` is given. Unknown name returns the available names. A `disable-model-invocation: true` skill is still loadable by name (Pi's own `/skill:<name>` loads it too).
- **Adapter-rendered `<available_skills>` block**: third ordered item of the ws system-prompt block (after the manual snapshot, after the Pi lead guide), same shape as Pi's own renderer (name/description/location per entry) but with a preamble telling the model to use `ws-skill <name>`, not `read`, and without Pi's "resolve relative paths against the skill directory" line. Skills with `disable-model-invocation: true` are excluded from the block. Frontmatter is read from `sourceInfo.path` at block-build time (session start), not cached at `pi.getCommands()` time.
- **No read/bash gate**: the block/tool are gated on role (`isLeadOrFork`) only — never on tool-set membership. This is explicit in the ticket because gating on active-tool presence, evaluated at the wrong point in `index.ts`'s `session_start` sequencing relative to the reshape, would silently reproduce the bug.
- **Constraints**: adapter-only, `agents-plugin-pi/`; ws skill text (`agents-plugin/skills/`) stays untouched; `agents-plugin-tool/` (Go) untouched. Skill list fetched once per session start; `ws-skill` re-reads the SKILL.md body on every call (edits picked up live, no restart). Missing/unreadable SKILL.md: the block silently skips that entry, `ws-skill` returns an error naming the path — neither path throws. Worker/explore get neither the tool nor the block (already excluded structurally — see Codebase Findings).
- **Phase 1 test list** (from the ticket): known-skill body w/ frontmatter stripped; `args` appended as `User: <args>`; unknown name lists available names; `disable-model-invocation:true` loadable by name but absent from block; block lists every `source:"skill"` entry (ws and non-ws) with name/description/location and skips an unreadable one; block present for lead/fork, absent for worker/explore, verified **on the post-reshape tool surface** via a test that drives `before_agent_start` "through the real `index.ts` ordering, not only the pure helper." Plus: amend three spec passages (Spec Impact) and add one `pi-lead-guide.md` verb-table row.
- **Live check** (owner-run, not part of this survey's automated verification): ask the lead to drain the ready queue without `/skill:...` and confirm it calls `ws-skill lead-drain-ready-queue`; arm `/goal` naming a skill and confirm each cycle starts with a `ws-skill` call.

## Out of Scope

- Any change to `agents-plugin/skills/*` prose or `agents-plugin-tool/` (Go) — constraint, not a phasing choice.
- Rejected directions already settled in the ticket: keeping native `read` on the lead; teaching the model to call `do-i-really-have-to-read-this-myself` on the SKILL.md path.
- The ticket has no further phases (`## Phases` contains only Phase 1) — nothing is being deferred.
- Live/manual owner-run verification (the two "Live check" bullets) — out of scope for the automated implementation/verification in this plan; call it out as a follow-up manual gate.

## Codebase Findings

**Pi runtime surface (verified against `agents-plugin-pi/node_modules/@earendil-works/pi-coding-agent`, not just the ticket's prose):**
- `dist/core/agent-session.js#L1982-2001` (`_bindExtensionCore`'s `getCommands`) — confirms the exact shape: `{ name: "skill:" + skill.name, description: skill.description, source: "skill", sourceInfo: skill.sourceInfo }`, from `this._resourceLoader.getSkills().skills`. `pi.getCommands()` (types.d.ts `ExtensionAPI.getCommands(): SlashCommandInfo[]`, index.d.ts confirms `SlashCommandInfo`/`SourceInfo` are both exported from the package root) is the exact call the ticket describes.
- `dist/core/slash-commands.d.ts` — `SlashCommandSource = "extension" | "prompt" | "skill"` (filter key), `SlashCommandInfo { name, description?, source, sourceInfo }`.
- `dist/core/source-info.js` / `.d.ts` — `SourceInfo.path` is the field carrying the SKILL.md path (confirmed via `createSyntheticSourceInfo`, used by `skills.js`'s `createSkillSourceInfo`).
- **Reusable component (not in the ticket text, found during survey): `parseFrontmatter`/`stripFrontmatter` are exported from the package root** (`dist/index.d.ts`/`dist/index.js`: `export { parseFrontmatter, stripFrontmatter } from "./utils/frontmatter.ts"`), along with the `SkillFrontmatter` type (`"disable-model-invocation"?: boolean`, `[key: string]: unknown`). `parseFrontmatter<T>(content) -> { frontmatter: T, body: string }` (`dist/utils/frontmatter.js`) does real YAML frontmatter parsing (`---\n...\n---` delimited, via the `yaml` package) and returns an already-`.trim()`ed body. **Use this instead of hand-rolling a regex frontmatter stripper** — it is the exact function Pi's own `/skill:<name>` expansion uses (`agent-session.js#L983-1007`, `_expandSkillCommand`) to get `disable-model-invocation` and the stripped body, so using it also guarantees byte-identical stripping behavior to Pi's own slash command.
- `dist/core/skills.js#L275-296` (`formatSkillsForPrompt`) — also exported from the package root, but its preamble/postamble text is hard-coded (not parameterized), and the ticket requires a *different* preamble (`ws-skill <name>`, no "resolve relative paths" line). Cannot be reused as-is; write a small dedicated formatter (~25 lines) mirroring its `<available_skills><skill><name>/<description>/<location></skill></available_skills>` XML shape and its private `escapeXml` (5 lines, not exported — must be reimplemented locally).
- `dist/core/skills.js#L208-266` (`loadSkillFromFile`) — confirms `disableModelInvocation: frontmatter["disable-model-invocation"] === true` is the exact predicate to reproduce.

**Adapter wiring (`agents-plugin-pi/src/`):**
- `src/index.ts#L189-212` — existing live-ref convention to mirror: `wsBlockRef`, `rpcRegistryRef` are `{ current: T | undefined }` objects filled inside `session_start`, read by declaratively-registered (factory-scope) handlers/tools. A new `skillEntriesRef: { current: SkillEntry[] }` follows the same shape.
- `src/index.ts#L399-415` — the manual-snapshot-gated block that calls `buildWsBlock(handle.manualSnapshotRef.current, guideText)`. `buildWsBlock`'s signature must grow a third parameter (skills block text) here.
- `src/index.ts#L417-441` — the three sequential role-gated `pi.setActiveTools(...)` calls (`computeLeadActiveTools`, `addForkToolIfLead`, `addAskToolsIfLead`), each re-reading `pi.getActiveTools()` between calls. A fourth tool (`ws-skill`) needs the same "add if lead-or-fork" treatment.
- `src/lead-bootstrap.ts#L45-47` (`buildWsBlock`) and `#L58-67` (`computeBeforeAgentStartResult`) — pure, already unit-tested (`test/lead-bootstrap.test.ts`) without a fake `ExtensionAPI`. `computeBeforeAgentStartResult`'s existing role gate (`isLeadOrFork`) is untouched — it already implements "no read/bash gate, role gate is the whole condition" for the block as a whole; nothing here needs to special-case the skills sub-block.
- `src/execute-gateway.ts#L287-319` — `LEAD_REMOVED_TOOL_NAMES`/`LEAD_ADDED_TOOL_NAMES`/`computeLeadActiveTools`: applies identically to **both** lead and fork (the outer `isLeadOrFork` gate in `index.ts` is what differentiates lead/fork from worker/explore, not anything inside this function). **Do not add `ws-skill` here** — this module's own test (`test/execute-gateway.test.ts#L165-170`, "an empty current list still ends up with exactly the 4 added tools") hard-codes the count, and folding an unrelated skills-tool name into the execute/approve gateway's own added-set would drift that module's stated responsibility (`computeLeadActiveTools`'s doc comment is scoped to "§8 lead `--tools` reshaping" for the execute/approve surface specifically).
- `src/fork.ts#L96` (`FORK_EXCLUDED_TOOL_NAMES = {ws-fork, ws-ask, ws-resolve}`) and `#L105-110` (`computeForkToolSurface`) — a fork's tools = lead's active tools at spawn time minus this exclusion set. `ws-skill` is not excluded, so a fork inherits it for free from the lead's already-reshaped surface at `ws-fork` spawn time; **no fork.ts change needed** for that path. But the fork process *also* independently re-runs `session_start` (role `"fork"` also satisfies `isLeadOrFork`), so it needs its own add-if-lead-or-fork step too (see Implementation Plan).
- `src/fork.ts#L125-130` (`addForkToolIfLead`) and `src/ask.ts#L442-449` (`addAskToolsIfLead`) — **both gate on `role !== undefined` (true top lead only)**, i.e. these two are *lead-only*, excluded even from fork (confirmed by `FORK_EXCLUDED_TOOL_NAMES` containing `ws-ask`/`ws-resolve`). This is a **different** gate shape than what `ws-skill` needs (lead **and** fork, matching `computeLeadActiveTools`'s applies-to-both semantics, not these two lead-only functions' semantics) — do not copy this gate verbatim; use `isLeadOrFork(role)` instead of `role !== undefined`.
- `src/process-role.ts#L58-60` — `isLeadOrFork(role)` is the existing pure predicate for "lead or fork" (already what `computeLeadActiveTools`'s outer `index.ts` gate uses); reuse it directly rather than reimplementing the `role !== undefined` check.
- `src/spawner.ts#L183-188` (`TOOL_GROUPS`) — worker/explore/execute-worker are spawned with a fixed, explicit `--tools` allowlist (never including `ws-skill` unless added there). This is *why* "worker/explore carry neither the tool nor the block" needs no extra exclusion code for the tool side: a newly, globally-registered tool never reaches a spawned child unless its `toolGroup` list names it.
- `src/skills-dir.ts` — unrelated to this ticket's `ws-skill`/block mechanism (it resolves the **directory** handed to Pi's own `resources_discover` skill loader, i.e. it is *upstream* of `pi.getCommands()`, not a second skill-discovery path). Do not conflate the two; no change needed here.
- `pi-lead-guide.md#L27-51` — the Verb-routing table; new row goes here, matching the existing row style (verb description | tool name + parenthetical usage notes).

**Risk signal (worth flagging, not blocking):** `computeLeadActiveTools`'s own doc comment (`execute-gateway.ts#L290-319`) explains the "auto-include footgun": on a fresh session (before any `setActiveTools` call), Pi auto-includes every newly-registered tool into the active set. This means a newly-registered `ws-skill` tool would *already* be present in `pi.getActiveTools()` for the lead by the time `index.ts`'s reshape runs, even before any explicit "add" step — the explicit add-if-missing step is still worth keeping (matches the codebase's existing defensive-idempotent pattern for `EXECUTE_TOOL_NAME`/etc., and is what actually excludes worker/explore since their tools never went through the global auto-include path in the first place, having been spawned with `--tools` from the start).

## Implementation Plan

**1. New module `agents-plugin-pi/src/lead-skills.ts`** (pure logic + thin IO glue, mirrors `fork.ts`'s/`ask.ts`'s split):
   - `export const WS_SKILL_TOOL_NAME = "ws-skill";`
   - `export interface SkillEntry { name: string; description: string; path: string; }`
   - `export function resolveSkillEntries(commands: readonly SlashCommandInfo[]): SkillEntry[]` — filter `c.source === "skill"`, map `name: c.name.slice("skill:".length)`, `description: c.description ?? ""`, `path: c.sourceInfo.path`. Import `SlashCommandInfo` from `@earendil-works/pi-coding-agent`.
   - `export type LoadedSkill = { ok: true; body: string; disableModelInvocation: boolean } | { ok: false; error: string };`
   - `export function loadSkillFile(path: string, readFile: (p: string) => string = (p) => readFileSync(p, "utf8")): LoadedSkill` — try/catch the read (never throw), then `parseFrontmatter<SkillFrontmatter>(raw)` (imported from `@earendil-works/pi-coding-agent`) to get `{ frontmatter, body }`; return `{ ok: true, body, disableModelInvocation: frontmatter["disable-model-invocation"] === true }`. On a read failure return `{ ok: false, error: "<message including path>" }` (constraint: "returns an error naming the path").
   - `export function buildSkillsBlock(entries: readonly SkillEntry[], loadFile: (path: string) => LoadedSkill): string` — for each entry call `loadFile`; skip entries where `!loaded.ok` or `loaded.disableModelInvocation`; if the visible set is empty return `""`; otherwise render a preamble ("Load a skill's file with `ws-skill <name>` ... never with `read`" — no "resolve relative paths" line) followed by one `<available_skills>` block with `<skill><name>/<description>/<location></skill>` per visible entry, XML-escaped (small local `escapeXml`, mirrors `skills.js`'s private one).
   - `export function computeWsSkillResult(name: string, args: string | undefined, entries: readonly SkillEntry[], loadFile: (path: string) => LoadedSkill): string` — find entry by exact `name` (search **all** entries, not just visible ones — a `disable-model-invocation:true` skill must still be loadable by name); if not found, return `Unknown skill "<name>". Available skills: <comma-joined ALL entry names, sorted>` (or `(none)` if empty) — this listing intentionally includes disabled-from-block names too, since they are still loadable by exact name; if found but `loadFile` fails, return `Error loading skill "<name>": <error>` (naming the path is inside `loadSkillFile`'s error string); otherwise return `args ? \`${body}\n\nUser: ${args}\` : body`.
   - `export function addSkillToolIfLeadOrFork(activeTools: readonly string[], role: SpawnRole | undefined): string[]` — `isLeadOrFork(role)` gate (import from `process-role.ts`), add-if-missing, same shape as `addForkToolIfLead`/`addAskToolsIfLead` but with the lead-**and**-fork gate instead of lead-only.
   - `export function registerWsSkillTool(pi: ExtensionAPI, entriesRef: { current: SkillEntry[] }): void` — registers `WS_SKILL_TOOL_NAME` (`name`, optional `args` string params), `execute()` calls `computeWsSkillResult(p.name, p.args, entriesRef.current, (path) => loadSkillFile(path))` and returns `{ content: [{ type: "text", text }] }` — never throws (matches constraint "neither throws").

**2. `src/lead-bootstrap.ts`**:
   - Extend `buildWsBlock(manualSnapshot: string, guideText: string, skillsBlock: string): string` to append `skillsBlock` as the third ordered section (join with `\n\n`, tolerate `""` producing a harmless extra blank line — same tolerance Pi's own `formatSkillsForPrompt`-into-`buildSystemPrompt` concatenation already has for an empty skills set).
   - Update `test/lead-bootstrap.test.ts`'s two `buildWsBlock` calls to pass a third arg (e.g. `"SKILLS-BLOCK-MARKER"` in the ordering test, asserting it comes after the guide text; `""` in the marker-prefix test) — signature change, not a behavior regression.

**3. `src/index.ts` wiring** (session_start, `isLeadOrFork(readSpawnRole(process.env))` already computed at L344/405/424 — reuse a single local `const role = readSpawnRole(process.env);` if convenient, otherwise follow the existing per-block re-read style):
   - New ref near `wsBlockRef`/`rpcRegistryRef` (~L192-197): `const skillEntriesRef: { current: SkillEntry[] } = { current: [] };`
   - Factory scope (next to `registerLeadBootstrap(pi, wsBlockRef);` at L251): `registerWsSkillTool(pi, skillEntriesRef);`
   - In `session_start`, immediately before the existing manual-snapshot-gated block (L405): when `isLeadOrFork(role)`, set `skillEntriesRef.current = resolveSkillEntries(pi.getCommands());`. This must run before `buildWsBlock` is called so the skills block reflects the current session's `pi.getCommands()` snapshot, and it is independent of `handle.manualSnapshotRef.current` (no bridge dependency) — but only actually observable through the tool/block once the surrounding role gate passes, matching the "no read/bash gate, role gate is the whole condition" requirement (this is a role-only condition, same as everything else here).
   - Inside the existing manual-snapshot-gated block (L405-415), change the `buildWsBlock(...)` call to pass `buildSkillsBlock(skillEntriesRef.current, (path) => loadSkillFile(path))` as the third argument.
   - In the active-tools reshape block (L424-440), add a fourth `pi.setActiveTools(addSkillToolIfLeadOrFork(pi.getActiveTools(), readSpawnRole(process.env)));` call alongside the existing three.
   - **Testability step for the ticket's explicit "drives before_agent_start through the real index.ts ordering, not only the pure helper" requirement**: rather than re-implementing this 4-step sequence a second time inside a test (which would only prove the test's own copy is self-consistent, not that `index.ts` itself is correct), extract the block-build-and-reshape sequence index.ts runs for a lead/fork session into one new pure function that `index.ts` itself calls, e.g. `computeSessionBootstrap(inputs): { wsBlock: string | undefined; activeTools: string[] }` in `lead-bootstrap.ts` (it already owns `buildWsBlock`/`computeBeforeAgentStartResult`, and its role is naturally "the ws system-prompt block + the session-start shape that produces it"), taking `{ role, manualSnapshot, guideText, skillEntries, loadSkillFile, currentActiveTools }` and internally: short-circuit `{ wsBlock: undefined, activeTools: [...currentActiveTools] }` when `!isLeadOrFork(role)`; otherwise build the skills block, `buildWsBlock` (if `manualSnapshot` present), and thread `currentActiveTools` through `computeLeadActiveTools` → `addForkToolIfLead` → `addAskToolsIfLead` → `addSkillToolIfLeadOrFork` in that order (this also incidentally simplifies `index.ts` from 3 separate `pi.setActiveTools`/`pi.getActiveTools()` round-trips to 1). `index.ts` then calls this once and applies its `{ wsBlock, activeTools }` result (`wsBlockRef.current = result.wsBlock` when non-undefined; single `pi.setActiveTools(result.activeTools)`). This is a design recommendation, not a mandated shape — the concrete requirement is "one function `index.ts` actually calls, that a test can call too, producing the whole lead/fork outcome including the reshaped tool surface and the block, for a given role" — any equivalent extraction satisfies the ticket's test bullet.
   - No test currently asserts the exact number/sequence of `pi.setActiveTools` calls (`grep` confirms — only one hit, an unrelated comment string), so consolidating the three calls into one is safe.

**4. `pi-lead-guide.md`**: add one row to the `## Verb-routing table` (after the existing rows, e.g. after the one-liner-exec row at L51): `| Load and follow a ws skill (lead-proceed, lead-drain-ready-queue, lead-write-ticket, ...) | \`ws-skill <name>\` (optional \`args\`, appended as \`User: <args>\`) |`. Also add the ticket-specified note that a `/goal` directive naming a skill is pursued by calling `ws-skill` at the start of every cycle — a short sentence near the table or in the `/goal` row's own context, not a new section.
