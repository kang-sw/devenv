### A / B / C boundary and the Anthropic research conclusion

**A — Exact effective prompt and callable serialized tools:** explicitly required. Capture and restore the effective Pi prompt; preserve actual registration/schema/order. Non-Codex is not excluded.

**B — Exact inherited effective input and provider-native cache annotations:** preserve inherited messages and all prompt-bearing content exactly through Pi's real serializer under equal configuration. Test raw provider output against an independent, same-history continuation reference, including annotations; do not normalize either side. Also inspect the previous lead request separately. A historical request's annotations are not necessarily the next request's annotations: the provider's documented continuation protocol can move cache breakpoints without changing the cached prompt content. Freezing historical Anthropic `cache_control` positions is **not necessary to the accepted effective-prefix/cache-preservation contract** and would introduce new marker-management behavior, including the risk of ceasing to cache the growing fork suffix. It is not selected.

This distinction is source/API-backed, not a license to delete differences from tests. Anthropic explicitly documents moving the fourth breakpoint to a new final message while reading all previously cached tokens and writing the new conversation segment. Pi does exactly that. The earlier research plan incorrectly promoted literal historical annotation immutability into a new acceptance condition; that manufactured blocker is withdrawn. Historical-versus-continuation raw payloads must remain visible in evidence and the exact expected native transition must be asserted, not normalized away or called byte-identical.

**C — Provider behavior:** even exact client content and correct native cache controls cannot guarantee retained cache entries, routing, minimum lengths, lookback reachability, cache lifetime, or billing. The ticket explicitly reserves this boundary. Provider-native limits are not a reason to lose A/B or to claim a cache hit.

### Anthropic lifecycle: why native marker movement should remain intact

Official API evidence, retrieved successfully as HTML using a normal browser User-Agent after the `.md` URL returned 403:

- `https://platform.claude.com/docs/en/build-with-claude/prompt-caching`, sections **How automatic prefix checking works**, **What invalidates the cache**, **Caching different sections of your prompt**, and **Cache limitations**.
- `https://raw.githubusercontent.com/anthropics/anthropic-cookbook/main/misc/prompt_caching.ipynb`, Example 2 and Example 3 (official Anthropic cookbook).

Relevant documented behavior:

- A breakpoint writes a prefix hash; later requests look backward for prior writes. The documented lookback is 20 positions per breakpoint, and up to four explicit breakpoints are supported.
- The documented four-segment example says a new turn without changing earlier content reuses all four cache segments. For a new final user message **with the fourth breakpoint moved to that message**, previously cached tokens are read and the new message/previous assistant segment is written.
- The official cookbook explicitly recommends moving the explicit breakpoint forward each turn, or automatic caching doing it for the caller.
- Empty text cannot be a cache target; thinking cannot be directly marked. Tool results, text and images can be cached. Some model-dependent thinking/effort/image changes affect cache validity, so effective model/API/auth/compat configuration must be held equal and native serializer behavior retained.

Source paths:

- Local `dist/bundle/chunks/anthropic-messages-JWX2WP65.js`.
- Global `dist/bundle/chunks/anthropic-messages-VWZZOSJQ.js`.

`buildParams` serializes `context.systemPrompt`, tools and messages. `convertMessages` groups consecutive tool results into a user message; skips empty blocks; converts text/images/thinking/tool use; applies the conversation `cache_control` only to the last eligible block when the final converted message is a user message. A string user message becomes an array when marked, so even its JSON representation can change when it is no longer final. Global 0.85.1 additionally uses `insertThinkingLevelMessages` for models supporting per-message effort, retaining `providerThinkingLevel` from historical assistant messages. These are normal serializer behaviors, not a fork-specific prompt mutation.

Conclusion: preserve the original Pi messages, signatures, effort metadata and tool definitions; serialize them with unchanged provider configuration. The native serializer can then keep advancing the suffix breakpoint over task/discussion turns and restarts. Do not transplant historical cache annotations into live payloads. That earlier candidate passed simple byte fixtures, but unnecessarily consumed/froze breakpoint slots and introduced precisely the later-turn problem this bounded research was asked to resolve.
