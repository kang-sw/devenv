# Plan: 260906-feat-ws-pi-spawn-warns-when-tier-resolution-degrades-to-inherit — Phase 1: Catalog check, warning line, and suggestions

## Relevant Ticket Contract

- Selected scope: Phase 1 only. Sage-settled catalog/auth validation, warning surfaces, suggestions, advisory reconciliation, tests, and the three specified spec passages are authorized. Adapter implementation stays in `agents-plugin-pi/`; no ws-mcp behavior changes. Migration anchors 260605 and 260802 preserve the one-directional adapter → harness-neutral ws-mcp dependency; do not revive mercenary machinery.
- Resolve a tier using the existing injected `config.resolve_agent` call (no explicit harness argument). Accept only `resolved_from === "pi"` and exact equality with a live catalog entry's `${provider}/${id}`, with configured auth. Supply catalog entries `{provider, id, hasAuth}` from the current execute/command context's `modelRegistry.getAll()` and `hasConfiguredAuth(model)` at resolution time. Do not use `getAvailable()`, `scopedModels`, a session-start snapshot, auth/network probes, or a `pi --list-models` subprocess for validation.
- A pi-labeled string absent from the catalog—including empty string, bare id, typo, unknown provider, and an appended `:thinking` not itself part of an exact catalog id—returns inherited model plus `rejected: {model, resolvedFrom, why: "unknown", suggestions}`. An exact entry without auth returns inherit and `why: "no-auth"`. Rejected resolutions contribute no tier effort. Accepted resolutions preserve existing model/effort handling and explicit caller-effort precedence.
- Non-pi resolutions (including non-bucket `resolved_from` values such as `tiers`), omitted tier, tool error, thrown call, missing/unparsable response text remain silent inherit. Preserve `resolvedFrom` as returned rather than normalizing bucket names. Never-configured tiers produce no per-spawn warning.
- Suggestions are a separate pure function: exact id first, then case-insensitive containment in either direction on the configured value's id half versus catalog id, then bounded edit distance on id. Preserve catalog order within a rank; return at most three unique provider/id candidates. Do not auth-filter suggestions. Use a finite, documented distance bound and tests; its numeric choice is an autonomous reversible implementation detail. Preserve the full id after the first provider separator (ids can themselves contain `/`); do not blindly strip legitimate catalog `:` characters before exact membership checking.
- Exact unknown warning base: `warning: tier <alias> is set to "<value>" for harness pi, which is not a provider/id entry in Pi's model catalog; inherited <lead provider/id>.` Append on the SAME line either ` Did you mean <provider/id>[, <provider/id> ...]?`, ` No close match in Pi's model catalog.`, or, for an empty catalog, ` Pi's model catalog is empty.`
- Exact no-auth warning: `warning: tier <alias> is set to "<value>" for harness pi, but provider <provider> has no configured auth; inherited <lead provider/id>.` No suggestion tail in this case. Format arbitrary configured strings safely as one line without changing the raw rejected detail.
- Cardinality: each rejected spawn gets exactly ONE warning in its immediate tool-result text and exactly ONE `ctx.ui.notify(..., "warning")` invocation on the supported UI path. Lead/fork explore uses the shared spawn warning, not a second lookup or second notification; blocking worker explore gets one of each through its own resolution. Each corresponding `ws-agent-list` row carries one spawn-time warning field. Accepted/silent cases get zero. Dormant send/resume emits zero new warnings and does not re-resolve. An in-memory parked record may retain its spawn-time row warning; a sidecar-rehydrated dormant record has none.
- Human-only pointer: only the UI notification appends ` See /ws-model-catalog-list for the models usable here.` No tool-result copy (spawn, explore, list, or advisory) instructs the model to run this human slash command. That command intentionally remains narrower: scoped models, otherwise available models; a suggestion may be absent there.
- Replace boolean `computePiAliasTableUnset` with `{unset, rejected: [{alias, rejected detail}]}` report `computePiAliasTableReport`. Reuse the resolver over ALL four tiers; do not stop after an accepted tier and miss later rejections. Any rejected tiers cause the advisory to list their common warning lines, even with another accepted tier; no empty-table sentence then. With no configured/accepted/rejected hits keep the existing empty-table advisory, including the existing all-transport-failures behavior. Accepted tier(s) without rejections suppress the advisory. Preserve append/copy semantics, successful-workflow_manual-only gating, and no notifications from advisory computation.
