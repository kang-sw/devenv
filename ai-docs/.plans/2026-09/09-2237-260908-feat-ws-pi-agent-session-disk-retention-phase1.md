# Plan: Pi adapter: bound subagent session files on disk (evict to disk, prune by age, drop empty spawn dirs) — Phase 1: Relocate child sessions to a durable owned home

## Relevant Ticket Contract
- Create each new worker, fork, and explore home below the configured Pi agent directory as `ws-agents/<stable lead-session identity>/<agent id>/`; workers and forks keep their session there, while no-session explores use the same owned home for their scratch material.
- Preserve fork ancestry, the approval-file channel, `record.sessionPath`, dormant resume, and shutdown-sidecar revival. Forks must launch with `--session-dir <owned-agent-home>` and reject a reported fork session path outside that home.
- Persist ownership, activity, and liveness information now so later cap cleanup and cross-lead TTL pruning can prove eligibility. Activity is refreshed by references/resume, prompts, reports, and session writes; it is not inferred from directory creation time.
- Existing legacy recorded paths remain readable and resumable. Unknown legacy filesystem material is not migrated or treated as owned.
- The owner live check must show that new children are absent from Pi's ordinary resume list and that no legacy `ws-pi-agent-*` homes are created.

## Out of Scope
- Phase 2's removal of scratch homes, cap-evicted homes, sidecar-orphan homes, path deletion, and deletion-failure handling.
- Phase 3's 30-day TTL configuration, scanning across lead homes, concurrent-lead pruning, and stale-subtree deletion.
- Any ws-mcp/legacy named-agent backend design; this is Pi-extension-local metadata and lifecycle work.

## Codebase Findings
- `agents-plugin-pi/src/spawner.ts#L2520-L2669` — `spawnAgent` currently creates a `mkdtempSync(tmpdir()/ws-pi-agent-)` directory for every persistent child before distinguishing workers from forks; a fork then replaces `record.sessionPath` with Pi's reported ordinary-session path.
- `agents-plugin-pi/src/spawner.ts#L1921-L1998` — fork launch transport is separately temporary, and `buildRpcClientOptions` owns RPC argv and derives `WS_PI_APPROVAL_DIR` from `dirname(sessionPath)`; it is the integration point for owned homes and `--session-dir`.
- `agents-plugin-pi/src/spawner.ts#L2705-L2777` — dormant children resume from the recorded `sessionPath`; fork resumes intentionally use `--session` rather than re-forking, so relocation must preserve that path exactly.
- `agents-plugin-pi/src/agent-sidecar.ts#L118-L275` and `agents-plugin-pi/src/index.ts#L509-L544` — the sidecar captures non-owner-bound records and restores them as dormant records on a matching lead session file, but stores no ownership/activity/liveness metadata today. The session-file guard means a no-session lead needs an explicit stable identity/sidecar-safe fallback rather than an implicit file path.
- `agents-plugin-pi/src/execute-gateway.ts#L374-L382` and `agents-plugin-pi/src/execute-gateway.ts#L712-L735` — approval decisions are sibling files under the recorded session path. A fork's approval directory must remain in its owned home through readiness and later dormant resume.
- `agents-plugin-pi/node_modules/@earendil-works/pi-coding-agent/dist/main.js#L529-L534` and `dist/cli/args.js#L88-L89` — Pi supports `--session-dir`; `getAgentDir()` is exported by the installed runtime, providing the configured root rather than a hard-coded home path.
- `agents-plugin-pi/test/spawner.test.ts#L3150-L3256`, `agents-plugin-pi/test/agent-sidecar.test.ts#L110-L275`, and `agents-plugin-pi/test/fork-lifecycle.integration.test.ts#L173-L186` — direct argv/environment assertions, sidecar round trips, and an isolated real Pi fork lifecycle fixture are established test patterns.

## Implementation Plan
1. Add a focused Pi-local durable-home helper (new `agents-plugin-pi/src/agent-storage.ts`, or the smallest existing lifecycle module if it avoids a cycle) that resolves `getAgentDir()/ws-agents`, derives and validates a stable lead identity from the active session manager even when no lead session file exists, creates an agent-id child home, and canonicalizes containment. Keep raw path components out of the authorization boundary: reject malformed IDs, resolve symlinks/parents before use, and return an explicit unavailable identity rather than falling back to `/tmp` or Pi's normal session directory.
2. Define versioned ownership metadata in that helper for each owned child home. Record the lead identity, agent id, spawn role, owned canonical home/session path, activity timestamps, and the protected/liveness facts the later phases require (running, owner-held/thread-bound, pending approval, and sidecar state). Expose narrow update/load operations so writes at prompt, report, resume/reference, session-write/readiness, and liveness transitions refresh the correct durable facts. Treat missing, malformed, or non-contained metadata as unknown/unowned; Phase 1 retains it and keeps legacy records resumable.
3. Route `spawnAgent` in `agents-plugin-pi/src/spawner.ts` through the durable-home allocator for all spawn shapes. Give workers and persistent explores `session.jsonl` inside their own home; give no-session explores an owned scratch home without inventing a session file; move only adapter-created fork-launch transport under the owned home or otherwise preserve its private cleanup semantics. Keep rejection-before-allocation ordering and the existing registry/alias behavior intact.
4. Extend `buildRpcClientOptions`, fork launch, and `validateForkReadiness` in `agents-plugin-pi/src/spawner.ts` to pass `--session-dir <owned-agent-home>` with `--fork`, then canonicalize and require Pi's `getState().sessionFile` to remain inside that exact home before assigning `record.sessionPath`. Preserve the existing readiness nonce, child-key, session-id, tools, and ancestry checks; on containment failure stop the new client and retain diagnostics rather than accepting an ordinary Pi session path.
5. Thread durable ownership through `RpcAgentRecord`, sidecar serialization/parsing/rehydration in `agents-plugin-pi/src/agent-sidecar.ts`, and `session_start`/`session_shutdown` in `agents-plugin-pi/src/index.ts`. Preserve backward parsing for legacy sidecars and paths, restore known owned records with their metadata and role wiring, and retain unknown/legacy entries without claiming ownership. Keep owner-bound and approval-wait protections visible in persisted state so Phases 2–3 can apply one shared eligibility rule.
6. Update the approval path in `agents-plugin-pi/src/execute-gateway.ts` only as needed to resolve decisions from the owned record home and to refresh durable activity/protection when a request is created, awaited, and decided. Do not remove any approval or scratch material in this phase.
7. Document the durable-root/legacy-compatibility contract in `ai-docs/spec/pi-adapter-runtime.md`, including no-session lead identity handling, `--session-dir` containment, metadata fail-safe behavior, and the distinction between Phase 1 persistence and later cleanup.

## Escalations
- Confidence: medium.
- Reason: the installed Pi runtime confirms `getAgentDir()` and `--session-dir`, but the extension context currently uses only `sessionManager.getSessionFile()` for lead persistence. The executor must confirm the exact stable `getSessionId()` contract for a no-session host before committing the identity helper; it must fail closed instead of deriving identity from cwd, time, or an untrusted path.
- Research should decide: only if Pi's no-session `getSessionId()` is not stable for the required lifetime, identify the supported Pi-provided stable session identity or an approved extension-local persistence point. Do not substitute a legacy backend identity scheme.
