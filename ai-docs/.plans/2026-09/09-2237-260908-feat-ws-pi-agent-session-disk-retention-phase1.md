# Plan: 260908-feat-ws-pi-agent-session-disk-retention — Phase 1: Relocate child sessions to a durable owned home

## Relevant Ticket Contract

- Create new worker, fork, and explore homes at `<configured Pi agent dir>/ws-agents/<lead session id>/<agent id>/`. Persistent children keep their session there; terminal no-session explores need only scratch material.
- Preserve fork ancestry, approval access, `record.sessionPath`, dormant resume, reopen, and sidecar revival. Fork launch passes `--session-dir <owned-agent-home>` and rejects a reported session outside that home.
- Persist ownership, activity, and liveness sufficient for later conservative cleanup. References/resume, prompts, reports, and actual session writes refresh activity. Unknown ownership/activity/liveness never proves eligibility.
- Legacy recorded paths remain readable/resumable without mass migration or claiming ownership from a pathname prefix.
- Verify configured-root overrides, all spawn shapes, ancestry, approval lifetime, reopen/resume, and both recovery paths. Owner live acceptance must show no children in ordinary Pi resume listings and no new `ws-pi-agent-*` homes.

## Out of Scope

No child-home deletion, TTL/configuration, cap deletion, orphan deletion, cross-lead pruning, audit missing-history redesign, or test-fixture cleanup campaign. Existing private fork-bootstrap transport cleanup and read-and-clear sidecar behavior remain intact. No ws-mcp or shared playbook edits. No new capability to reopen a vanished in-memory Pi conversation.

## Codebase Findings

### Verified SDK identity and directory contract

Installed `@earendil-works/pi-coding-agent` source, rather than an assumed API, establishes the mechanism:

- `dist/core/extensions/types.d.ts` exposes `ctx.sessionManager: ReadonlySessionManager`; `dist/core/session-manager.d.ts#ReadonlySessionManager` includes `getSessionId()` and `getSessionFile()`.
- `dist/main.js#createSessionManager` uses `SessionManager.inMemory` for `--no-session`, including the optional explicit `--session-id`. `dist/core/session-manager.js#newSession` assigns a UUIDv7 by default, stores it in the session header, and `getSessionId` returns that stored field. It is available without a session file and is stable while that logical session remains active. Explicit IDs allow alphanumeric, dot, underscore, and hyphen, beginning/ending alphanumeric; do not require UUID-only IDs.
- `SessionManager.open` / `_setSessionFile` restore the header ID. `newSession` assigns a new ID. A new no-session process without explicit identity is a NEW conversation, not a reopening of the previous one. `/reload` retains the same session manager; `dist/core/agent-session.js#reload` emits shutdown then start around extension reload. `dist/core/agent-session-runtime.js#teardownCurrent`, `switchSession`, and `newSession` emit shutdown for the outgoing session before starting its replacement. Capture outgoing identity before replacement, then recapture incoming identity on every `session_start`.
- An isolated no-model Node probe against the installed `SessionManager` passed: in-memory ID exists with no file, append preserves ID/header identity, independent manager and `newSession` change ID, disk reopen restores ID, and switch away/back restores each file's ID. The probe wrote only a disposable temp fixture, then removed it. No model or user session was accessed.
- `dist/config.js#getAgentDir` respects the configured environment directory and expands tilde; the package exports it. `dist/main.js#createSessionManager` forwards the CLI session directory into `SessionManager.forkFrom`. No hard-coded `~/.pi/agent`, cwd-derived identity, wall-clock identity, ws authentication key, or temporary identity is needed.

### Actual adapter seams and missing contracts

- `src/spawner.ts#spawnAgent` handles workers, task/discussion forks, and persistent simple/deep explore researchers. It currently creates `ws-pi-agent-*` first. `buildRpcClientOptions` derives approval environment from the session directory. `validateForkReadiness` already verifies nonce/key/session/tools and assigns the reported path; `spawnAgent` also assigns it prematurely before validation. Move assignment behind all checks.
- Terminal collectors use the separate `exploreLeaf` → `spawnPiProcess` → `harvestExplore` path and `AgentRecord`, not `spawnAgent`/`RpcAgentRecord`. They currently allocate no home and may inherit approval environment. Cover them explicitly; keep `--no-session` and no `sessionPath`.
- `prepareForkLaunch` creates a private `ws-pi-fork-launch-*` transport directory and readiness removes that entire directory. Keep this existing transport separate in Phase 1. Moving it into the agent home without narrowing cleanup would delete approval/session material. The rejected legacy prefix is `ws-pi-agent-*`, not this private transport mechanism.
- `src/agent-sidecar.ts#captureOrphans` excludes `threadBound` records. Owner-held forks instead persist through `src/ask.ts#PersistedForkResume`, `captureForkResume`, `rehydrateForkRecord`, and the thread-registry file. Both formats need additive ownership fields; sidecar-only changes lose ownership on owner-thread revival.
- `src/index.ts` writes sidecars before `stopAll` and currently only recovers them in a lead/fork session-file block. Worker/deep-research children can themselves own children. Durable namespace and child-registry persistence must cover every role that can delegate, independently of the lead/fork-only question UI.
- Identity is that of the immediate dispatching Pi session, which acts as lead for its own child registry. A nested worker/fork uses its own current Pi session ID when allocating grandchildren, not an inherited top-level ID or the fork's parent ws key. This avoids colliding registries/sidecars between parent and nested dispatcher; a persisted fork's own ID survives resume. Each record's allocated owner ID/home stays immutable across future dispatcher activity. No new inherited environment identity protocol is necessary.
- `RpcSpawnCtx` and `AgentCallCtx` currently lack Pi session identity. Add explicit storage context captured from the active tool/session context and forward through worker/fork/execute/ask/explore callers. Recovery uses recorded ownership, never a newly allocated home.
- No existing durable retention schema exists. The internal storage record and additive resume fields described below are new Pi-local contracts, not public ws protocol changes.

## Implementation Plan

1. **Define the internal ownership contract in new `agents-plugin-pi/src/agent-storage.ts`.** Provide a storage context from `getAgentDir()` and current `getSessionId()`, plus allocation/load/update operations and a JSON-safe ownership descriptor shared by `RpcAgentRecord`, terminal `AgentRecord`, `PersistedOrphan`, and `PersistedForkResume`. The descriptor contains schema version, immutable owner Pi session ID, agent ID, canonical home, role/explore mode, and optional canonical session path. A no-session leaf has no invented session path. Validate safe session-ID components using the SDK-supported character rule, validate generated agent IDs, and reject separators/traversal. Canonicalize the configured root and parents; reject symlinked child entries/escapes, including nonexistent-session paths via their real parent. Do not grant ownership solely because an arbitrary legacy path is inside a similarly named directory. Initial allocation/ownership-write failure fails that new spawn without falling back elsewhere.

2. **Persist an atomic per-home `ownership.json` through that helper.** In addition to the descriptor, store finite `createdAt`, monotonic `lastActivityAt`, `updatedAt`, last observed session file signature (`mtimeMs`, size), and a liveness snapshot: dispatching process PID and per-process instance nonce, observation time, lifecycle (`starting`, `live`, `stopping`, `stopped`, `unknown`), running, thread/owner-held protection, pending question, pending approval command ID, and recovery state (`none`, `sidecar`, `thread`, `revived`). Unknown/unreadable/malformed values remain unknown, never default eligible. PID/observation age alone is not proof of death; an expired live snapshot remains conservative until later phases supply their checks. Separate activity from liveness observation: polling alone must not renew activity. Publish with private permissions and atomic sibling-temp rename. Subsequent persistence failure uses existing diagnostics and leaves disk facts conservative; it must not interrupt an otherwise working child or fabricate a successful update. The helper must not import spawner/ask runtime modules.

3. **Wire allocation and argv in `src/spawner.ts`.** Extend `RpcSpawnCtx`/`AgentCallCtx` with explicit storage context; populate it from current Pi context in `registerAgentTools`, `src/fork.ts#registerFork`, `src/execute-gateway.ts#registerExecuteGateway`, and `src/ask.ts#ensureRespondent`. Keep guards/model refusal before allocation. Allocate workers and persistent researchers with `session.jsonl`; allocate terminal `exploreLeaf` scratch homes and pass their own approval directory to `spawnPiProcess` without altering its no-session argv. Keep existing `buildChildProcessEnv` isolation, overlaying only the child's own directory. Extend `buildRpcClientOptions` with owned home and pass `--session-dir` for initial fork copies and owned resumes so future Pi-created files stay contained. Preserve `--session <recorded path>` on resume and all legacy behavior when ownership is absent. `validateForkReadiness` checks canonical containment and all existing readiness invariants before updating either record or metadata. Keep private fork transport cleanup unchanged; never point it at the owned home.

4. **Centralize activity/protection updates at real lifecycle boundaries.** Give owned records a helper-backed update handle reconstructed on revival. In `spawner.ts`, update before `promptAgent` dispatch, including internal fork nudges without changing `lastLeadPromptAt` semantics; update on the live steer/follow-up branch of `sendToAgent`, reference/resume, `recordReport`, and `applyRpcEvent` running/settled/approval transitions. Mark `starting` before RPC start and `stopping` before teardown; `clearLiveState` is a memory reset, not proof the process stopped. Publish stopped only after confirmed close/stop, and unknown when teardown cannot establish exit. Tag each launch generation so an old stop completion cannot overwrite a concurrently resumed client's live metadata. Terminal `spawnPiProcess` error/close and `harvestExplore` update completion/last-consumer facts but retain the home.

   Use a helper-owned, unreferenced session-file stat observer for each registered owned persistent record, including dormant records; compare file signature and refresh activity when writes change it. Sample at readiness, settle, before stop and after stop, and before unregistering the observer. Keep this independent of the existing outstanding-only RPC liveness sweep, which misses idle/dormant writes. Observer failures mark observation unknown; directory creation time never substitutes for writes. Close observers on registry eviction/self-reap/shutdown without deleting material. Later cross-lead scans can also read current file stat; no background cross-lead scan is introduced now.

   User references touch activity at `sendToAgent`, `getAgentTranscriptPath`, explicit stop/approval actions, and `src/audit.ts#openViewer` (including already-selected direct views). Do not touch activity from bulk `listAgents`, `resolveAgentId` alone, picker enumeration, widget redraws, or liveness sweeps.

5. **Cover question, approval, and owner-held protections.** In `src/ask.ts`, route `bindThread`, `handleForkRaisedQuestion`, `detachForkRaisedThread`, `injectDiscussionSummary`, and respondent reopen/close paths through the same protection updater; pending/open owner questions remain protected even after a child is dormant. Extend `PersistedForkResume`, `captureForkResume`, its parser, and `rehydrateForkRecord` with optional ownership, validating against `ownership.json`; legacy resume data stays usable without ownership. Reconstruct ownership and protection before re-arming respondent hooks. In `src/execute-gateway.ts#registerExecuteGateway`, approval creation/relay and `ws-approve` persist pending command/liveness before waiting and activity on decision. Resolve owned decision files from the owned home, falling back to `dirname(record.sessionPath)` only for legacy records. Preserve the pending-consumer protection until the decision is written and the wait has ended; neither readiness nor approval completion removes the home. Keep future audit owner-held integration an explicit optional protection, without inventing the deferred steering feature.

6. **Preserve owner identity and recovery in `src/agent-sidecar.ts` and `src/index.ts`.** Add optional validated ownership fields to the existing version-1 sidecar format; do not invalidate legacy sidecars. Read ownership from the owned metadata and compare identity/home/session path on revival. Invalid ownership strips authorization, not the independently valid legacy resume path. Preserve `spawnRole`, explore mode, fork context, and role wiring through both recovery formats. Keep the existing `<leadSessionFile>.ws-agents.json` locator for file-backed dispatchers; extend the locator API to use `<configured root>/ws-agents/<current Pi session ID>/registry.ws-agents.json` when no lead file exists. Reuse the same serializer/read-clear/revival logic rather than creating a second implementation. This supports same-ID no-session reload; a fresh no-session identity does not scan or adopt another identity's sidecar.

   Capture current identity and outgoing sidecar locator at each `session_start` for all delegating roles. On shutdown, snapshot original running state for the existing orphan announcement, mark durable recovery intent before `stopAll`, then publish confirmed stopped/unknown liveness after teardown without erasing pending question/owner protections. Clear process-scoped context only afterward. On the next start, restore the matching sidecar and thread ownership before new work. Incoming new/switch sessions allocate under their own ID; returning/reopening recovers the original namespace and recorded paths. A revived orphan's in-memory `running:false` is not evidence that every previously owned process is dead; ambiguous disk liveness remains conservative. No child/session/home deletion is added.

7. **Document the implemented boundary in `ai-docs/spec/pi-adapter-runtime.md`.** Describe configured root, immediate-dispatcher Pi identity, no-session lifetime/reload limitation, nested/reopen identity, fork containment, ownership/activity/protection metadata, both recovery formats, and legacy compatibility. State that retention deletion/TTL remain later phases. Read spec conventions before changing the spec; this research changes only this plan.
