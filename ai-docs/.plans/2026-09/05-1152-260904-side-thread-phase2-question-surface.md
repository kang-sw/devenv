# Plan: 260904-feat-ws-pi-side-thread-fork-question-surface — Phase 2: Owner question surface (`ws.ask`, registry, overlay chat, lazy discussion fork, injection)

## Relevant Ticket Contract

- Thread registry (§1): `thread := { thread_id, title, question?, context?, entry_id, respondent?: agent_id, status }`; `entry_id` is mechanically recorded by the adapter, never authored by the model.
- `ws.ask(title, question, context) -> {question_id}` **registers only, NO spawn**; `ws.resolve(question_id)` lead self-resolves a pending question. `/answer <id>` opens it — spawns a discussion fork **at the lead's tip at open time** (not ask time) and attaches the overlay. `/done` inside the overlay ends the thread: fork writes a summary, adapter injects it into the lead session.
- Fork-raised question (Entry A meets Entry B): a task fork's `ws-report-to-lead(kind:"question", message)` registers a thread with `respondent` already set to that live fork; `/answer` attaches to the **live** fork — no new spawn. No fork-less quick-answer path exists.
- §3 tool surface: `ws.ask`/`ws.resolve` are excluded from a fork's own surface (added to `FORK_EXCLUDED_TOOL_NAMES`), exactly like `ws.fork` — a fork's only question path stays `ws-report-to-lead(kind:"question")`.
- §4 anti-bleed loop is **Entry A (task threads) only**. Discussion threads (Entry B, both the lazy `/answer` spawn and the fork-raised attach) **run no loop** — the fork is meant to speak *as* the lead, persona continuity is the feature, and the structural initial-message frame (`buildForkInitialMessage`, Re-decision 2026-09-05) applies **only to Entry A** — do not wrap a discussion fork's initial message with it.
- §5 owner-facing surface: overlay via `ctx.ui.custom({overlay:true})`; child `text_delta` → `Markdown.setText`; owner input → `RpcClient.prompt()` when the fork is waiting, `steer()` when running. Closing the overlay has no effect on the fork (reopenable while alive). `setWidget(aboveEditor)` shows `N pending`; `/answer <id>` opens one; `/thread` lists all (pending + running); a shortcut reopens the most recent; `/done` ends a discussion thread. **Never auto-pop.** No child-side `ctx.ui.*` dialogs. Captured-`ctx` staleness: re-capture `ctx` on every `session_start`, store only plain data in the registry. **One overlay at a time** — opening a new `/answer` closes the current overlay first (its fork unaffected). **Registry is persisted**, not in-memory only, in the adapter's per-lead-session state file, so pending questions and dormant threads survive a lead restart.
- §6 injection: `/done` → fork writes summary → adapter injects `context + original question + summary` as a **Pi custom message** (distinguishable from a user turn), delivered via `followUp` (never `steer`) when the lead is idle, queued in order for multiple closes. Task-thread final reports are unchanged (`260903` path). Lead session is never rewound.
- §7 `context`/`entry_id`: `context` is lead-authored, 2-3 sentences, no paths/hashes. `entry_id` addresses the lead-session entry; when it has fallen behind a compaction boundary, the adapter inserts a verbatim excerpt around it into the fork's first message. Rejected: model-authored time-capsules, rewinding the lead.
- §8 headless (`ctx.mode !== "tui"`): fork-raised questions relay through the lead via `ws-agent-wait`/`ws-agent-send` (unchanged Phase-1 path). `ws.ask` registers and notifies via `ctx.ui.notify` (fire-and-forget `extension_ui_request`); **no discussion fork spawned headless**; owner's answer arrives as an ordinary lead turn.
- §9 lifecycle: lazy spawn (unopened question costs nothing); closed threads are dormant+retained (`260903` `ws-agent-stop` semantics), reopenable; a retained task fork owns its authored artifact's continuing edits (not this phase's code, but must not be broken).
- Constraints: golden rule (`agents-plugin-tool/` Go, `agents-plugin/skills/` untouched); no child-side `ctx.ui.*` dialogs; no overlay auto-pop; no lead rewind; `ScrollView` has no bundled overlay precedent — verify inside an overlay or fall back to `Container` + tail truncation.
- Preconditions from the ticket's "Unblocked" note: adapter must stay **user-scope installed** (`pi install <abs path>`) for spawned children to load `ws-report-to-lead`; structural frame is Entry-A only; human-judgment verification items (visual polish, IME/CJK, cross-emulator) are packaged as a one-shot owner runbook at closeout.
- Verification boundary (ticket's own two-tier split): (a) **unit** — instantiate the overlay/widget `Component` and call `render(width)`/`handleInput(data)` in `node --test`, no TTY; (b) **integration** — a `tmux -L ws-probe-<pid>` (isolated socket, never default) probe driving `pi --offline --no-session -e <ext>`; anything TTY-only/flaky is packaged as a one-shot human runbook, not left un-driven.

## Codebase Findings

- **Risk signal — ticket assumption vs. reality: no persistence exists today.** `agents-plugin-pi/src/spawner.ts#L723` (`export type RpcAgentRegistry = Map<string, RpcAgentRecord>`) is a plain in-memory `Map`; nothing in `spawner.ts` ever serializes it (no `writeFileSync`/`JSON.stringify` of a registry anywhere in the file — confirmed by grep). The ticket's §5 bullet says the new thread registry sits "next to the `260903` D-C ... agent_id → session mapping (which must already persist for dormant resume)" — that mapping does **not** persist across a lead-process restart today; `260903`'s D-C decision ("dormant/resumable") only survives within one running lead process's lifetime (the child process exits, the in-memory record and its `sessionPath` stay valid because the *lead's own process* never restarted). **Resolution adopted below**: persist the thread registry's own denormalized copy of the fields needed to reconstruct an `RpcAgentRecord` on demand (sessionPath, explicitTools, wsToolNames, modelBase), and lazily rehydrate a plain object literal into `rpcRegistry` the first time a dormant thread is reopened post-restart — this satisfies verification item 5 without broadening `spawner.ts`'s own registry persistence (surgical, additive, no `spawner.ts` edit required since `RpcAgentRecord`'s fields are all public/exported).

## Implementation Plan

1. **`agents-plugin-pi/src/fork.ts`** (small, additive):
   - Extend `FORK_EXCLUDED_TOOL_NAMES` to `new Set([FORK_TOOL_NAME, "ws-ask", "ws-resolve"])`, with a comment noting these two literals are `ask.ts`'s tool names, duplicated here specifically to avoid a `fork.ts` → `ask.ts` import cycle (fork.ts must keep importing only FROM `spawner.ts`/`process-role.ts`).
   - Add an optional `onQuestion?: (agentId: string, message: string) => void` parameter to `registerFork` (threaded into `wireAntiBleedLoop`, mirrors `RpcSpawnCtx.onApprovalPending`'s existing shape); invoke it inside the existing `outcome === "question"` branch (`wireAntiBleedLoop`, after the current `nudgeCount = 0; return;`) with the report's `message`. No behavior change when the callback is omitted (existing tests unaffected).
   - Update `test/fork.test.ts` only for the new parameter's plumbing (a fake callback receives the message on a "question" outcome) — no change to any existing pure-predicate assertion.

2. **New file `agents-plugin-pi/src/ask.ts`** (mirrors `fork.ts`'s pure/IO split and its "imports FROM spawner.ts/process-role.ts/fork.ts only" placement):
   - `ASK_TOOL_NAME = "ws-ask"`, `RESOLVE_TOOL_NAME = "ws-resolve"`.
   - `ThreadStatus = "pending" | "open" | "dormant" | "closed"`; `ThreadRecord` (in-memory, plain data): `{ threadId, title, question?, context?, entryId?, status, respondentAgentId? }`. `entryId` is set only for a `ws.ask`-originated thread (Entry B lazy spawn); absent for a fork-raised thread (no lead entry exists to anchor).
   - `PersistedForkResume` (denormalized, JSON-serializable): `{ sessionPath, explicitTools, wsToolNames: string[], modelBase?: string }` — attached to a `ThreadRecord` once a respondent fork exists, so a dormant thread can be rehydrated after a lead restart with no live `RpcAgentRecord`.
   - Pure: `deriveThreadTitle(message: string): string` (first line, truncated) — for fork-raised threads with no author-supplied title.
   - Pure: `threadRegistryPath(sessionFile: string): string` → `` `${sessionFile}.ws-threads.json` `` (sibling file, per-lead-session, named off the lead's own `getSessionFile()`).
   - Pure: `serializeThreadRegistry`/`parseThreadRegistry` (tolerant: malformed/missing JSON → `[]`, mirrors `goal-loop.ts#L107-116`'s never-throw contract).
   - IO: `loadThreadRegistryFile(path)`/`saveThreadRegistryFile(path, records)` — `try/catch` around `readFileSync`/`writeFileSync`, degrade to empty / no-op + a `ctx.ui.notify("warning", ...)` on failure, never throw (same contract as `readGoalLoopConfig`).
   - Pure: `countPending(records): number` (status `"pending"` only — matches the widget's "`N pending`" wording); `buildWidgetLines(count): string[] | undefined` (`undefined` clears the widget at `count === 0`).
   - Pure: `isEntryLive(entryId: string, liveEntries: {id:string}[]): boolean`; `buildVerbatimExcerpt(entryId: string, branch: {id:string; ...}[], windowSize: number): string` (renders a small window of the ancestor chain from `ctx.sessionManager.getBranch(entryId)` as plain text) — the §7 post-compaction anchoring.
   - Pure: `addAskToolsIfLead(activeTools: readonly string[], role: SpawnRole | undefined): string[]` — identical shape to `fork.ts`'s `addForkToolIfLead` (adds `ASK_TOOL_NAME`/`RESOLVE_TOOL_NAME` only for `role === undefined`), kept as its own function rather than folded into `fork.ts`'s (single-responsibility, same reasoning `fork.ts`'s own doc comment already gives for not folding `FORK_TOOL_NAME` into `execute-gateway.ts`'s shared list).
   - Pure: `buildDiscussionForkInitialMessage(context: string | undefined, question: string): string` — Entry B's initial prompt; deliberately **not** wrapped in `buildForkInitialMessage`'s structural frame (ticket's explicit "do not wrap" rule) — plain text naming the context/question and inviting the fork to continue the discussion as itself.
   - Pure: `buildDiscussionForkDirectiveText(): string` — a short, framing-free system-prompt directive for Entry B (no `kind:"final"` report instruction, since Entry B's exit is `/done` in the overlay, not a report).
   - Pure: `buildInjectionMessage(context: string | undefined, question: string, summary: string): string` — the §6 payload body (`context + original question + summary`).
   - IO glue (module-scope refs, mirrors `event-bus.ts`'s `currentCtx` idiom, scoped to this file only): `askCtxRef: { current: ExtensionContext | undefined }`; a `ThreadRegistryHandle` bundling the in-memory `Map<string, ThreadRecord>`, `askCtxRef`, and the resolved `threadRegistryPath`.
   - `registerAsk(pi, bridge: BridgeHandle, rpcRegistry: RpcAgentRegistry, handle: ThreadRegistryHandle, sessionCtx: {cwd, modelCatalogPath})`:
     - `ws-ask` tool: `{title, question, context}` params; `execute(...,toolCtx)` records `entryId = toolCtx.sessionManager.getLeafId()`, creates a `"pending"` `ThreadRecord`, persists, and — only when `toolCtx.mode === "tui"` — calls `refreshPendingWidget(toolCtx, handle)`; when `toolCtx.mode !== "tui"` (§8), skips the widget and calls `toolCtx.ui.notify(...)` instead (fire-and-forget `extension_ui_request`, works in rpc mode per the ticket).
     - `ws-resolve` tool: `{question_id}`; marks the record `"closed"` (lead self-resolve, no injection — the lead already knows), persists, refreshes the widget.
   - `handleForkRaisedQuestion(handle, rpcRegistry, agentId, message)` — the callback passed as `fork.ts`'s new `onQuestion`: creates a `"open"` `ThreadRecord` with `respondentAgentId = agentId`, `title = deriveThreadTitle(message)`, `question = message`, no `entryId`; persists; refreshes the widget via `askCtxRef.current` (may be `undefined` immediately after a restart-before-first-session_start race — guarded no-op, matching the ticket's own "captured-ctx staleness" note).
   - `registerThreadCommands(pi, bridge, rpcRegistry, handle, sessionCtx)`:
     - `/thread` — lists pending + open/dormant threads (`ctx.ui.notify` or a plain text render — no overlay needed for a list).
     - `/answer <id>` — resolves the thread; if `respondentAgentId` is set and live in `rpcRegistry`, attach directly; if set but **not** in `rpcRegistry` (dormant post-restart), rehydrate a plain `RpcAgentRecord` object from the persisted `PersistedForkResume` fields (`client: undefined, streaming:false, idlePending:false, waiters:[], pendingReports:[], reportsDropped:0`) into `rpcRegistry`, then resume it the same way `sendToAgent`'s existing dormant-auto-resume branch does (reuse `sendToAgent`, do not reimplement); if no respondent at all, spawn a **lazy discussion fork** at `ctx.sessionManager.getSessionFile()` (the lead's current tip, "at open time") via `spawnAgent` with `forkFrom` set, `explicitTools = computeForkToolSurface(pi.getActiveTools())`, `systemPromptPath` from `buildDiscussionForkDirectiveText()`, `prompt` from `buildDiscussionForkInitialMessage(...)` (checking `isEntryLive`/`buildVerbatimExcerpt` first when `entryId` is set) — **no `wireAntiBleedLoop` call** (Entry B runs no loop). Then, regardless of path, calls `openOverlayForThread(ctx, thread, record)` (from `overlay-chat.ts`).
     - `registerShortcut` — reopens the most-recently-touched open/dormant thread via the same `openOverlayForThread` path.
   - `injectDiscussionSummary(pi, thread, summary)` — called from the overlay's `/done` exit: `pi.sendMessage({customType:"ws-thread-summary", content: buildInjectionMessage(thread.context, thread.question, summary), display:true, details:{threadId: thread.threadId}}, {deliverAs:"followUp"})`; marks the thread `"dormant"` (retained, reopenable per §9) and persists.

3. **New file `agents-plugin-pi/src/overlay-chat.ts`** (the pi-tui `Component`, mirrors `questionnaire.ts`'s shape):
   - `OverlayChatComponent implements Component`: constructor takes `(tui, theme, client: RpcClient, streamingRef: {current:boolean}, onDone: (summary: string) => void)`. Internal state: a text buffer accumulating `text_delta`s into a `Markdown` (or `Container` + tail-truncated plain lines if `ScrollView` proves unusable inside an overlay — both code paths implemented behind one small render seam so the fallback is a one-line swap, not a rewrite) and an `Editor` (from `pi-tui`, same as `questionnaire.ts`) for the owner's input box.

## Escalations

- Confidence: high — every Pi runtime API the ticket names is confirmed present with an exact matching signature (`ctx.ui.custom`/`setWidget`/`notify`, `pi.sendMessage`/`sendUserMessage`, `registerCommand`/`registerShortcut`, `RpcClient.onEvent`/`prompt`/`steer`/`followUp`, `sessionManager.getLeafId`/`getEntry`/`getBranch`/`buildContextEntries`, `pi-tui`'s `Component`/`Markdown`/`ScrollView`/`Container`), and every codebase seam the implementation needs (fork.ts's forward-compatible exclusion-set comment, the `onApprovalPending`-style callback-injection convention, `RpcAgentRecord`'s all-public fields, `sendToAgent`'s reusable resume path) is already in place or trivially extensible. No strategic uncertainty blocks a single implementation path.
- One **flagged-but-not-blocking** contract-vs-reality mismatch (see Codebase Findings' first bullet): the ticket's §5 text asserts the `260903` D-C agent_id→session mapping "must already persist for dormant resume" — it does not (in-memory `Map` only, confirmed by reading `spawner.ts` in full and grepping for any serialization of `RpcAgentRegistry`). This plan resolves it with a **narrower, additive** fix (persist only the thread registry's own denormalized fork-resume fields, lazily rehydrate on reopen) rather than broadening `spawner.ts`'s own registry persistence — this fully satisfies the ticket's *observable* restart-survival requirement (verification item 5) without expanding scope into general subagent-registry persistence, so it is a strategy choice within the plan, not a scope reduction requiring lead sign-off. Surfacing it here per the survey doctrine's "any spec or doc entry that produced a wrong assumption" instruction, not as a blocker.
