# Retire native Pi agent tools in favor of daemon Pi agents

## Context

The owner wants to retire the Pi extension's native `ws-agent-*` spawning path now that daemon-backed `pi.*` exists. Direct Pi TUI and daemon-independent operation are no longer requirements. Concrete model selection has repeatedly been a footgun; retain capability-tier selection, not per-spawn concrete model or effort selection. Owner clarification (1225), recorded 2026-11-16: write-path limiting is valuable but profiles have no write-scope field; do not port it in this ticket. Track it as Forward instead.

Start implementation only after the Pi background-shell idle signal work on `impl/develop/pi-lead-idle-stop`, followed by Pi bundling hardening (loud fallback failure and native-pi regeneration), has merged. Both touch `agents-plugin-pi/src` and `dist`; re-inspect their landed changes before editing. This is a sequencing prerequisite, not a claim that a particular ticket has landed.

Today native `registerAgentTools` owns a session `rpcRegistry` (`agents-plugin-pi/src/spawner.ts:4591`), shared with execute, fork, recovery and dashboard (`agents-plugin-pi/src/index.ts:901,960-998,1149`). The daemon `pi.spawn` has no `write_scopes`, alias, model_effort or concrete-model argument (`agents-plugin-tool/internal/mcp/pi_tools.go:529-543`); its profile and tier ceilings, child forwarding and depth limit remain relevant (`agents-plugin-tool/internal/wsagent/spawn.go:151-176`, `agents-plugin-tool/internal/wsagent/children.go:251-326`).

Dependency inventory and intended disposition, subject to the policy questions below:

- `explore` is a persistent read-only researcher preset using `spawnAgent` and the registry (`agents-plugin-pi/src/spawner.ts:4833-4900`). Recommend replace with tier-small `pi.spawn` and a read-only brief, not claim sandbox enforcement; whether to drop the preset is (1227).
- `ws-fork` spawns into that registry and arms fork-specific wiring (`agents-plugin-pi/src/fork.ts:355-378`). Recommend migrate its useful interaction to daemon Pi agents rather than silently lose it; whether to drop it is (1228).
- `ws-report-to-lead` returns from the child tool while the parent observes its RPC tool-start event and pushes progress (`agents-plugin-pi/src/spawner.ts:3074-3086,4816-4829`). It depends on the native RPC observation path. Migrate any required progress reporting to daemon messaging, not pretend completion mail is equivalent.
- `ws-execute` spawns a registry worker and `ws-approve` resolves that record (`agents-plugin-pi/src/execute-gateway.ts:711-740,774-795`); the approval request is relayed as a steerable `ws-agent-approval` (`agents-plugin-pi/src/execute-gateway.ts:595-634`). Migrate the approval workflow to daemon-backed agents and preserve actionable request/response correlation; completion mail is not approval transport. No orphaned approval or silent auto-approval.
- Sidecar shutdown snapshots the registry and startup revives entries, including execute/fork wiring (`agents-plugin-pi/src/index.ts:328-345,374-389,1165-1176`); it preserves selected metadata, not live clients or report history (`agents-plugin-pi/src/agent-sidecar.ts:140-167,354-358`). Replace native orphan revival with the daemon's lifecycle and explicitly handle already-persisted native sidecars; do not promise live process or report recovery. Decide migration/refusal behavior before deleting the reader.
- Dashboard feed projects the registry and relayed descendants, including approval state (`agents-plugin-pi/src/index.ts:960-988`, `agents-plugin-pi/src/dashboard-feed.ts:350-377`). Migrate to daemon agent state, preserving useful status and approval visibility without duplicate rows; do not keep a dead registry as a dashboard source.

Native push events include progress `ws-agent-report`, terminal/idle `ws-agent-settled`, approval, advisory, question and orphan notices (`agents-plugin-pi/src/spawner.ts:1003-1017`). Daemon settled-turn completion for a lead is system mail labelled `pi:<child-id>` with replies via `pi.send`, not `mailbox.send` (`agents-plugin-tool/internal/mcp/pi_tools.go:497-510`, `agents-plugin-tool/internal/mcp/lead_mail.go:227-229,266-280`); nested parents receive steering or queued delivery, and `pi.wait` may consume the report instead of redelivery (`agents-plugin-tool/internal/wsagent/children.go:509-543,729-770,832-883`). Completion mail replaces settled notification, not intermediate progress, approvals, questions, advisories or orphan recovery. Design explicit mappings for each retained behavior and test once-only delivery.

## Decisions

- Daemon Pi agents replace native `ws-agent-*`; daemon independence is not a goal. No concrete-model selection or per-spawn model effort; use existing `agents.tier` Pi mapping and tier ceilings. Do not port native aliases or other spawn options merely for parity.
- Owner (1225): do not port `write_scopes` or invent a Profile write-scope field in this ticket. The earlier narrow-port plan is superseded. Forward: separately design write-path limiting with actual edit/write enforcement and honest shell limitations; this ticket does not claim a sandbox.
- Owner (1227)=b: replace extension `explore` with builtin agent profile `explore` in `agents-plugin-tool/internal/wsagent/builtin.go` / `BuiltinProfiles`, using existing Profile fields only: backend Pi; tools read/grep/find/ls; small-model use via the caller's tier; minimal evidence-report instructions. T0 additive builtin: an older daemon may report unknown profile at spawn, so new callers must not assume old-daemon availability. No new Profile field (`DisallowUnknownFields` is an old-reader hazard).
- Network gap for (1227): native Explore has extension-owned `web_search` and `ws_web_fetch` (`agents-plugin-pi/src/delegation-policy.ts:12`, `web-tools.ts:32`). The inspected installed host's `dist/core/tools/index.js:19-28,29-50` lists read/bash/powershell/edit/write/grep/find/ls and rejects unknown core names; there is no core web-search/fetch equivalent to put in this profile's `tools`. Keep the builtin local/read-only; do not invent a network/Profile field or claim equivalent web capability.
- Owner (1228)=a: drop `ws-fork` outright, rather than migrate its question/thread behavior. No removal has occurred while the compatibility prerequisite below is blocked.
- Enable daemon `pi.*` by default for Pi leads, while respecting explicit configuration, host availability and version gates. Pi currently defaults off (`agents-plugin-pi/dashboard-config-manifest.json:35-38`; compare `agents-plugin/dashboard-config-manifest.json:35-38`); inspect all three manifests and packaged mirrors. Switch Pi playbook idioms, including explorer wording, from native names (`agents-plugin-tool/internal/mcp/playbook_tools.go:46-47,160-170`) to namespace-correct `pi.spawn`/`pi.send` and capability tiers.
- Owner (1229)=b is a conditional T0 reading: an old, unupdated native Pi extension should keep working against a new daemon, with removal treated as extension feature retirement rather than an MCP API break. The owner requires proof that (i) ws-agent-* tools make no daemon calls and (ii) no daemon-embedded instruction text names ws-agent-* or the explore/ws-fork tools. If either fails, stop and report before removal. Both literal prerequisites fail on develop d7534a5f7; see Blocked below. Do not convert this conditional approval into an unconditional T0 or T3 verdict.
- Existing daemon calls alone do not prove a T3 removal: retaining their compatible APIs could preserve old plugins. However, that is a different compatibility argument than the one approved conditionally; explicit owner continuation is required before proceeding. Manifest defaults, old/new daemon/extension/text combinations, persisted native sidecars and capability-gated use of the new builtin still need directional analysis after that continuation.

## Blocked — owner compatibility prerequisites fail (2026-11-16)

Pre-removal inspection only; no implementation, registration removal, artifact regeneration or status promotion occurred. Owner answers are recorded in Decisions and the Open Decision Queue has been removed. Sage/ready promotion is held because the approved compatibility premise contradicts the current code.

1. **Condition (i) fails:** `ws-agent-spawn`'s execute handler calls `spawnAgent` with `client: bridge.client` (`agents-plugin-pi/src/spawner.ts:4670-4697`). `spawnAgent` resolves the requested model through that client (`:3771`); non-concrete selections route to `resolveModelForAliasViaWsMcp` (`:347-354`), which calls `config.resolve_agent` (`:297-306`). `McpStdioClient.callTool` sends a real `tools/call` request (`agents-plugin-pi/src/mcp-stdio-client.ts:341-342`), and the daemon dispatches that API (`agents-plugin-tool/internal/mcp/server.go:1275-1296`). Omitted/concrete model paths can avoid this call; that does not establish the universal no-daemon-calls condition.
2. **Condition (ii) fails:** the daemon-compiled Pi playbook terminology explicitly names `the explore researcher`, `ws-agent-spawn`, and `ws-agent-send` (`agents-plugin-tool/internal/mcp/playbook_tools.go:44-47`). This is live emitted instruction text, not just comments/tests: terminology overwrites declared playbook variables (`:442-447`); `delegationTip` inserts ContinueIdiom into follow-up instructions (`:484-494`); rendering selects this terminology and appends that tip (`:966-994`). Updating this text is required, but its current existence fails the owner's pre-removal condition.

Proposed continuation for owner judgment: allow a T0 argument based on **retaining compatible daemon APIs used by old extensions**, not on daemon independence, and authorize replacing all daemon-rendered native-tool idioms in the same retirement change. Require explicit mixed-version/capability analysis for old daemon/new extension and new daemon/old extension before removal. If that is not approved, rescope the retirement or choose an explicitly approved compatibility boundary; no automatic T3 escalation is inferred here.

Verification boundary: source/call-path inspection and documentation diff checks only. No Go tests/builds, executable/launcher invocation, or implementation review was needed or run for this stop. Work remains in todo.

## Phases

### Phase 1: Builtin explorer profile and Pi defaults

Only after the compatibility blocker is explicitly cleared, add the minimal builtin `explore` profile from (1227), with existing Profile fields and caller-selected tier. Do not implement or add an argument/field for `write_scopes`; it is Forward. The read-only profile intentionally has no equivalent of the extension's web-search/fetch facade.

Enable default Pi-lead availability while respecting explicit opt-out and host/version gates, and switch relevant rendered playbook idioms to namespace-correct `pi.*` / `pi.spawn(profile: "explore")`. Trace manifest default compatibility and old-server/profile capability detection before release. Acceptance: focused tests cover builtin fields, read-only tools/evidence instructions, tier/profile ceilings, configured opt-out, rendered Pi lead/daemon-worker text, host/version disabled cases and mixed-version behavior. Subsequent registry migration/removal must not run before the blocker is cleared.

### Phase 2: Migrate registry dependents

After Phase 1 and resolution of (1227)-(1228), implement the dispositions above. Specify and test progress versus completion, questions, actionable approval correlation and responses, advisory delivery, daemon restart/reconnect, persisted native orphan handling, dashboard state and descendant visibility; verify fresh spawn and dormant/recovery paths. Keep `ws-execute`/`ws-approve` behavior safe, or explicitly obtain an owner decision before changing its contract. No lost or duplicate settled mail when `pi.wait` consumes a result. Do not remove the registry until every retained consumer has an equivalent source.

### Phase 3: Remove native agent registrations and ship mirrors

After Phase 2 and compatibility decision (1229), remove native `ws-agent-spawn`, send, list, stop and transcript registrations, obsolete registry machinery and tests, plus other native surfaces only as resolved above. Update `pi-lead-guide.md`, push/render/compaction references and workflow instructions to the actual retained transports. Regenerate `agents-plugin-pi/dist` and first-party `agents-plugin/native-pi` and `agents-plugin-wsflow/native-pi` source/dist/guide mirrors using the landed bundling process; satisfy the dist freshness guard. Test registration absence, retained flows, mirrored assets/freshness, and the approved old/new compatibility boundary. No merge or release is implied by this ticket.
