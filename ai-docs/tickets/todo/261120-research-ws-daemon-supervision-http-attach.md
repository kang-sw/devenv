# Research daemon supervision and direct HTTP MCP attachment

## Background

Owner decision (1872)=a on 2026-11-20 demoted
`261117-feat-ws-single-session-holder` to `idea/` while retaining a separable
question: can one long-lived component build, version-check, start, replace,
and restart ws-mcp so independently user-started Claude Code and Codex sessions
attach directly over HTTP, without one stdio launcher process per session?

This is accepted backlog (`todo/`) rather than an underspecified idea because
the investigation has bounded host-config, lifecycle, compatibility, and
file-touch questions with named evidence surfaces. It does not authorize an
implementation architecture.

The existing hosted path proves direct attachment is possible when the daemon
owns process creation: it mints a per-process bearer, binds it to session
context, and supplies the URL and token to the harness without a launcher
(`agents-plugin-tool/internal/wsagent/mcp_session.go:14-31,78-116`). Claude and
Codex adapters then inject that HTTP server into the child configuration
(`agents-plugin-tool/internal/wsagent/claude.go:250-274`,
`agents-plugin-tool/internal/wsagent/codex.go:224-236`), and start/rejoin logic
restores the tuple for a held process
(`agents-plugin-tool/internal/wsagent/runner_process.go:379-418`). A
user-started session has no equivalent daemon-owned process-start event, which
is the central bootstrap gap.

## A. Host HTTP MCP configuration and token delivery

### Verified now

- The shipped Codex compatibility manifest points to
  `agents-plugin/.mcp.json`, whose ws server is currently stdio through
  `ws-mcp-launcher.py` (`agents-plugin/.codex-plugin/plugin.json:15-17`,
  `agents-plugin/.mcp.json:2-11`). The shipped Claude manifest likewise declares
  the launcher inline as a stdio server
  (`agents-plugin/.claude-plugin/plugin.json:17-30`). No shipped plugin manifest
  currently declares the daemon HTTP route or a bearer source.
- Claude Code plugin MCP entries may be declared in plugin-root `.mcp.json` or
  inline in `plugin.json`; remote entries accept `type: "http"`, with
  `streamable-http` accepted as an alias, and may carry headers. Claude expands
  environment variables in `url` and `headers`, and a plugin `userConfig`
  secret can be substituted directly into a header. These behaviors are
  documented by the official [Claude Code MCP reference](https://code.claude.com/docs/en/mcp)
  and [plugin manifest reference](https://code.claude.com/docs/en/plugins-reference).
  The current hosted adapter uses exactly `Authorization: Bearer
  ${WS_MCP_SESSION_TOKEN}` (`agents-plugin-tool/internal/wsagent/claude.go:265-274`).
- Codex compatibility plugins can bundle an HTTP server in `.mcp.json`; the
  official [OpenAI plugin packaging guide](https://developers.openai.com/plugins/build/plugins)
  shows both portable `type: "streamable-http"` and compatibility `.mcp.json`
  URL forms. Codex configuration supports `bearer_token_env_var`,
  `env_http_headers`, static `http_headers`, and a local
  `http_headers_helper`, per the official
  [Codex configuration reference](https://learn.chatgpt.com/docs/config-file/config-reference).
  The repository manual also records plugin-managed HTTP support and per-thread
  bearer injection (`ai-docs/manuals/codex-integration.md:46-86,123-125`). The
  current hosted adapter supplies the bearer through the child environment and
  names it with `bearer_token_env_var`
  (`agents-plugin-tool/internal/wsagent/codex.go:53-62,224-236`).
- Existing hosted tokens are per process, generated by the runner, resolved to
  the stdio-equivalent hello, and voided with the process/session lifecycle
  (`agents-plugin-tool/internal/wsagent/mcp_session.go:18-31,78-116,151-180`).
  They are not a pre-existing machine credential that a user-started host can
  discover from a static plugin manifest.

### Open

- Verify against installed Claude Code and Codex plugin loaders that the exact
  proposed HTTP/auth fields work from these packages' current compatibility
  manifests, not only from project/user MCP configuration or newer portable
  plugin format. Codex's runtime config fields are verified, but their complete
  pass-through from compatibility `.mcp.json` still needs a fixture or live
  plugin probe.
- Decide who mints and revokes the bearer for a user-started session, and how
  the host receives it before its first MCP connection without embedding a
  rotating secret in the repository, plugin archive, process arguments, or a
  per-session launcher process.
- Determine whether a connection-time header helper can safely query a local
  supervisor for a short-lived token on both hosts. Claude documents
  `headersHelper`; Codex documents `http_headers_helper`, but host parity,
  plugin trust prompts, restart behavior, and the helper's process/file-touch
  cost need measurement.
- Define how direct HTTP attachment carries the current launcher's per-session
  context: cwd/project root, harness identity, caller environment, and plugin
  policy. The existing proprietary hello carries those fields
  (`agents-plugin/bin/ws-mcp-launcher.py:1489-1508`); a URL plus bearer alone
  does not establish their replacement.

A daemon cannot perform cold-start work while absent. |

### Open

- Choose the minimal always-on authority: daemon plus an external bootstrap
  stub, a small dedicated supervisor, an existing desktop controller, or an OS
  user service. "The daemon supervises itself" is incomplete unless another
  component starts it when absent and replaces its executable when required.
- Specify supervisor ownership and discovery across independent Claude, Codex,
  Pi, dashboard, dev rebuild, and installer lifecycles. Resolve which package
  version supplies the supervisor and which numeric core wins.
- Decide whether build-from-source remains a local-devenv-only action invoked
  explicitly, rather than an automatic responsibility of the always-on
  component.
- Establish direct-host reconnect semantics. Today the launcher fails sent
  requests with unknown outcome, queues only unsent requests, and replays MCP
  initialization after reconnect (`agents-plugin/bin/ws-mcp-launcher.py:2080-2136`).
  Host-native reconnect must be compared before removing that behavior.

## C. Cross-version compatibility

### Verified now

- MCP configuration and the `/mcp` hello are cross-version surfaces, so a
  concrete design must state a directional T0-T4 verdict before release
  (`AGENTS.md:106-123`). T3 means an old binary is blocked from running or
  connecting and requires a minor bump plus explicit owner approval
  (`AGENTS.md:119-123`; `ai-docs/manuals/release-compatibility.md:52-65,142-147`).
- Current old/new-minor behavior is already a T3 connection boundary: the
  launcher refuses a daemon outside its minor and tells an older session to
  update and restart when the daemon is newer
  (`agents-plugin/bin/ws-mcp-launcher.py:1879-1887`;
  `ai-docs/manuals/release-compatibility.md:26-38,107-108`).
- The HTTP session route has a known downgrade-only failure against a daemon
  predating `/mcp/session`; the release scenario sheet records the resulting
  functional degradation and recovery path
  (`ai-docs/manuals/release-compatibility.md:116-116`).
- Changing only a newly installed plugin manifest does not rewrite an older
  installed plugin: that old plugin continues to start its stdio launcher from
  its own package (`agents-plugin/.mcp.json:2-11`,
  `agents-plugin/.claude-plugin/plugin.json:17-30`). Its outcome therefore
  depends on whether the successor daemon retains the launcher's authenticated
  upgrade route and hello contract.

### Open

- Prove the directional matrix for old launcher -> new supervised daemon, new
  direct-HTTP plugin -> old daemon, downgrade after token issuance, daemon
  replacement during a direct session, and supervisor/plugin version skew.
- Determine whether retaining both the legacy launcher route and the new direct
  HTTP route makes old launcher -> new daemon T0. If the new architecture
  removes or refuses the old route/hello, that direction is T3, not a
  tool-list-refresh issue.
- Decide whether a direct-HTTP plugin can detect an old route-less daemon and
  trigger safe upgrade/restart, or must fail with a T3 update boundary. Cite
  the exact old/new read, write, refusal, and recovery lines in the eventual
  verdict as required by `ai-docs/manuals/release-compatibility.md:52-71`.

## D. File-touch and process budget

### Verified now

- Target Windows systems scan every file touch at an estimated 10-100x clean
  machine cost; the required unit is file operations per user action measured
  on a Windows PC with heavy security software
  (`ai-docs/manuals/performance.md:7-10,63-73`).
- Runtime state should be memory-first, recovery should use delta appends,
  handles/locks should stay open, interactive paths must not wait on file I/O,
  and a process should spawn only when no in-process route exists
  (`ai-docs/manuals/performance.md:14-40`).
- Each current user session necessarily starts one Python launcher process and
  one daemon socket. Launcher startup also reads runtime/endpoint metadata and
  may stat/hash/install/stage the runtime before daemon start; hash memoization
  lasts only for that launcher process
  (`agents-plugin/bin/ws-mcp-launcher.py:154-160,1644-1686,1697-1703,2301-2384`).
  A healthy compatible daemon avoids some install work, but not the per-session
  Python process.

### Open

- Measure before/after process launches, file operations, and connection
  latency for one session start, N concurrent session starts, daemon cold start,
  compatible warm attach, source rebuild, update replacement, crash restart,
  and token refresh on the owner's Windows baseline.
- Bound supervisor persistence to startup/recovery state: no heartbeat file
  rewrites, no per-attach endpoint/token file rereads, held locks/handles where
  needed, and zero file I/O on normal MCP calls.
- Include header-helper cost if selected. Replacing one long-lived launcher
  with one short-lived helper per connection may save resident processes while
  retaining process-scan and file-touch costs.

## Research completion criteria

Research is complete when it records: verified host-plugin fixtures for HTTP
and secret delivery; the chosen cold-start/update/replacement owner; the
session-context and token lifecycle; a directional compatibility matrix with a
settled tier; and measured Windows file/process costs against the current
launcher baseline. Any implementation ticket must derive authority only from
the Outcome Ledger.

## Outcome Ledger

### Verified Findings

- [VERIFIED] Claude Code and Codex support streamable HTTP MCP plus bearer/header
  authentication, and the hosted ws runner already uses those mechanisms when
  it owns process creation. Exact evidence is in sections A and Background.
- [VERIFIED] The shipped user-facing plugin configurations still start
  `ws-mcp-launcher.py` over stdio, so each user-started session retains a Python
  proxy process. Exact evidence is in section A.
- [VERIFIED] The launcher currently owns runtime acquisition/build/verification,
  daemon lifecycle coordination, compatibility errors, environment/context
  construction, authenticated proxying, and reconnect behavior. Exact evidence
  is in section B.
- [VERIFIED] A daemon alone cannot cover cold start while absent; some external
  activation authority remains necessary. The current external authority is the
  launcher's serialized `daemon-start` path (`agents-plugin/bin/ws-mcp-launcher.py:1752-1877`).
- [VERIFIED] Compatibility can be T0 only for behavior-preserving retained paths;
  blocking the old launcher or old HTTP route is T3. The exact tier remains
  design-dependent and unsettled.
- [VERIFIED] Performance policy favors eliminating per-session processes and
  repeated file reads, but requires Windows before/after measurement rather than
  an assumed win.

### Confirmed Decisions

- None. Owner decision (1872)=a preserves this research question but does not
  choose a supervision or token architecture.

### Proposals

The following are non-authoritative candidates, not implementation direction:

- Prefer a small long-lived supervisor (or an existing long-lived controller
  with the same role) as the cold-start/build/version/replacement authority,
  while the daemon owns live MCP service and session admission.
- Retain the legacy launcher upgrade route through a compatibility window while
  adding direct HTTP attachment, aiming for T0 old-launcher -> new-daemon
  behavior; do not remove the launcher path in the same patch that introduces
  direct attachment.
- Mint short-lived per-session bearers through a connection-time local
  registration/helper exchange, keeping secrets out of manifests and argv. Use
  a machine-wide endpoint bearer only if its exposure, rotation, and
  multi-session context binding are explicitly accepted.
- Keep build-from-source explicit for local devenv, with the supervisor able to
  select a verified already-built runtime; measure before assigning automatic
  source walks/builds to an always-on loop.

### Open Questions

- Which supervisor/activation mechanism satisfies all hosts without adding a
  second per-session process or a new mandatory desktop dependency?
- How does a user-started host obtain and refresh its bearer and register
  project/harness context before the first HTTP MCP request?
- Do both current plugin compatibility loaders accept the exact dynamic-header
  fields needed, and how do they report auth/version failures?
- What is the settled compatibility tier for every direction in section C?
- What are the measured Windows process, file-operation, and latency deltas for
  the scenarios in section D?

### Rejected Alternatives

- None. No architecture has yet been selected or rejected by the owner.
