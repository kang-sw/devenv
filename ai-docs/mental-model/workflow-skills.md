# Workflow Skills

## Entry Points

- `agents-plugin/skills/lead-*` holds the 16 directly user-invocable `ws:` entry skills; uses `ws:` skill names plus `ws/<tool>` MCP notation. {#260505-lead-skill-namespace-surface}
- `agents-plugin/rsrc/lead-*/` holds procedure bodies for all lead-* workflows — entry-skill bodies (e.g., `lead-proceed`, `lead-discuss`, `lead-bootstrap`) and internal-only procedures (e.g., `lead-implement`, `lead-write-ticket`, `lead-workflow-manual`); all are invoked via `ws/playbook.print(name: "<name>")` and executed inline. Entry-skill playbooks have a corresponding `SKILL.md` shim; most shims are a single print-and-execute line, but context-heavy entry skills (`lead-discuss`, `lead-sprint`) carry a parallel init declaration — `playbook.print` + `workflow_manual` in parallel — so the workflow manual loads in the same round as the procedure body; internal-only playbooks have no user-invocable shim. `lead-prefer-subagent` and `lead-verify-discussion` are exceptions: their bodies are inlined directly as static `SKILL.md` text (no rsrc playbook, no `playbook.print` indirection). {#260609-rsrc-playbook-distribution} {#260610-entry-skill-surface-reduction}
- `agents-plugin-wsflow/skills/lead-*` is the wsflow entry-skill surface: package-local bare `name: lead-*` frontmatter plus a shim delegating to shared rsrc playbooks rendered in wsflow product mode. Most wsflow shims are a single `wsflow/playbook.print` call; context-heavy skills (`lead-discuss`, `lead-sprint`) use the same parallel pattern as their ws counterparts with `wsflow/` namespace prefixes. {#260513-wsflow-agentless-skill-surface}
- The `lead-workflow-manual` playbook is the notation and primitive boundary reference for shared skill text; load it via `ws/playbook.print(name: "lead-workflow-manual")` (ungated) or through `ws/workflow_manual(session_key)` (lead-only, role-gated). {#260505-workflow-primitive-reference}
- `agents-plugin/skills/lead-revive/` and `agents-plugin-wsflow/skills/lead-revive/` are the post-compaction manual-restore entry skills (inline-body launchers, no rsrc playbook); they call `ws/workflow_manual` with the sentinel for fresh start and carry the compaction-recovery pointer for the lead when the session key is lost. When the working root is already known at bootstrap time, `ws/workflow_manual(session_key: <sentinel>, root: <abs-path>)` mints the lead key inline and returns `## Session Key` + `## Session State` without a separate `ws.ferrule` call; omitting `root` preserves the prior two-step flow. {#260626-post-compaction-session-restoration}

## Module Contracts

- Codex skill directory names and `name:` frontmatter are externally visible invocation strings; renames break user workflows.
- Codex-facing workflow guidance teaches MCP primitives first; CLI adapter syntax belongs only in compatibility or testing references. {#260507-mcp-centric-workflow-language}
- Agent and wsflow subagent prompts are written in English; user-facing lead discussion may still use the active conversation language. {#260505-workflow-primitive-reference}
- Skills delegate scoped codebase fact-finding via direct host-native exploration-worker dispatch: spawn a host-native worker with an English prompt that includes the scoped question or purpose-specific query block, collect cited evidence plus gaps before synthesizing, and spawn parallel surveys in one turn when possible. `ws/subquery` is removed; the generic `explore` render playbook is fallback/compatibility only for unknown or unsupported harness contexts, not the normal skill guidance path. {#260610-subquery-explore-delegation-shift} {#260609-rsrc-playbook-distribution}
- Shared workflow examples use `model: light|core|deep` as portable delegate aliases (read-compat synonyms for the `small`/`medium`/`large` capability tiers); concrete provider names are reserved for intentional overrides. The `tier:` frontmatter is the single tier vocabulary (`small`/`medium`/`large`/`xlarge`; `light`/`core`/`deep` accepted as read-compat) — `playbook.render` surfaces it as `recommended-tier` and the `lead-implement` review-allocation default speaks it (correctness `large`, fit/test `medium`). See spec `#260612-first-class-tier-vocabulary` and `#260620-tier-vocabulary-collapse-direct-model-map`. {#260508-workflow-model-alias-guidance}
- Skill descriptions are the runtime trigger surface: keep top-level entries strong, derived primitives lighter, and conditional utilities explicit. {#260508-skill-description-attention-policy}
- `lead-add-rule` requires explicit persistence intent such as save, remember, persist, or add a durable rule; prescriptive task wording alone must not trigger it. {#260508-add-rule-explicit-persistence-trigger}
- Skill-to-skill handoffs share the active conversation; do not declare carry blocks, and reserve argument language for MCP tools, CLIs, and templates. {#260514-skill-authoring-carried-context}
- User-approval gates in skills fire only on direct user invocation; chained invocations re-ask only for safety, deletion, or explicit consent rules. {#260514-skill-authoring-carried-context}
- Dense skill routing should use Markdown hierarchy, grouped invariants, fixed lookup tables, responsibility-named handler sub-blocks, and command-shaped lists before custom notation; skill, agent, and prompt edits run a no-prior-context fresh-reader audit through a separate reviewer that is instructed to read only the target file or excerpt, the lead edits only findings classified as fix, and audit/revision loops stop after at most three cycles. {#260514-skill-authoring-carried-context}
- `lead-skill-authoring` invariant audit covers both `agents-plugin/skills/*/SKILL.md` entry skill files and `agents-plugin/rsrc/lead-*/lead-*.md` procedure playbook files; apply the invariant checklist before shipping changes to either surface. {#260514-skill-authoring-carried-context}
- `lead-tune` loads `config.tuning` first and treats that catalog as the source of supported knobs, writer tools, field options, and current values; keep routing prose compact and do not duplicate writer enums in the playbook. {#260619-lead-tune-workflow-tuning-skill} {#260625-tuning-catalog}
- `"workflow.prefer_subagent"` is the global bootstrap posture knob consumed by keyless `lead-workflow-manual` rendering: when it is `on`, loading the manual also loads the rendered `lead-prefer-subagent` posture inside a `<playbook name="lead-prefer-subagent" title="Prefer Subagent">` boundary. When it is `off`, orchestration-heavy skills that require the strict posture must still load or invoke `lead-prefer-subagent` explicitly.
- `lead-prefer-subagent` is a maximum-delegation posture: every delegated task routes to a fresh spawn built from named artifacts plus general constraints, while the lead only routes, collects, adjudicates, asks, and synthesizes. The sole inline-execution carve-out is a central authoring/mutation whitelist the skill owns: durable-artifact authoring or mutation (tickets, specs) stays with whichever session already holds the authoritative context for the decision — lead-inline when settled in this conversation, the delegated subagent's own continuing session when settled there. The fork-style full-conversation-context delegation mechanism was removed entirely (no partial retention behind a flag); it is not a routing option. The skill body is static text inlined directly in `agents-plugin/skills/lead-prefer-subagent/SKILL.md` (loaded via `LoadSkillBody`, no override-marker pass), identical across harnesses; there is no per-harness override slot for this point. {#260505-workflow-primitive-reference}
- `lead-proceed` routes through handoff stages and captures the `Ticket:` line from `lead-write-ticket`; changing that artifact breaks chaining. {#260505-proceed-routing-pipeline}
- `lead-proceed` must stop on epic and workset ticket paths because they are board artifacts; implementation routes through child or included actionable tickets. {#260505-proceed-routing-pipeline} {#260524-workset-workflow-skill-routing}
- `lead-proceed` gathers route facts, calls `ws.enter.proceed` for deterministic verdict resolution, then follows MCP's `Next:` instruction instead of restating a separate Routing Verdict or local follow-step; entry skills (`ws:lead-discuss`) are invoked directly, internal procedures (`lead-implement`, `lead-write-ticket`) are invoked via `ws/playbook.print(name: "<name>")` and executed inline; when `NEXT: lead-implement`, the playbook call must precede source inspection, planning, or editing. {#260505-proceed-routing-pipeline} {#260519-proceed-implementation-dispatch-precheck}
- `lead-proceed` treats `idea/` and `todo/` ticket paths as implementation intent, routes them through `lead-write-ticket` for triage, refresh, or ready promotion rather than pre-routing through `lead-write-spec`, and escalates only for unresolved design or spec-address/readiness blockers. {#260505-proceed-routing-pipeline}
- `lead-proceed` can route a ticketless inline request to `lead-implement` when accepted work is one bounded reviewable slice recoverable from its eventual implementation commit plus any relevant existing spec, regardless of file count or public surface. After required discussion, multiple independently reviewable phases or pre-implementation traceability beyond those artifacts still require a ticket; the normal `lead-discuss -> lead-write-ticket -> ticket -> lead-proceed` path is unchanged. {#260505-proceed-routing-pipeline}
- `lead-proceed` does not rejudge ticket decomposition; absent an explicit phase name, it selects the first unfinished phase and treats that phase as hard downstream scope. {#260505-proceed-routing-pipeline}
- `lead-proceed` keeps ticket freshness lead-owned: compare active conversation decisions against the ticket only, refresh through `lead-write-ticket` when settled decisions are missing, and stop for discussion when freshness is uncertain. {#260513-proceed-ticket-freshness-gate}
- Migration-sensitive workflow turns load `260605-research-ws-native-subagent-pivot` before answering or implementing; `lead-proceed` treats a missing anchor as a stop, and delegated `lead-implement` copies binding anchor constraints into the implementation plan before executor dispatch. {#260513-proceed-ticket-freshness-gate} {#260505-implementation-workflow-skills}
- `lead-implement` delegated mode handles public or cross-module contract work; contract checkpoints live in the implementation plan, not in generated skeleton artifacts. {#260512-skeleton-inside-implement-branch}
- `lead-implement` continues on existing `implement/*` or `impl/*` branches, normally creates `impl/<stem>` (stem <=15 characters recommended) before source edits elsewhere, may safely rename implementation branches before execution, closes docs before the final gate, and treats merge as one user-approved final action. Legacy `implement/*` branches are still recognized for in-progress work. The sole isolation exception is MCP-derived `Branch Action: current`: a named non-implementation branch with a real non-`(initial)` start commit may be retained only for an inline target whose raw facts independently satisfy automatic direct-edit and lead-only review, with automatic review selection and an explicit documentation-skip reason, and whose caller clearly requested a low-ceremony flow through `policy.low_ceremony_if_safe=yes`. That preference is necessary but non-authoritative: it is judged independently from direct-edit and documentation policy, and it waives no safety, verification, review, documentation, confirmation, or closeout gate. Caller overrides and near misses cannot authorize the exception. {#260505-implementation-workflow-skills} {#260707-impl-branch-convention-autodelete}
- `lead-implement` gathers implementation facts first, calls `ws.enter.implement`, and follows the MCP-authored Implementation Verdict before Prep. MCP owns branch action, delegation, plan depth, review allocation, review need, doc mode, agenda storage, todo replacement, and verdict-derived todo instruction prose; the always-rendered playbook owns ambiguous fact gathering plus shared templates, then treats the replaced todo list as the post-verdict runbook. `Branch Action: stop` is a hard pre-edit blocker whose todos should keep later prep/edit/review/doc work visibly unreachable; `Branch Action: current` instead omits final-action and merge work and ends with focused verification, one logical explicit-path commit, lead-owned review, and retained-branch/commit-range reporting without a push. {#260505-implementation-workflow-skills}
- Automatic `review_alloc` uses independent correctness, fit, and test risk partitions: zero or one partition yields the delegate-grade generic `reviewer` over the shared full-scope `code-reviewer` contract, and two or more yield partitioned review. Public-interface and existing-test surfaces alone do not add partitions; material risks, contracts/public symbols, cross-module/reuse uncertainty, and new or unknown test surfaces do. Explicit overrides remain authoritative. {#260505-implementation-workflow-skills} {#260612-reviewer-allocation-tier-default}
- `lead-implement` initial implementer dispatch is file-first: render `implementer` with declared path/metadata inputs (`PlanPath`, verification hint, result expectations, commit-range hint), pass only the rendered prompt path to the worker, and keep recommended tier as lead dispatch metadata. The implementer prompt treats the plan and listed references as the contract and blocks ticket-file reads unless the plan's `Escalations` section explicitly authorizes ticket-file reading. {#260505-implementation-workflow-skills} {#260505-workflow-delegate-prompt-boundaries}
- wsflow `lead-implement` is the converged unified spine (no separate `lead-edit`): Edit is lead-owned direct edits plus optional scoped native subagents with no implementer stage, and survey/plan/review/mental-model delegate prompts dispatch through wsflow-mode `playbook.render` to native subagents rather than ws named agents. {#260529-wsflow-converged-implement-spine}
- `lead-implement` compacts only safe documentation-only branch-tip closeout suffixes before merge readiness; planning, ready-promotion, source, test, review-fix, merge, ambiguous-authorship, and non-documentation commits are preserved and reported as skipped. Approved merges may fast-forward a single workflow-owned, message-clean commit; multiple-commit branches default to no-fast-forward unless each commit is independently deployable and independently revertible, while one logical change with noisy or dependent commits squashes. {#260523-implement-doc-closeout-compaction}
- `lead-write-ticket` Sage Review Gate is two sequential stage gates keyed to landing status: `sage-review-design:` at `todo/` dispatches only `ticket-reviewer-design` (tier: large); `sage-review-completeness:` at `ready/` dispatches only `ticket-reviewer-completeness` (tier: medium), after first confirming `sage-review-design` is terminal (never-skippable design invariant). Each field independently resolves `skipped`/`recommended`/`required` the same way the old single field did. Category exemptions: `epic` needs design only; `research`/`workset` are exempt from both. Both reviewer playbooks are internal delegate-only — no wsflow shim, no `EXPECTED_SKILLS` entry, not user-invocable. See spec `{#260624-sage-review-gate}`.
- `lead-write-ticket` runs the spec-address gate only when non-`epic`, non-`research`, non-`workset` work enters `ready/`; `todo/` is accepted backlog with optional spec recovery hints. {#260505-planning-workflow-skills} {#260524-workset-workflow-skill-routing}
- `lead-write-ticket` accepts existing spec stems, `spec-remove:`, or ticket-local `## Spec Impact` for ready addressing; it invokes `lead-write-spec` only for contract-first planned spec entries. {#260505-planning-workflow-skills}
- `lead-write-ticket` keeps epics at milestone-board scope and routes detailed discussion, implementation phases, and phase-specific decisions into child tickets; child-ticket phases are complete fresh-session implementation units, not internal task lists. {#260508-write-ticket-epic-child-boundary}
- `lead-write-ticket` keeps worksets non-hierarchical: inclusion never changes `parent:`, planned entries go under `## Planned References` until real tickets exist, and implementation detail or settled constraints move to the relevant included actionable ticket or phase. {#260524-workset-workflow-skill-routing}
- `lead-write-ticket` preserves settled decisions before brevity: actionable child tickets record enough contract, agreed strategy, rejected-alternative, verification, and binding cross-ticket detail that a fresh implementation session cannot produce a materially different caller-visible, workflow, API, or verification result without contradicting the ticket. {#260516-write-ticket-related-ticket-propagation}
- `lead-write-ticket` writes only user-confirmed discussion decisions; discussion-derived cleanup runs an Open Decision Queue, uses the harness task-list guidance from playbook-local `task-list[.<harness>].md` fragments, and omits open/rejected/deferred items unless the user approves recording their status. {#260505-planning-workflow-skills}
- `lead-write-ticket` reviews related-ticket decisions by default; explicit cascade wording broadens the pass to board and multi-ticket edits, with epics board-level, worksets operating-context-only, and no implicit ready promotion. {#260516-write-ticket-related-ticket-propagation} {#260524-workset-workflow-skill-routing}
- `lead-discuss` uses the user's active conversation language for discussion responses. {#260505-planning-workflow-skills}
- `lead-discuss` response shape keeps the load-bearing point, evidence/gap, and user decision adjacent; do not bury the actionable point inside exhaustive option lists. {#260505-planning-workflow-skills}
- `lead-discuss` searches the ticket/spec/mental-model cascade before answering undocumented architecture facts; commit history is an additional tier — `## AI Context` bodies carry decision rationale not yet reflected in docs, accessed via Explore-type subagent dispatch rather than inline reads. Reports when no documented answer exists instead of filling gaps from memory. {#260505-planning-workflow-skills}
- `lead-discuss` routes explicit implementation intent through `lead-proceed`; persistence-only discussion still feeds `lead-write-spec` and `lead-write-ticket`. {#260505-planning-workflow-skills}
- `lead-discuss` uses symbolic-label Intent Frames for proposal, evaluation, design-direction, causal-claim, scope-assumption, and trade-off turns; Interview Workflow starts only when unresolved branches need user priority or scope input. {#260510-discuss-intent-frame-interview}
- `lead-verify-discussion` is a small explicit checkpoint for refreshing discussion premises, finding reusable existing implementation, validating direction, naming over-alignment risks, testing the best countercase, and steering from corrected assumptions via scoped Explore-style subagents when investigation is useful (conditional, not guaranteed per run); keep it compact, callable, and lightweight. The skill body is now static text inlined directly in `agents-plugin/skills/lead-verify-discussion/SKILL.md` (loaded via `LoadSkillBody`, no `playbook.print` indirection); it no longer carries a `delegates:true`-driven continuity/mercenary-path tip, since that unconditional append was a poor fit for this checkpoint's conditional, lightweight delegation shape (see `260703-chore-prefer-subagent-verify-discussion-inline-mirror` Phase 2). {#260512-discussion-verification-skill}
- `lead-goal-step` advances a goal-pursuit run by one step: select and dispatch exactly one ticket from `ready/`, the sole progress gate. It never lists `ready/` or reads ticket files itself: it spawns a light-tier Explore-style subagent to pick the next ticket (a `related:`/`parent:` frontmatter-named prerequisite if one is also in `ready/`, otherwise the oldest by FIFO) and return exactly one path, or report the queue empty. The lead then hands off to `lead-proceed` with that returned path as an explicit target — it never calls `lead-proceed` bare, stops with no handoff when the subagent reports `ready/` empty, and never loops internally over `ready/` (the `/goal` Stop-hook owns repeated draining, degenerating this skill to a single-cycle shim outside a goal run). Beyond selection it also directs the lead to delegate everything else for the invocation, including simple tasks like commits, to a subagent per `lead-prefer-subagent`, to conserve lead context across a long-running goal. The skill is deliberately short: a purely user/`/goal`-invoked shim, not a heavier discussable workflow skill. The skill body is inlined directly in `agents-plugin/skills/lead-goal-step/SKILL.md` (no rsrc playbook, no `playbook.print` indirection), mirroring the `lead-verify-discussion`/`lead-prefer-subagent` inline-body shape. It also carries explicit ticket-curation authority — editing existing tickets and creating/linking new ones through `lead-write-ticket`, with no new ticket-system state field — and bounded in-scope bug-capture routing (goal-relevant/blocking bugs to `ready/`, incidental bugs to `idea/`, explicitly deferred bugs captured only), judged skill-intrinsically rather than against any downstream project's own dogfood-capture convention. {#260703-drain-ready-queue-skill} {#260723-goal-step-ticket-curation-authority}
- `lead-goal-step` is goal-branch-staging aware: the lead itself (not the ticket-selection subagent) checks, before each dispatch, whether an active `/goal` Stop-hook reminder is present and the current branch is not already `goal/*`; when both hold it captures the current branch as the fork PARENT (`git rev-parse --abbrev-ref HEAD`, with a detached-HEAD guard that aborts staging instead of producing `goal/HEAD/<slug>`), derives an arbitrary random branch-safe slug (never from the goal text, to avoid collisions across concurrent runs), and creates/checks out `goal/<parent>/<slug>` via plain `git` commands before handing off. While staged on `goal/<parent>/<slug>`, the handoff to `lead-proceed` adds `policy.branch.merge_confirm: "skip"` as explicit caller policy — no `merge_target` override needed, since `deriveImplementBranchPlan`'s create-path already derives the merge target from the checked-out branch (`agents-plugin-tool/internal/mcp/implement_resolver.go`) — so each ticket still merges into the goal branch through its own `impl/<stem>` branch without asking. When the selection subagent reports `ready/` empty and the current branch is `goal/<parent>/<slug>`, the skill performs the run's single confirmed final merge itself, directly in its own prose (not via `lead-proceed`/`lead-implement`, since `enter.implement` requires a ticket target this ticket-less step cannot supply): derive PARENT and SLUG from the branch name by stripping the `goal/` prefix and splitting on the last `/` (old-format single-segment `goal/<slug>` falls back to `main` as the merge target), ask the user for explicit approval, then merge `goal/<parent>/<slug>` into `<parent>` (or the `main`-fallback equivalent) with plain `git` commands, never pushing. Outside an active `/goal` context, or once already off a `goal/*` branch, behavior is byte-identical to the pre-staging shape above — no branch creation, no `merge_confirm` override, no local staging state beyond the checked-out branch name. The step also has a second clean terminal beside empty-queue completion: a blocked-progress conclusion, reached only when every remaining `ready/` ticket is blocked (not merely one among otherwise-workable candidates) and the selection subagent's advanceable-now read (skipping tickets with a recorded blocker note, replacing the old body-blind FIFO pick) finds nothing left to advance. This conclusion reports the recorded blocker(s) and ends the run without ever running the empty-queue completion's merge-approval flow, and is discriminated from a hard-gate pause (work remains, only sign-off is pending) so a pause can never be reclassified as goal-complete. Recording the blocker onto the ticket itself before yielding is a non-skippable step, mirroring the sage `## Blocked (YYYY-MM-DD)` precedent, since an unrecorded blocker causes the next turn's selector to re-pick the same stuck ticket. {#260707-drain-goal-branch-staging} {#260723-goal-step-blocked-progress-conclusion}
- `lead-verify-design` is removed; its `SKILL.md` and rsrc playbook were deleted entirely (delete-don't-diet decision, `260630-epic-skill-playbook-diet`), zero call sites. - Sprint is an episode shell: only one-context lead-owned `sprint-edit` changes stay inside it, and each marked episode runs its own documentation closure when wrapped. {#260505-sprint-session-container}
- wsflow sprint mirrors the episode shell: sprint-edit applies a lead-owned direct edit, while larger or subagent-worthy work routes through normal wsflow workflow gates (the converged wsflow `lead-implement` spine). {#260513-wsflow-agentless-skill-surface} {#260513-wsflow-sprint-skill}
- wsflow mirrors proceed route clarity with a single-next-hop Routing Verdict and no pre-applied `wsflow:lead-implement` branch or execution judgments. {#260519-proceed-implementation-dispatch-precheck}
- `lead-review` loads `ai-docs/_review.local.md` for all environment-specific configuration (remote, phases, comment/merge/notification methods); when absent, it interviews the user and writes the config before the first review runs. {#260513-review-workflow-skill}
- `lead-review` routes NEEDS FIX local-fix through `lead-discuss` with findings as context; re-review after fix is user-discretion, not automatic re-entry. {#260513-review-workflow-skill}
- `lead-review` judge `follows-ws-workflow` auto-detects conventional commits and `## AI Context`; PARTIAL (some commits qualify) counts as NO (conservative); the `## Contributor Workflow` config setting can force YES or NO. {#260513-review-workflow-skill}
- `lead-review` judge `is-large-diff` uses subagents for parallel alignment and risk phases when diff exceeds the configured threshold; both depth judges are independent and combinable. {#260513-review-workflow-skill}

## Coupling

- Skill text that names a delegate playbook must match an rsrc playbook name under `agents-plugin/rsrc/` (manifest-checked), not an embedded prompt stem.
- Playbook-local include fragments live beside their owning playbook and resolve before root-level include fallbacks; they are not standalone playbook variants. Use this for harness-local guidance, not shared reviewer bases.
- Legacy skeleton prompts may remain bundled for compatibility; normal implementation routing does not register skeleton-populator or skeleton-reviewer.
- Discuss ready-promotion logic routes through `lead-write-ticket`; direct moves bypass the ready spec-address gate and focus checks.
- Moving updater dispatch into the Edit stage can double-run documentation updates; implementation doc pre-pass and sprint-edit episode closure own their separate doc pipeline calls.
- `lead-salvage` routes ticket writes through `lead-write-ticket`; direct ticket graph mutation inside salvage would bypass ticket conventions and commit handling.
- Bootstrap guide semantics stay host-neutral; root `CLAUDE.md` only delegates to `AGENTS.md`.
- Bootstrap template changes must check both ws and wsflow packages; matching behavior may use different template version numbers because each package owns its own downstream lineage.

## Extension Points & Change Recipes

- **Add a Codex workflow skill**: for a user-invocable entry skill, create both (a) a thin-shim `agents-plugin/skills/lead-<name>/SKILL.md` (frontmatter + H1 + single `ws/playbook.print(name: "<name>")` execute line) and (b) the full procedure body at `agents-plugin/rsrc/lead-<name>/lead-<name>.md` as a `kind:print` playbook (set `delegates:true` if it spawns subagents). For an internal-only procedure (no user shim), create only the rsrc playbook. Then wire the wsflow surfaces in the same change: add the wsflow shim `agents-plugin-wsflow/skills/lead-<name>/SKILL.md` (same shape but `wsflow/playbook.print` + the "If the playbook cannot be loaded…" sentence), add the stem to `EXPECTED_SKILLS` in `agents-plugin-wsflow/tests/test_wsflow_skill_bundle.py`, and regenerate both rsrc manifests and the byte-identical wsflow rsrc mirror with `WS_REGEN_MANIFEST=1` then `WS_REGEN_WSFLOW_RSRC=1 go test ./internal/wsrsrc -count=1 -run <regen-test>` (the `-count=1` is mandatory — the cache silently no-ops otherwise). Wrap any agent-backed-only content in `ws:full-only` markers and narrow the wsflow shim description to match, since `config.agents_tier`/`config.workflow_prefer_mercenary`/`ws.mercenary.*`/`exec.*` are hidden in agentless wsflow; `config.workflow_prefer_subagent` remains shared. Follow skill-authoring invariants and run the Fresh-Reader Audit for both surfaces; add OpenAI UI metadata only for entry skills; update workflow specs and mental models. Entry skills are not listed in `runtime.json` (it lists MCP tools/commands, not skills).
- **Add a config-first review skill variant**: follow `lead-review` pattern — machine-local `ai-docs/_review.local.md` captures environment judgment, setup interview fires only when config is absent, judges gate subagent depth rather than hard-coding it.
- **Change a shared lead playbook visible in wsflow**: verify wsflow product-mode output and the `agents-plugin-wsflow` shim/package tests in the same logical change, or record a follow-up ticket when the wsflow surface cannot be checked.
- **Change a full workflow skill excluded from wsflow**: check `ai-docs/ref/wsflow-mirroring.md` and update wsflow docs, workflow manual text, or exclusion rationale if the excluded skill's meaning changed.
- **Change bootstrap baseline behavior**: update both `lead-bootstrap` packages when applicable, but bump each package's `AGENTS.template.md` version only inside that package's own lineage.
- **Add a delegate prompt to a workflow**: author it as an rsrc playbook under `agents-plugin/rsrc/` (regenerate `manifest.json`), then have the skill render it via `ws/playbook.render` and spawn native/mercenary — the `register(prompts:[stems])` path and its runtime prompt bundle metadata were retired (260611 Phase 6b). Keep reviewer/implementer context boundaries explicit. {#260505-workflow-delegate-prompt-boundaries}

## Common Mistakes

- Treating `lead-proceed` as an implementation skill; it routes, sends `todo/` tickets through ready promotion, selects scope slices, and does not read source.
- Skipping the workflow manual load (via `ws/workflow_manual(session_key)`, or `lead-revive` after compaction) before executing orchestration-heavy skills, which causes notation drift back to Claude shell helpers. The removed `lead-load-workflow-manual` shim is not a valid recovery path; use `lead-revive`.
- Editing downstream `ai-docs/WORKFLOW.md` as if it overrides installed ws tooling; upstream plugin/runtime semantics and bundled conventions remain canonical.
- Removing the final `Ticket:` artifact from write-ticket output.
- Reintroducing curated procedure bodies into wsflow skills; wsflow `SKILL.md` files are entry shims and shared rsrc playbooks own workflow intent.
- Relaying reviewer file contents instead of file paths, which breaks implementation review relay and inflates lead context.
- Treating brief compression as permission to drop settled caller-visible contracts, implementation strategy decisions, rejected alternatives, or verification expectations.
- Adding a second `enter.*` call in the same skill invocation (e.g., a second `enter.implement` after the plan is ready) — `enter.*` replaces the todo list; a second call discards the derived checklist. Extend session state through `agenda.set` instead.
- Using a hardcoded `ws.` namespace when calling `enter.*`, `agenda.set`, or other session-state tools in skill playbook text; use `{{.McpNamespace}}/` so wsflow product-mode namespace substitution applies.
