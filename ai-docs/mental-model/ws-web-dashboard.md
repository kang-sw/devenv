# ws Web Dashboard

## Domain Rules

- Any ws-dashboard frontend implementation that changes visible browser UI must include browser-level visual/interaction verification, preferably Playwright or equivalent screenshot/DOM automation against the daemon-served production frontend; pure TypeScript tests, Vite build, and curl/API dogfood are not sufficient to close UI-facing work.
- User-visible dashboard controls must expose stable command identities and route their mouse/click behavior through the same dashboard command dispatch path that future tmux-like prefix keybindings will invoke; terminal raw byte input is the narrow exception and must not fork shell input semantics.
- Dashboard terminal work must treat cross-platform behavior as part of the contract: shell selection, PTY commands, browser/harness tests, and control-key evidence must avoid POSIX-only assumptions or record explicit OS-scoped limitations.
- After owner authentication, ws-dashboard viewers have PC-owner-level visibility for dashboard-captured command/tool output: prefer bounded faithful rendering over redacting ordinary command output, and reserve redaction for daemon-private implementation metadata such as pairing tokens, session ids, cache/transcript storage paths, and unauthenticated diagnostics.

## Module Contracts

- Loopback is only a reachability default, not authorization: every browser route except `/pair` must pass owner-session auth before handler execution, including fallback paths. {#260515-ws-web-daemon-foundation}
- The pairing URL is constructed after the listener is bound so port `0` resolves to the actual socket; changing startup reporting must preserve a single owner-visible pairing URL without leaking it through request diagnostics.
- Server shutdown is signal-led rather than browser-connection-led: `server.rs` should start graceful shutdown but keep a bounded drain window so idle sockets, SSE streams, or WebSockets cannot make `dev.sh run` appear to ignore `Ctrl-C`. {#260515-ws-web-daemon-foundation}
- Valid `/pair?token=...` exchanges consume the token, install the owner cookie, and redirect to token-free `/`; missing, invalid, reused, or expired tokens must stay non-redirecting and cookie-free so browser history and retry paths do not retain usable pairing URLs. {#260516-ws-web-dashboard-token-free-pairing-landing}
- `OwnerAuthState` is cloned into Axum state, so auth storage changes must preserve shared one-time pairing consumption, pairing TTL enforcement before consumption, and rejection of session cookies before pairing succeeds.
- Bearer auth is a daemon-local protected-route exception for CLI/smoke callers; it authenticates before cookie pairing state is considered, so browser cookie flow changes must not accidentally remove or broaden that non-browser path.
- Authenticated browser requests and WebSocket upgrade requests pass conservative Host/Origin checks; missing headers are tolerated for ordinary clients, but clearly non-loopback hosts/origins fail before handler or upgrade behavior.
- Health output is deliberately exact and minimal (`ok\n`); host paths, cache paths, Git roots, wsstate data, diagnostics, pairing tokens, and session values belong only in authenticated diagnostic surfaces.
- Bind reachability and browser authorization stay separate: local/tunnel modes keep non-loopback hosts rejected, while public mode may accept non-loopback hosts only when owner auth remains enabled. Relaxing Host/Origin or route auth is not part of public bind enablement.
- The daemon is not ws MCP authority. The WorkRoot Activity view reads wsstate/wsagent cache state as a daemon-owned projection; it must not adopt the caller's MCP root, harness, model backend, or agent session ownership.
- Dashboard core exposes the physical open/spawn/run target as `workRoot`, not `worktree`; serialized resource paths must keep `workRootId` camelCase vocabulary so later HTTP routes and fixtures do not leak Git-worktree-specific names into the generic directory hierarchy. {#260516-ws-web-dashboard-core-resource-vocabulary}
- The resource view-model API preserves `server -> workspace -> workRoot -> mainInstance -> subInstance` as data even when rows are compactable; browser left-nav compaction is a presentation hint, not a route identity or daemon-side pre-collapse. The singleton row condition is per workspace: a workspace with exactly one workRoot renders as a compact row that selects the concrete workRoot id, keeps workRoot metadata visible, and ignores main/sub instance presence because instances are workbench surfaces/projections. {#260516-ws-web-dashboard-resource-view-model-contract} {#260523-ws-dashboard-single-workroot-nav-collapse}
- Frontend operation helpers treat `server-local` and omitted `serverId` as local compatibility routes, while non-local server ids produce canonical `/api/dashboard/servers/{serverId}/...` shapes. Any browser command, route helper, pane key, stream key, restore descriptor, or App-owned state that can reference an opaque workspace/workRoot/activity/terminal/file id from more than one server must carry or derive `serverId`; use `serverScopedIdentity` for local state keys instead of assuming bare ids are globally unique. Existing local-only persisted file panes and terminal restore records are read as `server-local`. {#260525-ws-dashboard-server-scoped-operation-forwarding}
- Backend server-scoped one-shot routes are explicit aliases, not a generic proxy: `server-local` dispatches in-process through the legacy root-picker/open/activation handlers, while linked servers forward only the registered ordinary HTTP/JSON operation to the legacy path with the stored daemon-lifetime bearer token. Unknown, unauthenticated, tunnel-required, or unreachable linked servers return bounded JSON refusals; unregistered server-scoped operation paths, including current SSE/WebSocket/terminal coverage gaps, must remain protected-router misses until a specific gateway implementation exists. Forwarded responses preserve upstream status/body and the opened-workRoot header where practical, but successful forwarded resource views must be rewritten from the remote daemon-local identity to the selected linked server id/label, including nested `ResourcePath.serverId` values. {#260525-ws-dashboard-server-scoped-operation-forwarding}
- The daemon resource route belongs inside the protected router and returns the public core view-model shape; `GET /api/dashboard/resources` reports live known-workRoot state seeded from daemon-local durable registry entries and returns an honest empty live view (`server` present, `workspaces: []`) before any workRoot is opened or remembered — it must never silently fall back to the mock workspace. {#260516-ws-web-dashboard-resource-view-model-contract} {#260516-ws-web-dashboard-live-resource-authority} {#260516-ws-web-dashboard-workroot-io-restore-model} {#260523-dashboard-workroot-registry-activation}
- WorkRoot `activation` is user-controlled targeting permission, while `availability` is discovery-derived filesystem/Git operability; do not overload `status` or collapse offline activation into missing/inaccessible availability. A known offline or unavailable root remains visible while its workspace remains visible, but file, Activity, terminal HTTP routes, terminal WebSocket I/O, resource rows, and activation actions must derive activation from the same registered workRoot id. The planned workspace-root policy treats workspaces as owner-managed root scopes: root workRoot unavailable means disabled or recovery-needed when an active child workRoot remains, while no active workRoots means automatic workspace pruning. {#260523-dashboard-workroot-registry-activation} {#260524-dashboard-workroot-registry-wide-activation-lookup} {#260524-dashboard-workspace-root-prune-policy}
- The open-workRoot route registers the requested path only after proving it is currently available, persists the registry update before advertising success, and rolls back in-memory membership if persistence fails. Successful responses return the aggregated live view of every known workRoot — not just the just-opened candidate — plus `x-ws-dashboard-opened-work-root-id`, because the daemon-owned opaque id is the only safe selector when labels collide. The single-candidate view built inside `open_work_root` is only the availability gate. {#260516-ws-web-dashboard-open-workroot-resource-refresh} {#260523-dashboard-workroot-registry-activation}
- The `OpenWorkRootControl` modal is server-scoped: local and linked-server row affordances share the same control, but linked-server picker list/navigate/create/pin/unpin/open calls must go through the local gateway server-scoped routes, never direct browser calls to linked daemon endpoints. Host or remote paths remain authenticated picker/open request data, not command payload identity; root-picker and `workRoot.open` command payloads carry `serverId` while omitting paths. React Aria collection keys may be paths inside picker-local state. Built-in places come from the selected server's root picker response and are navigation affordances only; the frontend must not infer host filesystem topology locally. Persisted pins are owner-managed sidebar navigation state in daemon-local persistence: pin/unpin must not create, open, delete, rename, or otherwise mutate filesystem/workRoot resources, and state-file writes must preserve both the workRoot registry and root picker pins. Picker loads are scoped by server identity plus modal/request lifetime; late responses after close, server-context reset, or successful open must not repopulate hidden state. Opening reconciles the aggregated open response immediately using the daemon-opened id header when present, selects against the response's rewritten server resource identity, then re-fetches that server's canonical resources as source of truth through the resource refresh coordinator. While the dashboard is mounted, bounded polling uses the same canonical endpoint for availability refresh, skips overlapping poll requests, queues foreground refreshes behind an in-flight poll, treats open/activation responses as externally applied newer resource views, ignores older in-flight poll results after those views or after unmount, and preserves the last known resource tree on refresh failure. `reconcileSelectedId` drops a selection that left the entity set so a stale mock-workspace selection cannot survive the mock-to-live transition. {#260516-ws-web-dashboard-open-workroot-resource-refresh} {#260523-dashboard-workroot-registry-activation} {#260524-ws-dashboard-root-picker-modal} {#260524-ws-dashboard-react-aria-root-picker-pilot} {#260524-ws-dashboard-root-picker-pins} {#260525-ws-dashboard-server-scoped-operation-forwarding}
- Git worktree add is workspace-scoped, not selected-workRoot-scoped: options/preview/submit routes resolve an available Git primary root or linked worktree inside the workspace, share the same daemon preview validation, and submit revalidates immediately before invoking `git worktree add`. Submit success must persist the new workRoot registry entry before returning canonical `resources`; the optional `createdWorkRootId` is only present when that id appears in the returned live view and is the browser's only authority for selecting the new row. Command payloads for `workspace.menu.open`, `gitWorktreeAdd.open`, `gitWorktreeAdd.close`, and `gitWorktreeAdd.submit` carry only `workspaceId`; owner-provided custom target paths are allowed only in authenticated modal request bodies and must not appear in command logs, URLs, tooltips, or resource ids. Preview and submit responses may display a target path label to the authenticated owner, but bounded errors must not leak daemon-private command arguments or Git roots. {#260524-ws-dashboard-git-worktree-creation}
- `daemon/tests/fixtures/dashboard_resources.json` is the shared golden mock artifact consumed only by `MockDashboardResourcesProvider` and its deserialization test; the canonical route no longer exercises it. Keep mock data in the fixture instead of a second in-code sample. {#260516-ws-web-dashboard-mock-view-model-fixtures}
- Local discovery preserves workRoot identity from the remembered candidate path, not the canonical symlink target, so availability or kind changes do not churn `resourcePath.workRootId`. {#260516-ws-web-dashboard-local-workroot-discovery-provider}
- Existing directories must be readable before they are classified as online Git/plain roots; metadata success alone is not enough because unreadable directories must surface as inaccessible. {#260516-ws-web-dashboard-local-workroot-discovery-provider}
- Root picker routes belong inside the same owner-auth protected router as other dashboard APIs; they may expose host paths only as authenticated picker/open request data, never as public resource ids. {#260516-ws-web-dashboard-root-picker-empty-directory-creation}
- The only filesystem mutation in the first root picker backend is single-segment empty-directory creation; generic delete, rename, move, copy, and recursive folder operations stay absent. {#260516-ws-web-dashboard-root-picker-empty-directory-creation}
- WorkRoot file listing routes address a known online/available workRoot by opaque `workRootId` and accept only workRoot-relative child paths. Listing responses must not expose daemon-private absolute host paths, must reject traversal before reading outside the root, and remain read-only. {#260516-ws-web-dashboard-workroot-file-listing-api}
- Read-only file reads share the workRoot-relative route boundary and must bound content size both before and after reading, reject binary/unsupported content, and return unavailable states without exposing absolute host paths. Writes reuse the same route boundary, require the caller's last read content hash, serialize per `workRootId + path`, reject conflicts without writing, and publish `document.contentChanged` only after a successful daemon write. {#260516-ws-web-dashboard-readonly-file-api} {#260524-ws-dashboard-document-edit-save-fanout}
- Document translation routes are owner-authenticated dashboard routes, not frontend-only helpers. Provider config, API keys, prompts, raw model responses, and cache storage stay daemon-private; browser-visible provider/status/cache/block results must be bounded and secret-free. {#260524-ws-dashboard-document-translation-overlay}
- Translation cache identity must include every prompt-affecting dimension: source content hash, target and source locale, document title, provider id/kind/model/config version, block model version, and prompt version. Omitting one can silently reuse a stale translation for a different prompt. {#260524-ws-dashboard-document-translation-overlay}
- WorkRoot Activity is a read-only projection over known online/available Git workRoots. It derives the wsstate `proj/<projectKey>` or `proj/<projectKey>@<worktreeId>` state directory from canonical Git roots, reads current named-agent rows from `state.sqlite agent_defs`, resolves file-backed payloads through each row's safe relative `state_path` under `agents/`, and treats non-Git/bare roots plus missing, locked, or incompatible registries as an empty healthy projection. Do not scan `agents/*/agent.json` or join payload directories by `agent_key`; the role key is browser identity, while `state_path` selects current-call/output/native-session payloads. Retained `agent_instances` rows can add historical `items` only after cleanup-state/useful-signal filtering; they must keep opaque `agent-instance:<token>` ids, resolve transcripts through the retained row's `state_path`, and never affect `agents` compatibility rows or current summary totals. Agent cache paths, host paths, session ids, raw instance ids, payload paths, pids, output paths, and stream paths stay daemon-private; current-call state is reduced to bounded status/timing/error fields and presence flags. The Activity Feed `items` list is the forward source-neutral contract; `agents` remains a compatibility projection for the existing pane and must be kept in sync until that consumer is removed. Current named-agent items use `agent:<agentKey>` ids and historical retained items use selected-item backfill over bounded transcript blocks, not live stream or control authority. Codex native session JSONL can replace `output.md` as the block source only when daemon-private registry metadata identifies a Codex backend or harness and a bounded session lookup succeeds; `output.md` remains the fallback. {#260517-ws-dashboard-workroot-activity-projection} {#260521-ws-dashboard-activity-console-read-model} {#260522-ws-dashboard-activity-console-transcript-expansion} {#260525-ws-dashboard-sqlite-agent-activity-source}
- WorkRoot Activity freshness has two private signal classes that must be combined, not prioritized: SQLite registry timestamps/cleanup/retention metadata can change item versions and recent ordering even when payload files are untouched, while payload mtimes for current-call, output, runtime log, stdout, stderr, and native transcript files still carry transcript-only freshness. Recent-limit selection uses the latest valid registry or payload timestamp with RFC3339Nano fractional precision preserved; visible current-agent timing remains the user-facing `last_call_at || last_seen_at || updated_at` fallback rather than the private freshness key. {#260525-ws-dashboard-sqlite-agent-activity-source}
- The Activity Console event route is an owner-authenticated SSE stream scoped to one known online/available `workRootId`, but it is currently a bounded polling fallback over `work_root_activity` snapshots rather than native filesystem watch state. It always announces `pollFallback`, emits source-neutral `ActivityConsoleEvent` payloads as `event: activity` SSE frames, and uses snapshot invalidation on reconnect/coalescing instead of promising durable replay from `after` cursors. {#260521-ws-dashboard-activity-console-watch-stream}
- Activity transcript expansion is daemon-owned and preserves the public `ActivityTranscript`/`TranscriptBlock` browser contract. Native Codex parsing normalizes fixture-backed assistant/status/user prompt/message/tool call/tool result/custom-tool/MCP/exec-command/patch-apply/interruption/handoff records into bounded blocks. Low-value Codex telemetry such as token counts, session metadata, and turn context can be skipped rather than rendered as transcript noise. Malformed or unsupported records must stay useful but safe: provide bounded structural context or omission reasons without echoing raw native JSON, paths, session ids, private record strings, or tool output. Claude, Gemini, and exec native sources stay unsupported until fixture-backed formats exist, and live transcript updates intentionally use feed-level `transcriptUpdated` plus selected backfill instead of block-level SSE. {#260522-ws-dashboard-activity-console-transcript-expansion}
- The Activity Console frontend is a route-backed read-only workbench surface, not a second activity authority. Ribbon selection, transcript refresh, and load-more controls dispatch dashboard commands with stable command ids, while background feed/transcript fetch completion stays guarded by workRoot/activity/request identity so stale async results cannot overwrite a newer root, selection, or unavailable transcript state. Live UX consumes the daemon stream through named `event: activity` EventSource frames (with default-message compatibility), applies item upserts/removals into the source-neutral feed, refetches snapshots for invalidations, refreshes transcripts only for the selected item, and keeps `recentLimit` polling as a stream-error or `pollFallback` fallback instead of normal healthy-stream behavior. Activity pane opening now uses opened-surface support-split placement, then records the pane in App-owned per-workRoot pane order so rerenders and resource refreshes do not snap it back to the agent/terminal group. Transcript reads are tail-first by default; older history is fetched with the selected transcript's earliest cursor and prepended from the top edge while preserving the visible scroll offset. Transcript scroll state is browser-local and keyed by workRoot plus activity; it follows the tail by default, pauses when the user scrolls away, and preserves the away-from-tail position across selected-transcript refreshes and split rerenders until the user returns to the tail. Ribbon items use source discriminators rather than duplicate titles, and their status line may combine state, relative update time, and completed duration in the fixed three-line card. Compact transcript summaries must use only bounded normalized safe fields or first-line text, not arbitrary backend data stringification, so tool/status/degraded one-line blocks stay useful without leaking native payloads. {#260521-ws-dashboard-activity-console-ui-shell} {#260521-ws-dashboard-activity-console-live-ux} {#260522-ws-dashboard-activity-console-transcript-expansion}
- Terminal sessions are daemon-owned live resources scoped to known online/available workRoots. Terminal ids are opaque, input/output/resize/close routes stay owner-authenticated, re-check the owning workRoot before each access, and close must terminate and reap the PTY child rather than detach it. ## Coupling

- `server.rs` creates the auth state used by the router; route tests that build `AppState` directly must stay aligned with the server startup path.
- `static_dir` couples CLI config, `router.rs`, route tests, and frontend build output: production UI availability depends on passing the built `frontend/dist` directory, while auth behavior for `/`, `/servers...`, and assets is enforced by router placement rather than frontend code.
- Startup output intentionally prints the pairing URL for the local owner, while structured logs should avoid query-string/token material; request logging changes must preserve that split.
- Dashboard resource JSON couples `core/src/view_model.rs`, the daemon provider trait, the protected route tests, and the golden fixture; field or hierarchy changes must update all four in one logical change.
- `/api/dashboard/resources` is live-backed by `LocalDashboardResourcesProvider` over the daemon's known registry entries, which may be seeded from `persistent_state.rs`; persistent state is only a startup seed and durable registry snapshot, not an alternate resource authority. The frontend refresh coordinator depends on this endpoint recomputing availability without mutating activation or membership. The mock provider stays behind the same seam only for deterministic frontend/contract tests and explicit fixture contexts. Live discovery runs synchronous fs and `git`-subprocess work, so the canonical handler wraps it in `spawn_blocking` to keep it off async worker threads.
- Root picker open and activation routes couple `root_picker.rs` to `resources.rs` (`live_dashboard_resources`) and `work_root_files.rs` (`OpenedWorkRoots::candidate_roots`): open/activation mutations serialize persistence and roll back in-memory registry changes on write failure, then return the aggregated live view over all known workRoots, so provider field changes ripple into route tests.
- Server-scoped one-shot forwarding couples `router.rs` protected route registration, `servers.rs` linked-server session/endpoint resolution, the legacy root-picker/open/activation handlers, and resource-view rewriting. Extending it requires an explicit route-to-legacy-path mapping plus tests for local alias equivalence, bounded linked-server refusals, upstream status/body/header preservation, and remote `DashboardResourcesView` server-id rewriting; adding a route path alone should not make arbitrary daemon paths forwardable. {#260525-ws-dashboard-server-scoped-operation-forwarding}
- Remote root-picker/open behavior couples `ServerRows`, `OpenWorkRootControl`, root-picker/open helper endpoints, command builders, the resource refresh coordinator, and the Phase 2 gateway. Tests need to cover route selection through `/api/dashboard/servers/{serverId}/...`, command payload path omission with server identity retained, stale picker responses after close/context switch/open, and selection of the opened linked-server WorkRoot from rewritten resources; unit-only helper coverage is not enough because the race is modal-lifetime and browser-state dependent. {#260525-ws-dashboard-server-scoped-operation-forwarding}
- Git worktree creation couples `git_worktree.rs`, `router.rs` protected route placement, `OpenedWorkRoots` persistence, `live_dashboard_resources`, `frontend/src/gitWorktreeAdd.ts`, command builders, App modal state, and browser acceptance. Route tests must cover unauthenticated rejection, non-Git workspaces, existing checked-out branches, blocked submit side effects, persistence rollback, existing-branch checkout identity, resource aggregation, and `createdWorkRootId`; frontend tests must keep URL privacy and blocked-submit preview preservation aligned with modal stale guards.
- Browser acceptance fixtures are order-sensitive once a test opens more than one Git workRoot: Activity route fixtures must resolve the intended main `workRootId` from authenticated `/api/dashboard/resources` before installing per-root Activity responses, rather than treating the first Activity request as the main fixture root.
- WorkRoot file listing couples successful root picker opens, activation state, daemon `AppState`, and `work_root_files.rs`: listing can resolve only daemon-registered, online, currently available workRoots and should not infer host paths from browser-provided ids.
- Text document panes couple daemon file read/write authorization, frontend file helpers, command-routed edit controls, document event refresh, and workbench placement state. Changes to logical surface keys, placement groups, read/write response shape, or source-key fan-out require route/helper/workbench tests together.
- Markdown document viewing couples `App.tsx` pane selection to `documentViewer.tsx` pure model helpers and browser acceptance. Parser/render changes must keep unit tests for block ids, line ranges, pathref privacy, safe links, and overlay matching aligned with daemon-served Playwright evidence.
- Document translation couples `router.rs` protected route placement, `server.rs` environment-backed service construction, daemon route tests with fake OpenAI-compatible providers, `commands.ts` command identity, `App.tsx` pane-local toggle/request state, and `documentViewer.tsx` payload/overlay helpers; provider, cache, or block-shape changes need all of those updated together.
- Document events are invalidation signals, not a durable change log: the daemon broadcast stream is per process and workRoot-scoped, while the browser must keep focus/visibility re-read fallback and request sequencing so stale event/fallback reads cannot overwrite newer pane content. {#260524-ws-dashboard-document-edit-save-fanout}
- WorkRoot Activity couples `work_root_activity.rs`, core activity view structs, frontend `workRootActivity.ts`, App-owned EventSource lifecycle, protected route tests, frontend helper/browser tests, Codex session fixture parsing, and the wsstate cache layout. Key derivation must stay compatible with the Go wsstate tool, including linked-worktree keys, Windows verbatim-prefix stripping, and raw Unix path bytes for non-UTF-8 paths. Feed metadata (`updateMode`, `feedCursor`, `selectedItemId`) travels with the newest item snapshot during frontend merges; otherwise incremental refreshes can show stale selection/cursor hints beside fresh source-neutral rows. Streamed selected-item revisions remain dirty until explicit acknowledgement; selection changes or transcript refreshes must not silently clear the local dirty cue. Native Codex session mtimes participate in recent ordering and watch diffing, so transcript-only native session changes still need feed-level `transcriptUpdated` coverage.
- Terminal substrate couples daemon terminal registry state, workRoot access gating, PTY process lifecycle, frontend terminal helpers, workbench pane ordering, browser input-fidelity evidence, and portability evidence. Changes to close, resize, output cursoring, WebSocket attach/resume, workRoot access re-checks, stale HTTP fallback polling, placement, shell selection, or command profiles require daemon route tests plus frontend terminal/workbench tests. `terminalSizeBounds` in `terminals.ts` mirrors the daemon PTY `MIN/MAX` columns/rows in `crates/daemon/src/terminal.rs`; changing one bound requires changing both.

- Instance event JSON couples `core/src/events.rs`, daemon fixture transcripts, and future stream routes; changing cursor, category, payload, or resource identity fields must keep fixture and serialization tests aligned.

## Common Mistakes

- Adding a new route to the top-level router beside `/pair`, which bypasses owner auth.
- Treating `/api/dashboard/servers/{serverId}/...` as a wildcard proxy or forwarding SSE/WebSocket/terminal routes through the one-shot JSON helper; only explicitly registered protected aliases are forwardable, and deferred operation families should 404 until implemented.
- Opening a linked-server root picker by constructing the linked daemon endpoint in browser code, omitting `serverId` from root-picker command payloads, leaking remote paths into command logs, or allowing late picker responses from a closed/reset/opened modal to seed the next picker session.
- Serving frontend assets through a separate unauthenticated static-file service or fallback route; the frontend is not an auth boundary and must rely on daemon owner auth.
- Reintroducing `WorktreeId`, `worktreeId`, or `worktree_id` at the public dashboard core/API boundary; linked Git worktrees are a `WorkRootKind`, not the identity vocabulary.
- Pre-collapsing singleton workspace/workRoot chains in the daemon, selecting a main instance id for the compact browser row, or making compaction depend on main/sub instance presence; these break stable workRoot selection and re-couple navigation to workbench surfaces.
- Editing Rust mock constructors without updating `dashboard_resources.json`; the fixture is the source of truth for deterministic mock responses.
- Hashing canonical paths for remembered workRoot ids; symlink targets and missing paths can change while the dashboard must keep the same remembered workRoot identity.
- Duplicating dashboard resource fixtures in React state, hiding post-load refresh errors, trusting `/servers/:serverId` over `/api/dashboard/resources`, or bypassing `resourceRefresh.ts` for loads/polls/open reconciliation; all make the browser disagree with the daemon-owned resource view or let stale poll results overwrite newer open/activation views.
- Backing the canonical `/api/dashboard/resources` route with the mock provider, or returning the mock workspace when no workRoot is opened instead of an honest empty live view.
- Returning only the just-opened candidate from the open-workRoot route instead of the aggregated view of every known workRoot, dropping previous registry entries from the immediate response.
- Selecting a newly added Git worktree by label, target path, or row order instead of the daemon-returned `createdWorkRootId`; browser-created branch names and display labels can collide or be transformed.
- Letting the file explorer replace or obscure resource identity navigation, or turning read-only file preview into an editable surface.
- Treating Markdown document view or raw edit mode as a new pane identity, backend document authority, or safe navigation surface; both ride the same read-only file pane lifecycle, use local AST/raw-draft state, and keep relative links inert.
- Echoing raw translation provider output, unknown provider block ids, API keys, prompts, cache paths, or absolute source paths into browser responses/status; the daemon must reduce failures to bounded statuses/reasons before the overlay sees them.
- Adding translation prompt inputs without adding the same dimension to the daemon cache key; source locale and title are easy to miss because they do not affect the frontend content hash.
- Deriving an opened workRoot id in the browser from labels, paths, or flattened order instead of consuming the daemon-opened id response header; same-label roots will select the wrong row.
- Treating a successful open or activation response as valid before registry persistence succeeds, or failing to roll back the in-memory registry after persistence failure.
- Using `status` as both availability and activation, deriving resource-row activation from a different source than route gates, pruning a workspace only because its root workRoot is unavailable while a child remains active, or letting explicit forget/remove UI substitute for automatic empty-workspace pruning.
- Rendering read-only file panes under whichever workRoot is currently selected instead of the pane's owning workRoot, or appending panes directly to a hard-coded split instead of using workbench placement policy.
- Keying preview read-only panes by file path or bare workRoot id instead of one preview logical surface per server/workRoot, or failing to discard stale preview read responses; quick file clicks or same-id linked servers will leave duplicate previews or show content for the wrong selected preview.
- Pinning a file without removing the workRoot's matching preview pane; the tab strip will show both preview and pinned copies for the same file and browser evidence will miss the intended preview-to-pinned transition.
- Updating only the pane that performed a save, or blindly overwriting dirty drafts on a document event; same-source preview/pinned panes must fan out clean content, while dirty drafts become stale and preserve local raw text.
- Treating document SSE events as durable filesystem watch truth; they are best-effort daemon write invalidations and still require focus/visibility reread fallback with stale-response guards.
- Adding overflow only to `.readonly-text-content` while breaking the height chain through `.workbench-pane[data-surface-kind="editor"]`; long files will expand the Dockview panel instead of scrolling inside the pane.
- Letting terminal output/input/resize routes or already-open WebSockets remain usable after close, workRoot deactivation, or unavailable state; rendering closed panes from stale output polls; or treating terminal panel close as detach rather than terminate.
- Treating HTTP terminal output polling as still-live while a WebSocket is connecting or connected; this reopens the duplicate-output race that the cursor and `canApplyTerminalOutputPoll` guards exist to prevent.
- Using Playwright keypress-only assertions as terminal input-fidelity evidence; the browser gate must observe shell-visible effects for editing, history, control keys, paste, clear-screen behavior, and Dockview focus/fallback paths.
- Forwarding terminal fallback keydown events during IME composition, handling `ctrl-u`/`ctrl-w` as browser shortcuts instead of xterm-style raw control bytes, or omitting browser evidence that the xterm helper textarea keeps focus across input and shell output; these break native shell line editing when Dockview focus leaves the helper textarea.
- Adding padding or generic pane chrome around the terminal fit container without rechecking xterm's measured screen box; FitAddon will otherwise overestimate rows and clip the bottom line of scrollback or fullscreen TUIs.
- Treating a local POSIX browser pass as native-Windows evidence, running an external daemon browser gate without explicitly binding the remote shell profile/platform, or using a Playwright-host temp workRoot path when the daemon runs on another host.
- Adding a "focus the freshly created surface" effect without a per-request sequence guard, or keeping terminal fallback focus after selecting a non-terminal Dockview pane; either reasserts/duplicates terminal input against the user's visible selection.
- Reintroducing a bodyless placeholder or mock terminal pane; an opened workRoot with no live daemon terminal must show an explicit empty workbench with a `New terminal` affordance.
- Restoring terminal tabs by reusing stale daemon terminal ids, storing host cwd paths, or bypassing `terminal.create`; daemon restarts only allow new sessions from safe workRoot-relative cwd hints.
- Persisting workbench surface kind, row policy, or daemon ids in layout JSON; those belong to the dashboard registry/resource model and make restored layouts authoritative over daemon state.
- Returning raw Dockview panel or group handles from dashboard workbench APIs; that bypasses the adapter policy for detach, placement, floating/popout, focus, and later PTY/TUI resize constraints.
- Handling Dockview tab close inside the Dockview adapter instead of sending a dashboard close request with pane id, surface kind, and cursor coordinates; that skips registry confirmation policy and breaks cursor-near session prompts.
- Treating visible tab drag/drop as raw Dockview state; the adapter must synchronize Dockview moves into dashboard-owned pane order and active-pane reconciliation so cross-split moves, empty split drop targets, and resource refreshes do not snap tabs back, show stale bodies, repeatedly activate inactive split groups, or churn pane parameters from recreated React node identity.
- Keeping Dockview-created group ids, pane order, or active-pane state global instead of keyed by workRoot; opened roots will leak split layouts or active panes into each other.
- Letting automatic placement target user-created groups 3+; current policy preserves those groups but only auto-places opened/support surfaces such as read-only files and WorkRoot Activity into group 2, and terminals into group 1 unless later explicit targeting policy changes.
- Reintroducing a custom two-row pinned/opened tab shell beside Dockview; Dockview is the visible tab owner, while pinned/opened policy survives as dashboard model state and tab metadata.
- Making the tab close button permanently visible or replacing the cursor-near Yes/No popover with `window.confirm`; the acceptance gate asserts hover/focus reveal metadata and non-native confirmation behavior.
- Reintroducing generic workbench pane header/footer chrome as a shared status surface; visible identity now belongs to Dockview tabs backed by dashboard metadata, while useful status/control affordances must be pane-local.
- Reintroducing mainInstance/subInstance rows as default left-nav hierarchy; that competes with the workRoot workbench and breaks the workspace/workRoot navigation model.
- Adding a visible dashboard control that mutates state directly from a click handler without a command builder/dispatcher path; keyboard bindings will either fork behavior or miss observer evidence.
- Putting owner custom Git worktree target paths into workspace-menu/add-worktree command payloads, URLs, test notes, or chrome labels instead of authenticated request bodies and bounded owner-visible preview text.
- Letting an older Git worktree preview or blocked submit response update the modal after inputs changed, or submitting from a preview that does not match the current request; this can show blockers for the wrong branch/path or create a different worktree than the user previewed.
- Opening duplicate workbench attachments because the caller keys by display title, raw Dockview id, or daemon process id alone instead of a dashboard logical surface key.
- Adding new dashboard UI with raw light palette values, rounded cards, decorative shadows, or gradients instead of the semantic dark tokens and square operational style.
- Treating `localhost`, `127.0.0.1`, explicit public bind mode, or passing Host/Origin checks as sufficient authorization for host-control features.
- Accepting absolute paths or `..` traversal in workRoot file listing requests, or leaking absolute root paths in listing responses/errors.
- Treating WorkRoot Activity as agent control authority, exposing wsstate/cache/session/process/output paths, hashing display/remembered workRoot ids instead of canonical Git roots for wsstate keys, using `agent_key` or `agent.json` as the payload authority instead of registry `state_path`, projecting retained `agent_instances` without cleanup/useful-signal filtering, adding historical rows to current `agents` counts, prioritizing registry timestamps over payload mtimes instead of comparing them as one freshness signal, adding new Activity Console behavior only to the legacy `agents` projection while leaving source-neutral `items`/transcripts stale, or making native transcript parsing depend on frontend-visible session ids/paths.
- Treating Activity Console `after` cursors as a durable event log, listening only to default EventSource messages, wiring fallback polling across all opened roots, or clearing dirty state on selection/streamed selected-item updates; reconnects may require snapshot refetch, backend frames are named `event: activity`, each stream must stay scoped to the subscribed workRoot, and dirty acknowledgement is browser-local until explicit user acknowledgement.
- Treating unsupported Codex native records as content-free noise, or echoing raw native record types, session ids, JSONL paths, tool output, raw JSON, or unsupported payload snippets in transcript blocks/diagnostics. Unsupported or malformed records should become bounded degraded blocks or aggregates with safe structural context and omission reasons.
- Logging full request URIs or health payloads that include pairing tokens, session cookies, wsstate internals, paths, or Git roots.
- Letting daemon harness startup/readiness failures print raw command arguments, forwarded endpoints, pairing URLs, hostnames, or static-dir paths; portability diagnostics should identify the failing layer without preserving private evidence.
- Building startup URLs before binding the listener and accidentally exposing `:0` to the owner.

## Technical Debt

- Pairing, bearer, and session secrets are process-memory only and have no persistence yet.
- Workbench close/select/move still use Dockview lifecycle callbacks directly; migrating them into command dispatch is a larger follow-up because confirmation anchors, drag placement state, and active-pane reconciliation are coupled.
