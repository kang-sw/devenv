# Terminal Frontend Render (ws Web Dashboard)

Sub-domain of `ws-web-dashboard`; read `ws-web-dashboard/index.md` first — the
terminal pane/WebSocket wire contract, xterm emulator behavior, and workbench
placement stay documented there, and daemon-side helper-process/registry/
reconcile mechanics are `ws-web-dashboard/terminal.md`. This file covers only
the frontend render-state batching layer sitting between per-chunk PTY
output and committed `terminalPanes` React state.

## Entry Points

- `ws-dashboard/frontend/src/terminals.ts` — `createOutputCursorFlushScheduler`: the framework-agnostic `accumulate`/`flushNow`/`cancel`/`pendingNextSequenceFor` factory; `appendTerminalOutput`'s front-trim (`outputTrimOffset`, `terminalOutputCharacterBudget`); `fetchTerminalOutputBatch`/`applyTerminalOutputBatch`/`applyTerminalOutputBatchError`/`nextTerminalOutputPollIntervalMs` for the batched HTTP fallback.
- `ws-dashboard/frontend/src/workbench/terminalVisualRestore.ts` — pure `resolveTerminalDeltaWrite` (alongside the existing `resolveTerminalMountWrite`): the noop/tail/reset decision over the absolute coordinate space, unit-testable without React/xterm.
- `ws-dashboard/frontend/src/App.tsx` — constructs one scheduler instance lazily per `WorkbenchShell` (ref-if-null), wires the `"output"` WebSocket branch's `accumulate` call, every `flushPendingOutputCursorsNow()`/`pendingNextSequenceFor()` call site, the revalidation effect's identity-signature memoization, and the poll-tick path (`fetchTerminalOutputBatch` build/apply, single in-flight guard, adaptive interval).
- `ws-dashboard/frontend/src/terminalPaneBody.tsx` — `writtenAbsoluteRef` (the emulator-side bookmark) and the mount/delta-write effects that seed and advance it.

## Module Contracts

- A WebSocket `"output"` frame no longer calls `setTerminalPanes` synchronously. `applyTerminalSocketMessage` instead calls `scheduler.accumulate(logicalKey, chunkSequence)`, which coalesces same-key advances via `Math.max` and commits the whole pending `Map<logicalKey, maxChunkSequence>` at most once per animation frame (`applyBatch` -> `setTerminalPanes(current => flushPendingOutputCursors(current, pending))`). This bounds `App` re-render and the workbench revalidation effect to one commit per frame regardless of PTY output volume or open-terminal count.
- Because the commit is deferred to the next frame, `pane.nextSequence` on committed React state can be stale at any point between chunks. Every site that reads or persists a pane's cursor, or tears down/reattaches a pane, MUST either call `scheduler.flushNow()` first (synchronously commits the pending batch and cancels+nulls the scheduled frame) or read the pending-adjusted value through `scheduler.pendingNextSequenceFor(pane)`. Skipping this reintroduces the stale-cursor duplicate-output-on-resume race `markTerminalOutputCursor`'s own doc comment (`ws-web-dashboard/terminal.md`) describes — at the batching layer instead of the per-chunk layer.
- The enumerated flush/pending-read call sites — adding a new pane teardown or persist path requires adding one here too: the non-`"output"` socket branch (`flushPendingOutputCursorsNow()` before its own `appendTerminalWebSocketMessage` merge), `closeTerminalPane` (flush before the async `closeTerminal` call), the work-root-close effect (flush before `removeTerminalPanesForWorkRoot` drops panes that may reattach by the same `logicalKey` later), the debounced visual-capture read in `terminalPaneBody.tsx` (via `TerminalPaneActions.getPendingNextSequence`, since that effect reads off its own `liveRef` inside a `window.setTimeout` outside App's rAF scheduling — a same-tick flush-then-read ordering isn't reachable across that boundary), and the `WorkbenchShell` unmount-cleanup effect (`scheduler.cancel()`, no flush — a torn-down tree must not receive a late `setTerminalPanes`).
- The revalidation effect (`App.tsx`, the `openWorkRootKeys` effect around the pane-reconciliation logic) depends on memoized `terminalPaneIdentities`/`agentChatPaneIdentities` arrays — built from a sorted, `,`-joined, `|`-delimited per-pane signature string of `paneId`/`workRootId`/`serverRoute` — instead of raw `terminalPanes`/`agentChatPanes` state, so a cursor-only flush does not re-trigger the O(open roots × panes) rescan.
- **Single absolute-coordinate-space invariant (260723).** `pane.output` is front-trimmed to stay under `terminalOutputCharacterBudget` (`appendTerminalOutput`), and `pane.outputTrimOffset` counts how many leading characters have been dropped. `outputTrimOffset`, `currentEnd = outputTrimOffset + output.length`, and `terminalPaneBody.tsx`'s `writtenAbsoluteRef` (an absolute stream position, not a raw string length) MUST all live in this one shared coordinate space. `resolveTerminalDeltaWrite` computes `localStart = writtenAbsolute - outputTrimOffset` and returns `noop` (`currentEnd === writtenAbsolute`) / `tail` (`localStart >= 0`, write `output.slice(localStart)`) / `reset` (`localStart < 0`, or the defensive `currentEnd < writtenAbsolute` branch — clear + redump the full retained `output`). Consequence: a front-trim that keeps `output.length` flat while the tail advanced is still detected as new content (`currentEnd` still grows), so no appended character is ever silently dropped; and an ordinary per-append trim never forces a spurious full `terminal.clear()`+redump — `reset` only fires when the writer fell a full trimmed buffer behind. Every seed site — mount-time restore/replay (`writtenAbsoluteRef.current = pane.outputTrimOffset [+ replay text.length]`), the live-socket direct-write path (raw increment, since that path never trims — offset stays `0`), and the poll-append path (via the same `resolveTerminalDeltaWrite` effect keyed on `pane.output`) — must seed/advance in this same absolute space.
- **Batched HTTP poll fallback (260723).** When the WebSocket path is unavailable (`shouldPollTerminalOutput`), `App.tsx`'s poll tick sends ONE batched `fetchTerminalOutputBatch` request per tick for every such pane (not one request per pane), hitting the daemon's `terminals/output/batch` route; `applyTerminalOutputBatch` applies the response to every requested pane in a single `setTerminalPanes` pass (or `applyTerminalOutputBatchError` on transport failure), guarded by a single in-flight flag so a slow tick is never overlapped by the next interval firing. The poll interval is adaptive (`nextTerminalOutputPollIntervalMs`, a pure step function of pane count with no hysteresis, backing off past `terminalOutputPollBackoffPaneThreshold` panes). The daemon batch route omits unknown/inaccessible terminal ids from `results` rather than erroring the whole batch ({#remote-terminal-http-lifecycle}) — `applyTerminalOutputBatch` treats a missing key as "no update this tick," never as an error.

## Extension Points & Change Recipes

- **Add a new pane teardown/persist site that reads a cursor**: add it to the flush/pending-read enumeration above, and call `flushPendingOutputCursorsNow()` (or the scheduler's `pendingNextSequenceFor`/`TerminalPaneActions.getPendingNextSequence` if flushing App state isn't reachable from that call site) before reading — never read `pane.nextSequence` straight off committed state at a teardown/persist boundary.
- **Change the revalidation-effect identity signature**: keep a delimiter-safe leading token (`paneId` first) when composing the join string; a signature built without one risks a false-negative collision if a `workRootId`/`serverRoute` value happens to contain the field or item delimiter.
- **Add a new `writtenAbsoluteRef`-style bookmark or a new `pane.output` writer path**: seed/advance it in the same absolute coordinate space as `outputTrimOffset` (never a raw string length) — see the coordinate-space invariant above.

## Common Mistakes

- Reading `pane.nextSequence` (or persisting a cursor) from committed `terminalPanes` state at a teardown/reattach/persist site without first flushing or reading the pending-adjusted value — this silently reintroduces the duplicate-output race the batching layer must not regress.
- Seeding or advancing `writtenAbsoluteRef` (or any future writer-position bookmark) as a raw string length instead of an absolute stream position — this silently drops output across a front-trim boundary (`localStart` computes wrong once `outputTrimOffset` is nonzero), reintroducing the gap `resolveTerminalDeltaWrite` exists to prevent.
- Gating status-dependent UI (e.g. the 260724 retirement gray-out) on `terminalPaneBody.tsx`'s component-local `displaySession` state instead of the `pane` prop's `pane.session.status`. `pane.session.status` is written by every status producer (the WS `"message"` listener via `appendTerminalWebSocketMessage`, and HTTP-fallback/reconciliation via `appendTerminalOutput`/`mergeListedTerminalSessions`), while `displaySession` is a separately-maintained local mirror whose freshness also depends on Dockview's panel-param-forwarding gate (`shouldUpdateDockviewWorkbenchPanelParams` in `workbench/dockviewLayoutModel.ts`, which deliberately withholds `persistentTerminal` panel param pushes — including a fresh `pane` prop — while `socketStatus` is `connecting`/`connected`, to avoid disrupting the live xterm stream). Read `pane.session.status` for new status-gated UI in this component instead of trusting that whole chain to stay wired.
