# Terminal (ws Web Dashboard)

Sub-domain of `ws-web-dashboard`; read `ws-web-dashboard/index.md` first —
route auth, workRoot access gating, and the browser-facing terminal
pane/WebSocket contract stay documented there. This file covers only the
daemon-side helper-process/registry/reconcile subsystem.

## Entry Points

- `ws-dashboard/crates/daemon/src/terminal.rs` — `TerminalSession`/`TerminalRegistry`: a thin daemon-side IPC proxy over a helper connection plus a local output-chunk read cache, the HTTP/WebSocket route handlers, and the `boot_reconcile`/`reconcile_entry` async driver.
- `ws-dashboard/crates/daemon/src/terminal_helper_process.rs` — the detached helper binary's own runtime (`run_terminal_helper`, dispatched from the hidden `ws-dashboard terminal-helper` CLI subcommand in `cli.rs`, never invoked by a human): owns the `portable-pty` master/child, the reader/writer threads, and `RingState`, the authoritative bounded output ring.
- `ws-dashboard/crates/daemon/src/terminal_reconcile.rs` — pure `classify(identity, ipc)`: the boot-reconcile decision table, decoupled from I/O for direct unit-testability.
- `ws-dashboard/crates/daemon/src/terminal_platform.rs` — cfg-gated detach-spawn / OS start-time read / identity-verified kill, split into a portable `unix` submodule (`spawn_detached` only, shared Linux/macOS) plus `target_os`-gated `linux` (`pidfd_open`+`pidfd_send_signal`), `macos` (`proc_pidinfo`+bare `kill(2)`), and `windows` (`OpenProcess`+`TerminateProcess` plus a `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE` kill-on-close job object for the shell subtree) leaves, re-exported through a cfg-independent block.
- `ws-dashboard/crates/daemon/src/terminal_registry_file.rs` — the on-disk `<registry_dir>/<terminal_id>.json` entry (pid, start_time, socket_path, ...): atomic temp-rename write, tolerant directory scan (skip-and-warn on a malformed entry).
- `ws-dashboard/crates/daemon/src/agent_profile_store.rs` — daemon-owned per-terminal spawn-profile provenance sidecar (`agent-profiles/<terminal_id>/profile.json`): write/tolerant-read/path helpers, read back in `reconcile_entry`'s adopt arm so a terminal re-adopted after a daemon restart still reports the profile it was spawned with. {#260725-ws-web-dashboard-terminal-spawn-profile}
- `ws-dashboard/crates/daemon/src/terminal_helper_ipc.rs`, `terminal_helper_protocol.rs`, `terminal_ipc_transport.rs` — NDJSON framing, the daemon<->helper message enums, and the cross-platform transport underneath (Unix domain socket / Windows named pipe, type-erased behind `BoxedIpcStream`). Deliberately separate from the browser-facing `TerminalWebSocketServerMessage`/`TerminalWebSocketClientMessage` wire contract in `terminal.rs`.
- `ws-dashboard/crates/daemon/src/terminal_reaper.rs` — thin interval-tick + spawn/abort glue around `TerminalRegistry::sweep_once`; wired by `server.rs` right after `boot_reconcile` on a `TERMINAL_REAPER_INTERVAL` (10s, owned by `server.rs`) tick, `JoinHandle::abort()`ed at both shutdown `select!` branches. {#260728-terminal-helper-periodic-reap}

## Module Contracts

- The daemon does not own the terminal PTY. A detached `ws-dashboard terminal-helper` process owns the `portable-pty` master/child and its reader/writer threads; `terminal.rs::TerminalSession` is a proxy plus a read cache fed by helper pushes, never a second source of truth. {#260516-ws-web-dashboard-terminal-registry-pty-spawn}
- A live terminal survives a daemon restart. `TerminalRegistry::boot_reconcile` MUST run to completion before `build_router`/`axum::serve` starts accepting connections (wired in `server.rs::run`) so an adopted terminal is already visible to the very first `list_terminals`/WS-reattach request. It scans the registry dir, checks each entry's OS-level identity (PID + start-time) before ever attempting an IPC connect, and applies `terminal_reconcile::classify`'s 6-row table (collapsed to 5 code branches because identity short-circuits before IPC is consulted): `AdoptLive`/`AdoptGrace` insert via `insert_unchecked` — bypassing the session cap so scan order can never evict an adopted session — `KillVerified` kills through a verified handle then drops the entry, and `DropNoSuchProcess`/`DropPidReused` only delete the registry entry. An unverified identity is NEVER killed. {#260523-ws-dashboard-terminal-tab-restore}
- Every kill of a registry entry (boot-reconcile's `KillVerified` row, `TerminalSession::spawn`'s handshake-failure orphan kill, and `sweep_registry_backstop`) routes through the shared `kill_verified_and_delete_entry` helper, which calls `terminal_platform::kill_verified` then prunes both registry files; `TerminalSession::terminate`'s fallback tier calls `kill_verified` directly, since it already owns that session's registry-entry lifecycle. `kill_verified`'s TOCTOU guarantee is platform-tiered, not uniform. On Linux/Windows it is an identity-gated *handle* (pidfd / process handle) captured at verification time — never a bare-PID re-resolve — which structurally closes the PID-reuse TOCTOU window a plain `kill(pid, SIGKILL)`/`TerminateProcess(pid)` would leave open. macOS has no pidfd-equivalent stable handle: it re-verifies via `proc_pidinfo` immediately before signalling, then signals the bare recorded pid through `kill(2)` — this narrows but does not close the same race, and its best-effort post-kill re-read only logs a pid-reuse *signal*, never a reliable mis-kill detector. Measured platform quirk: macOS `proc_pidinfo` returns no info (n=0) for a genuine unreaped zombie of our own target, indistinguishable from a pid that is simply gone — so the post-kill re-read's `SZOMB`-status discrimination branch, while present in the code, is not reachable through `proc_pidinfo` in practice; "gone" and "our own zombie" collapse to the same silent-success outcome.
- Beyond the daemon-restart and lazy next-terminal-creation paths, `TerminalRegistry::sweep_once` proactively reaps two orphan classes on every `TERMINAL_REAPER_INTERVAL` tick. `sweep_evict_expired` evicts in-memory sessions strictly by `!admits_attach()` — the same grace-authority gate `insert()`'s own lazy retain uses, never `!is_live()`, which would evict a session still inside its 30s attach grace and leak its IPC connection (the periodic sweep can then never find it again) — then hands them to `evict_and_close` for IPC teardown. `sweep_registry_backstop` separately re-scans the registry directory for entries with no live in-memory session, excludes anything younger than `registry_entry_is_stale_enough_for_sweep` (`connect_timeout + STALE_ENTRY_SWEEP_MARGIN`, 2s slack beyond the plain age gate — needed because `connect_timeout` alone leaves no room for the scheduling gap between `spawn` returning and `insert()` taking the write lock), and kills only identity-verified entries; it deliberately never calls `connect_and_handshake`, so it can never adopt. A time-boxed `recently_evicted` id set (`EVICTION_BACKSTOP_GRACE`, 30s) makes the backstop skip anything `sweep_evict_expired`/`insert` just evicted, so it cannot SIGKILL a helper still mid-graceful-self-exit. {#260728-terminal-helper-periodic-reap}
- `close_ipc_connection` (invoked after `sweep_evict_expired`'s eviction, and by `terminate()`) must tear down BOTH halves of the daemon<->helper IPC stream: aborting only the reader task (`reader_task`) or dropping only the daemon-side `Arc<TerminalSession>` does not close the underlying transport, because `tokio::io::split()`'s read/write halves share the same stream state. It aborts the reader task AND `.shutdown()`s the write half — the write shutdown half-closes the transport, which is what makes the helper's own reader observe EOF and self-exit; no new helper-side logic reacts to a daemon-initiated disconnect otherwise.
- `terminate()` is unconditionally 2-tier regardless of apparent success: send `GracefulShutdown` over IPC, sleep 200ms, then always run the verified-PID kill fallback — the daemon has no reliable signal that the helper actually processed the graceful request before its IPC connection could drop.
- An exited terminal stays listed and WebSocket-attachable for a bounded grace window (`TerminalSession::admits_attach()`, daemon-local `grace_until_ms`, `DAEMON_GRACE_WINDOW_MS` = 30s) even though `is_live()` would say otherwise. The helper independently self-exits after its own `GRACE_WINDOW` (also 30s) elapses, or after serving exactly one post-exit reattach — whichever comes first — regardless of what the daemon believes; the daemon's flag is a display/attach-gating convenience, not the authoritative timer. Only an explicitly-closed (removed-from-registry) terminal now rejects a WebSocket upgrade, with 404 (gone) rather than a strict-liveness 410. {#260723-terminal-attach-grace-window}
- Shell-exit detection does NOT hinge solely on PTY-master EOF. On Windows a detached `spawn_process_exit_reaper` thread blocks on `WaitForSingleObject(INFINITE)` (`terminal_platform::windows::wait_for_process_exit`) over a `DuplicateHandle` copy of the shell process handle — captured in `spawn_shell` before the `Child` moves into `shared.child` — and on wake drives the same `SharedState::transition(Exited)` -> `Exit` IPC path the PTY-EOF reader uses, so a shell that dies without ConPTY ever signalling EOF (conhost holding the pipe open) is still detected. The reaper MUST own a `DuplicateHandle` copy (`DUPLICATE_SAME_ACCESS` so it carries `SYNCHRONIZE`) rather than the borrowed `portable_pty::Child::as_raw_handle`, which is `CloseHandle`d when `kill_shell_if_running` drops the `Child` and would invalidate/recycle a handle the blocking wait still depends on. To make the observer safe against a daemon-initiated kill, `kill_shell_if_running` stamps the ring `Terminated` BEFORE `child.kill()` (cross-platform) so the reaper waking on that intentional death finds a non-`Running` ring and its `transition(Exited)` is a genuine no-op (`transition` is `Running`-only) instead of overwriting the daemon's `Terminated` over the wire. The whole reaper is `#[cfg(windows)]`: a second `waitpid`-based reaper on Unix would race/steal portable_pty's own `Child::wait()` reap, whereas Windows handles admit many concurrent independent waiters; the Unix grandchild-inherited-slave-fd residual is knowingly accepted (`pidfd_open`+`poll` is the clean analog if it ever matters). {#260516-ws-web-dashboard-terminal-websocket-transport} {#260723-terminal-attach-grace-window}
- `SharedState::transition` (`terminal_helper_process.rs`) reaps `self.child` via `wait()` (no `.kill()` — it already exited on its own) on every self-detected `Running -> non-Running` transition, not only the daemon-initiated `kill_shell_if_running` path. This closes a Unix zombie-shell gap where the PTY-EOF reader thread's own `transition(Exited)` call previously never reaped the child it had just observed exit.
- The helper's `serve_connections` accept loop bounds only its wait for the FIRST successful handshake to `NO_HANDSHAKE_TIMEOUT` (10s, independent of daemon behavior) — a helper that never gets an initial connection self-terminates instead of lingering forever. Once a handshake has ever completed, the existing unbounded `IDLE_ACCEPT_POLL` idle-reconnect wait is unchanged; only the pre-first-handshake wait is newly bounded.
- Daemon exit must NOT kill terminal helpers: there is deliberately no Drop-based teardown loop over `TerminalRegistry`/`AppState`. Re-introducing one would break restart-survival — a helper's shell must keep running with nothing attached until either the daemon comes back or the terminal is explicitly closed.
- Workspace/worktree-root removal must explicitly `.await TerminalSession::terminate()` for every session `TerminalRegistry::remove_for_work_roots` returns. An `Arc`-drop of the daemon-side proxy does nothing to a detached helper (unlike the pre-decouple in-process PTY master, whose drop implied SIGHUP). The three coupled call sites are `git_worktree.rs`, `resources.rs`, and `root_picker.rs`; a `tokio::spawn`-detached fire-and-forget kill here can lose its race against the enclosing runtime/process exiting and silently leak the helper — this was dogfooded and fixed to an inline `.await` before landing.
- Terminal input crossing the daemon<->helper wire is lossy for non-UTF-8 bytes: `write_input` converts input via `String::from_utf8_lossy` before sending it as NDJSON text, a deliberate simplification rather than adding a base64 wire encoding. The browser's primary input paths are already UTF-8 `String`; only the WebSocket binary-frame fallback path can lose fidelity.
- The daemon-side `TerminalSession.output` cache (`append_output_from_helper`) mirrors the same gapless, strictly-contiguous `sequence`-run invariant as the helper's authoritative `RingState`: every push consumes exactly one `next_sequence` value and eviction only ever pops from the front. `output_after` depends on this to slice by index arithmetic instead of a `filter(seq > after)` scan; a future change to either ring's retention/eviction must preserve gapless contiguity or the daemon-side shortcut must revert to a scan.
- The helper resets its per-connection "last sent sequence" to 0 on every new connection (fresh create, boot-reconcile adopt, or reattach) and replays its whole retained ring, flushed unconditionally at the start of `handle_connection` before the connection's select loop begins — not merely when a `Notify` permit happens to already be pending. This is the implicit backfill path for the common case; the protocol's `RequestBackfill`/`BackfillResponse` message pair exists but is not driven by this implementation.
- `mark_profile_pending`'s gate in `terminal.rs::TerminalSession::spawn` is `profile_id.is_some()`, not `hook_config.is_some()`: `resolve_create_command` returns `(None, _, None, None)` when no profile is named and errors before returning for an unresolvable one, so `hook_config.is_some()` strictly implies `profile_id.is_some()` but not the reverse — a resolved hookless profile (`dummy-echo`) still creates `agent-profiles/<id>/` via the provenance sidecar below. Narrowing the gate back to `hook_config.is_some()` reopens the concurrent-spawn GC race `pending_profile_ids` exists to close, because the sidecar write for a hookless profile would then land on a path the pending mark no longer covers. {#260725-ws-web-dashboard-terminal-spawn-profile}
- `agent_profile_store.rs`'s `profile.json` is deliberately unversioned: every field is `Option<T>` + `#[serde(default)]`, so a malformed or forward-written file reads back as absent rather than erroring, and it can never become a second instance of `terminal_registry_file.rs`'s skip-and-warn-on-malformed-entry hazard. It must never carry a secret — the callback token stays in `terminal-tokens/` (`agent_token_store.rs`) and `callback.json` (`agent_callback.rs`), kept in a separate file specifically so a hookless profile can have provenance without ever being handed a credential. {#260725-ws-web-dashboard-terminal-spawn-profile}

## Coupling

- `terminal.rs` <-> `terminal_helper_process.rs` are coupled only through the NDJSON messages in `terminal_helper_protocol.rs`, framed by `terminal_helper_ipc.rs`, carried by `terminal_ipc_transport.rs`. This protocol is independent of the browser-facing WebSocket wire contract in `terminal.rs`; changing one must not require changing the other.
- `terminal_reconcile::classify` (pure) and `terminal.rs::reconcile_entry` (async driver) must stay in lock-step: the driver duplicates the identity short-circuit `classify` also encodes (never attempting an IPC connect on unverified identity) so a change to one path without the other can desync unit coverage from actual boot behavior.
- macOS's `process_start_time` reads back `None` (via `proc_pidinfo` EPERM) for a pid it lacks privilege to query — e.g. one recycled by a root-owned process — where Linux's world-readable `/proc/<pid>/stat` would still yield a real start-time. `terminal.rs::identity_status` maps that same recycled-pid scenario to `IdentityStatus::NoSuchProcess` on macOS vs. `IdentityStatus::PidReused` on Linux. `terminal_reconcile::classify` currently treats both rows as drop-only, so the divergence is inert today, but a future change that gives those two rows different behavior must account for this platform-dependent classification skew rather than assuming parity.
- `terminal_platform.rs`'s Windows kill-on-close Job Object (`create_kill_on_close_job`/`assign_into_job`) is wired into `terminal_helper_process.rs`'s shell-spawn path right after `portable_pty::SlavePty::spawn_command` returns, via the child's raw handle rather than a `Command` — ConPTY does the actual `CreateProcessW` call internally, so there is no `creation_flags` hook to inject through `CommandBuilder`. This backs the verified-kill fallback tier with the same shell-subtree teardown Unix gets from `setsid()` + PTY-master-close.
- `terminal_registry_file.rs`'s on-disk entry is the identity source boot-reconcile keys off; a leftover `.sock` file after a hard-killed helper is disk hygiene only (`delete_registry_entry` prunes both) and has no effect on identity/adoption correctness.
- `terminal_reaper.rs` is a thin glue module: it owns only the interval tick and task lifecycle, while `sweep_once`'s actual decision logic (grace-authority eviction, registry-dir backstop, identity verification) lives in `terminal.rs` beside the private fns it needs. The tick period itself (`TERMINAL_REAPER_INTERVAL`) is chosen and owned by `server.rs`'s wiring, not this module.

## Extension Points & Change Recipes

- **Add a new daemon<->helper message**: add the variant to `terminal_helper_protocol.rs`'s `DaemonToHelperMessage`/`HelperToDaemonMessage`, keep it distinct from the browser WebSocket wire enums, and handle it on both sides (`terminal.rs`'s connection driver, `terminal_helper_process.rs::handle_connection`).
- **Change the boot-reconcile decision table**: edit `terminal_reconcile::classify` and its pure unit tests first (no I/O), then update `terminal.rs::reconcile_entry`'s matching identity/IPC handling; never let a row reachable from `classify` return a kill for an identity that was not independently `VerifiedOurs`.
- **Change terminal kill/teardown**: route every kill through `terminal_platform::kill_verified` (identity re-checked at kill time — a captured handle on Linux/Windows, a bare-pid `proc_pidinfo` re-verify-then-`kill(2)` on macOS since there is no stable handle there — never a fresh PID lookup with no re-verification at all); do not add a Drop-based cleanup path to `TerminalRegistry`/`AppState`; keep the three `remove_for_work_roots` call sites (`git_worktree.rs`, `resources.rs`, `root_picker.rs`) awaiting `terminate()` inline rather than detaching the kill into a spawned task.
- **Add a new platform leaf to `terminal_platform.rs`**: `unix` is a portable-Unix shared leaf (`spawn_detached` only), not a catch-all — `#[cfg(unix)]` alone would let a Linux-only syscall silently claim coverage on every Unix target, including macOS, with nothing to catch it. Add a new `target_os`-gated submodule (mirroring `linux`/`macos`) plus a matching arm in the cfg-independent re-export block at the bottom of the file; the trailing `compile_error!` arm exists so an unimplemented target fails the build instead of silently missing kill/identity functions.
- **Change terminal spawn environment**: keep shell executable selection (`terminal.rs::select_terminal_shell`, invoked from `terminal_helper_process.rs::spawn_shell`) and browser PTY capability environment as separate contracts. Non-interactive daemon launches may carry `TERM=dumb`, so the helper's spawn code must normalize unusable parent `TERM` values for the browser PTY session without overriding explicit capable terminal types.
- **Change the periodic sweep**: edit `sweep_evict_expired`/`sweep_registry_backstop`/`sweep_once` in `terminal.rs` and their pure/unit tests first; keep the `recently_evicted` skip-set and the `STALE_ENTRY_SWEEP_MARGIN` age-gate slack, and never let the registry-dir backstop call `connect_and_handshake` — it must only ever kill, never adopt.
- **Add or touch a terminal-removal path**: `remove`, `remove_for_work_roots`, `drain_all`, `insert`'s eviction `retain`, and `sweep_evict_expired` are the registry's fixed removal choke points, and each one owes BOTH obligations — forget the attention entry (`self.attention.forget`) and forget the callback token (`forget_token`: the in-memory `self.tokens` entry plus the on-disk `terminal-tokens/<id>.json` file). A new removal path, or an edit to one of these three, must discharge both, not just one; adding to this list means adding both calls, not one. The two eviction `retain`s (`insert`'s lazy path and `sweep_evict_expired`) discharge both through the shared `evict_and_close` they each hand their evicted set to — one implementation for two structurally identical retains — so an eviction path that skips `evict_and_close` silently owes both. The former known deviation (`insert`'s eviction discharging attention but not the token, `260728-bug-dashboard-terminal-eviction-leaks-callback-token`) is closed: eviction is now at full parity with the other three.

## Common Mistakes

- Assuming a daemon restart always produces a fresh terminal session; boot-reconcile can reattach to a still-live helper with cursor continuity, so tests/dogfooding that hard-kill the daemon must account for the helper outliving it.
- Relying on dropping the last `Arc<TerminalSession>` to close the shell; only an explicit `terminate()` (or the helper's own grace-window self-exit) does that now.
- Re-resolving a PID by number for a kill instead of routing through `kill_verified`'s identity re-check (a captured handle on Linux/Windows, a `proc_pidinfo` re-verify immediately before `kill(2)` on macOS); a reused PID would then kill an unrelated process.
- Treating boot-reconcile rows 3/5 (unverified identity — `DropNoSuchProcess`/`DropPidReused`) as kill-eligible; both are drop-entry-only by design.
- Dropping `writer_tx` (or the PTY `master`) before killing/waiting the child in `SharedState::kill_shell_if_running`/`transition` (`terminal_helper_process.rs`); only child death reliably unblocks a writer thread stuck on a full OS pipe buffer. This ordering lives entirely in the helper process now — `terminal.rs` no longer owns a writer thread.
- Calling `env_clear()` on a `portable_pty::CommandBuilder` to scrub inherited markers instead of removing them per-key: `CommandBuilder::new()` seeds a platform base environment at construction time (`get_base_env`), and on Windows that base reads HKLM/HKCU `Environment` and builds `PATH` as the system+user merge — `env_clear()` destroys that merge, so a child spawned this way resolves its program against a narrower `PATH` than a sibling spawned without the clear. Use `command.env_remove(marker)` per scrub key instead (`terminal_helper_process.rs::apply_claude_scrub_and_overlay`, :450-452), which removes exactly the markers from whatever `CommandBuilder::new()` already seeded rather than replacing that seed. This reasoning does not transfer to `std::process::Command` — it has no equivalent base-env construction, so hop 1's daemon->helper spawn (`build_helper_command`, `terminal.rs:1444`-`1449`) legitimately clears+repopulates from nothing. But `std::process::Command` has its own, opposite-shaped trap: it exposes no public API distinguishing "no env method was ever called" from "`env_clear()` called with nothing re-added" — `get_envs()` yields the identical empty iterator either way, so that property has no direct observable to assert on. The only proxy is the unix `Debug` rendering's `env -i` marker (Windows' `Debug` impl prints program + args only, with no env content, so any `Debug`-based assertion is unix-only by construction), and that proxy silently rots: std's unix `Debug` impl writes `cd {cwd:?} && ` BEFORE the `env -i` marker whenever `current_dir` is set (not set here today), so a `starts_with("env ")` assertion becomes a permanent false negative the day an ordinary local refactor — not an upstream std change — adds a `current_dir`. `helper_env_plan` (`terminal.rs:1313`) is the fix that generalizes: when a decision cannot be observed on the object it was applied to, extract the decision into an explicit value (`HelperEnvPlan`) and assert that value directly — `assert_eq!(helper_env_plan(None, None, fixture), HelperEnvPlan::InheritHost)` needs no platform-specific rendering and cannot be defeated by an unrelated refactor of the built `Command`. The hardened unix `Debug` sniff (`!debug.contains("env -i")`, with its own positive control) survives only as a non-load-bearing secondary detector for the one residual the plan value cannot see: an `env_clear()` written directly into `build_helper_command` outside the single plan-application site.
- Leaving a test-created terminal unclosed: with the PTY out-of-process, this leaks a real `ws-dashboard terminal-helper` OS process instead of silently exiting alongside the daemon/test process (tracked as a separate test-hygiene follow-up, not a correctness bug in this domain).
- Driving terminal input during the interactive-shell startup window in a real-daemon/real-PTY integration test: the daemon spawns the host default shell, and input delivered before the prompt is ready (heavy async `zsh`/powerlevel10k startup) is buffered and re-typed char-by-char by the line editor, so an early `exit`/command can sit unexecuted for seconds -> load-sensitive flake. Gate the real command behind a deterministic readiness handshake — send `echo <marker>`, then `poll_output_until_contains(<marker>)` proving the shell finished startup and is executing input — as `terminal_survives_*`/`terminal_live_pty_eof_*` do. `terminal_boot_reconcile_adopts_grace_row_*` still violates this and is flaky (idea `260724-idea-dashboard-daemon-terminal-lifetime-test-interactive-shell-timing`).
- Assuming an integration test's in-body `terminate()`/close reaps the helper on failure: the helper is detached (`setsid()`+double-fork), so it outlives the daemon child's `kill_on_drop`/SIGKILL, and a panic before shell exit (e.g. a readiness poll timing out) leaks a live helper plus its interactive shell — added host load that self-amplifies the flake above. Reap from a `Drop` guard (runs on success AND unwind): read `<WS_DASHBOARD_STATE_HOME>/terminals/<terminal_id>.json` for `pid`+`startTime`, verify identity through the crate's cfg-independent `terminal_platform::process_start_time` re-export before signalling (never kill a recycled PID, and never hand-parse `/proc/<pid>/stat` locally — see the mirroring mistake below), then `kill -KILL`.
- Letting the registry-dir backstop kill a session in the same sweep tick `sweep_evict_expired`/`insert` evicted it, or while it is still mid-graceful-self-exit: use/extend the `recently_evicted` skip-set (`EVICTION_BACKSTOP_GRACE`) rather than removing it, or a still-alive shell can be SIGKILLed out from under its own graceful shutdown.
- Setting the registry-dir age gate to exactly `connect_timeout`: this leaves zero slack for the scheduling gap between `spawn` returning `Ok` and `insert()` taking the write lock, so a legitimately-spawning entry can be reaped as an orphan. Use `registry_entry_is_stale_enough_for_sweep` (`connect_timeout + STALE_ENTRY_SWEEP_MARGIN`).
- Evicting sessions in `insert()`'s lazy retain by `!is_live()` instead of `!admits_attach()`: this fires before the 30s attach grace even starts and leaks the evicted session's IPC connection, since the periodic sweep can never find it again once it is gone from the in-memory map.
- Aborting the periodic reaper task only after graceful shutdown drain completes; abort it as soon as shutdown begins (mirroring the existing `shutdown_task` abort sites) so it cannot keep sweeping mid-drain.
- Decoding each PTY read chunk independently with `String::from_utf8_lossy(&buffer[..n])` in `spawn_reader_thread`: a multi-byte codepoint split across two `read()` boundaries gets double-corrupted into two U+FFFD instead of one correct char (intermittent Korean/emoji/CJK corruption under chunking). Carry the incomplete trailing bytes (bounded ≤3) forward in a small `Vec<u8>` to prefix the next read before decoding; only emit U+FFFD for a genuinely malformed span (`Utf8Error::error_len()==Some(n)`) or a truncated tail flushed lossily at EOF.
- Mirroring a platform syscall in test code instead of calling the crate's cfg-independent `terminal_platform::process_start_time` re-export: a hand-rolled `#[cfg(unix)]`-scoped `/proc/<pid>/stat` parser reads as portable but only implements the Linux form, so on macOS it silently never matches instead of failing loudly — a reap-on-drop test guard built on it leaks the helper process and its PTY on every run with no test failure to flag it.
- Binding the terminal helper's Unix-domain socket under any process's `std::env::temp_dir()`/`os.tmpdir()`/`$TMPDIR`-derived base — Rust test fixtures AND the Node/Playwright e2e harness alike: macOS's `sockaddr_un.sun_path` caps at 104 bytes (Linux's is 108), and macOS `$TMPDIR` resolves to a long per-session `/var/folders/<hash>/T/` path that can consume most of that budget before the terminal id and `.sock` suffix are even appended, so the bind fails. Rust fixtures scope a short base (`/tmp`, which macOS symlinks to `/private/tmp`) to `#[cfg(target_os = "macos")]` (`crates/daemon/tests/terminal_lifetime.rs::temp_fixture_path`, `crates/daemon/tests/routes.rs::terminal_registry_temp_dir`); the Node harness does the same for its `WS_DASHBOARD_STATE_HOME` temp dir on `process.platform === "darwin"` (`ws-dashboard/frontend/e2e/dashboard-acceptance.spec.ts`'s `socketSafeTempBase()`, added after this exact bug shipped once — 260725 Phase 1's browser-gate root cause). Any new test harness that binds this socket via a temp-derived base needs the same scoped short-path treatment — don't widen it to non-socket fixtures or to Linux, neither of which has the headroom problem. Production is unaffected by the temp-dir form of this mistake (the registry dir resolves through `$HOME/.local/state/ws-dashboard/...`, not a temp dir) but the underlying 104-byte ceiling is otherwise unguarded there — see `260725-bug-dashboard-terminal-socket-path-length-unguarded`.
- Testing `TerminalSession::terminate`'s fallback `kill_verified` tier by simply closing a terminal (`DELETE`) and checking the process died: under normal load the helper self-exits inside `terminate()`'s 200ms `GracefulShutdown` window, so the fallback SIGKILL path never actually runs and a naive test passes "for free" without exercising it. `kill -STOP` the helper immediately before the close (after verifying its identity, per the mistake above) to force it past the graceful window; `SIGKILL` is not maskable by `SIGSTOP`, so the forced fallback still succeeds and the death poll observes a real kill through that tier. See `terminal_close_kills_verified_process_via_fallback_kill` in `terminal_lifetime.rs`.
- Constructing `TerminalRegistry` via `TerminalRegistry::default()` in a test that then asserts on-disk registry/token state: `Default` resolves `crate::persistent_state::default_state_dir()` — the developer's own real state directory, not a fixture — so the test silently reads and writes real `terminal-tokens/<id>.json` files instead of a temp one, and gives no signal either way. Any test asserting on-disk state must build the registry with `TerminalRegistry::new(...)` and an explicit temp `state_dir`, as `remove_forgets_the_callback_token`/`remove_for_work_roots_forgets_the_callback_token` do.
- Seeding a fake session fixture through `insert`/`insert_unchecked` and then asserting a callback-token file's presence or absence: neither method writes `terminal-tokens/<id>.json` — `remember_token` (called by both) only inserts into the in-memory `self.tokens` map, and the on-disk file is written solely by `TerminalSession::spawn`'s hook-materialization path. A fixture that needs the on-disk half present (e.g. to prove `remove`/`remove_for_work_roots` deletes it) must call `agent_token_store::write_token` directly after inserting, as `insert_fake_live_session_with_token_for_test`'s callers do — otherwise a post-removal "file is gone" assertion passes vacuously because the file was never there.
- Calling `spawn_shell` directly from an in-process `#[cfg(test)] mod` to test the Windows reaper: `spawn_shell`'s Windows leg assigns the CALLING process into `terminal_platform::windows::create_kill_on_close_job()`'s `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE` job, so the `cargo test` binary itself joins the job and dropping the stored job handle at test end kills the whole test binary, including concurrently running sibling tests. Use a dedicated `crates/daemon/tests/*.rs` integration test that spawns the real `ws-dashboard terminal-helper` subprocess (`env!("CARGO_BIN_EXE_ws-dashboard")`), as `terminal_windows_reaper_acceptance.rs` does, confining the job's blast radius to that subprocess.
- Assuming the shell's OS PID is available over IPC for an out-of-band-kill test: no `HelperToDaemonMessage` variant carries it (only the helper's own PID, via `Handshake`), and a parent-PID discovery query (`Get-CimInstance Win32_Process -Filter "ParentProcessId=<helper pid>"`) returns TWO direct children on real Windows — the shell AND `OpenConsole.exe`, the modern ConPTY host process — so the query must filter to known shell executable names (pwsh.exe/powershell.exe/cmd.exe) or it may select the ConPTY host instead of the shell.
- Assuming a terminal pane's appearance proves its command actually started: creating a terminal completes its daemon handshake and builds the HTTP response BEFORE the helper attempts the child spawn, so the pane opens and renders even when the resolved command does not exist on the machine — a missing binary surfaces only later as an async status change, never as a failed create. This cuts both ways. It is what lets browser acceptance tests exercise a vendor agent profile with no dependency on that vendor's binary, credentials, or network (`e2e/agent-spawn-profile.spec.ts`; verified by repointing the profile at a nonexistent binary and observing the step still pass). It equally means a test that asserts only "the pane opened" proves nothing about the command behind it — assert on something the spawn itself produces if that is what you mean to check. This tolerance does NOT extend to restart survival, though: a failed `spawn_shell` puts the ring into `TerminalHelperStatus::Error` via `SharedState::transition`, which also stamps `exited_at`, and `serve_connections`'s outer accept loop self-exits the whole helper the next time the daemon's IPC connection drops (`None` from the reader, then `exited_at().is_some()` breaks the loop) — which is exactly what a hard `SIGKILL` of the daemon does. A restart-survival test that hard-kills the daemon and expects boot-reconcile to adopt a still-running helper therefore needs a command that actually spawns (a real vendor binary, or any real stand-in on `PATH`); a nonexistent-binary profile that tolerates the CREATE path will not survive that restart.
- Treating the daemon's startup stderr line (`ws-dashboard owner pairing URL: ...`, `server.rs:103`) as proof that boot-reconcile has finished: it prints strictly BEFORE `TerminalRegistry::boot_reconcile` runs (`server.rs:130`), with work-root registry loading in between — not after, despite reading like a readiness signal. A test or harness that watches stderr for that line and then immediately reads registry/adoption state off the filesystem races reconcile. Do a real round trip that only succeeds once the server is actually accepting requests — e.g. an HTTP pairing exchange, which blocks until the listener is live — rather than gating on that log line.
- Testing a deliberately-silent CLI's delivery path with hand-built requests on each side instead of driving the real binary end to end: `ws-dashboard terminal-notify` exits 0 and prints nothing regardless of outcome by design (`terminal_notify.rs`'s CONTRACT), and Phase 4's `post_terminal_turn_state` route persists/broadcasts nothing observable either (that is Phase 5's job) — so a test that hand-builds the JSON POST to the route, and a separate test that drives the real CLI against a throwaway mock listener, can each pass while the actual CLI-to-real-route seam is broken by a mismatched request shape on one side. `terminal_notify_end_to_end.rs` closes that gap by interposing a small transparent TCP relay between the real compiled CLI subprocess and the real running daemon: the CLI's `callback.json` fixture names the relay's ephemeral port, every byte still reaches the real daemon and its real route, and the relay tees the response bytes so the test — never the silent CLI — observes the real status line the route returned. This is a reusable pattern whenever a silent/no-effect CLI needs end-to-end proof without adding application-level observability that the phase's own scope forbids: interpose a transparent relay rather than instrumenting production code to make it observable.
- Proving a hoisted-mark-before-first-write ordering claim (e.g. `mark_profile_pending` must run before any `agent-profiles/<id>/` byte is written) with a timing poll instead of a lock-gated park: `mark_profile_pending` takes the write lock on `pending_profile_ids`, so a test holding a read guard parks the spawn task on that exact line and the write cannot have happened while the guard is held — a correct build cannot pass by winning a race, unlike a poll. This is NOT fully deterministic evidence, though: it pins only WHERE the task is parked, not the wall-clock instant it got there, so the window before asserting still has to stay generous enough for a mis-ordered build to have completed its write; a mutation run is what actually checks that residual assumption (`terminal.rs::spawn_marks_the_profile_pending_before_writing_the_first_sidecar_byte`).
- Rewording a daemon degrade/warning log line without checking for a regression test asserting its literal text: `crates/daemon/tests/agent_hook_missing_state_dir.rs:215` asserts real daemon stdout contains the exact substring `"no persistent state directory resolved"`; changing that wording silently breaks a passing test.
- Building a `tracing_appender::RollingFileAppender` via `.builder().build(dir)` without ensuring `dir` already exists: the builder's own startup log-pruning pass `fs::read_dir`s the target directory BEFORE it ever creates that directory, and on failure prints `"Error reading the log directory/files: ..."` directly to the process's real stderr from inside the library — not surfaced through the returned `Result`, so no caller-side error handling can suppress it. `terminal_notify.rs::log_failure` (the hidden `ws-dashboard terminal-notify` subcommand, fired as a vendor hook on every agent turn) has a load-bearing "write nothing to stdio" CONTRACT — any stdio output there becomes per-turn error noise inside the user's live agent session — so it must `create_dir_all(&dir)` before building the appender. A review-cycle fix that dropped that pre-existing call broke the contract the first time a hook fired against a fresh state dir with no `logs/` directory yet; the regression was caught only because the module's own stdio-silence integration test failed loudly on the draft, not by reading the library's source, which is itself evidence that test is load-bearing rather than decorative.
- Detecting a delete-then-recreate reset of a monotonic `(count, timestamp)` record — `notify_failure.rs`'s per-terminal failure record and `agent_profile_gc.rs`'s `NotifyFailureWatch::should_warn` warn-once flag over it — by comparing only the current count against the previously-observed count: a counter that is reset by DELETION (not decrement) restarts at 1, so "warned at count 1, self-heal clears the record, re-break also lands at count 1" makes `1 < 1` false and the count-only rule silently swallows the second, distinct breakage. That failure mode is not a corner case here — `count == 1` is the headline scenario the mechanism exists for (an idle owner whose single delivery attempt fails and nothing fires again). The reliable discriminator is that absent a reset, count and timestamp always advance together (every failure both increments one and stamps the other); a timestamp that advanced while the count did not can only mean a reset happened in between. Remember both fields together at warn time (`WarnedObservation`) and compare the pair, not the count alone. The deeper trap this proposal itself is a case of: the reset evidence lives only in a file polled by a periodic sweep (300s here), so any "drop the flag once you next observe it healthy" rule degrades to "drop it only if a poll happens to land inside the healthy window" — a window that can be far shorter than the poll interval (one agent turn here) and therefore effectively never sampled. Make the OBSERVATION itself carry evidence of the reset; do not try to poll faster.
